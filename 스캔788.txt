애자일 프로세스 모델

- 고객의 요구에 민첩하게 대응
- 요구사항의 변화를 유연하게 수용
- 대표적인 방법론: XP, 스크럼, 크리스털

애자일의 기본 가치

- 프로세스와 도구보다 → 개개인과 상호 소통
- 포괄적인 문서보다 → 실행 가능한 소프트웨어
- 계약과 협상보다 → 고객과의 협력
- 계획을 따르기보다 → 변화에 대한 대응


애자일의 핵심 원칙

- 고객 만족을 위해 가치 있는 소프트웨어를 빠르고 지속적으로 제공
- 개발 후반의 요구사항 변경도 수용
- 동작 가능한 소프트웨어를 짧은 주기로 자주 전달
- 업무 담당자와 개발자가 프로젝트 기간 동안 함께 참여
- 직접 만나서 하는 의사소통을 중시
- 실행 가능한 소프트웨어를 진척의 척도로 봄
- 자율적인 팀에서 좋은 요구사항·설계·아키텍처가 나옴
- 개발팀이 정기적으로 자신의 작업을 돌아보고 조율·수정

5. 애자일 프로세스 모델

(1) 애자일 프로세스 모델

① 고객의 요구에 민첩하게 대응하고 그때그때 주어지는 문제를 풀어나가는 방법론을 지칭한다.

② 폭포수 모델처럼 계획을 기반으로 하는 프로세스 중심의 전통적인 모델은 산출물 위주의 거대하고 무거운 방법론에 해당한다. 이러한 방법론은 요구 사항의 변화에 유연하게 대처하기 어렵다는 큰 문제점이 있다.

③ 가볍고 비교적 변화를 수용하기 쉬운 방법론이 필요하게 됐는데 이것이 익스트림 프로그래밍(XP : eXtreme Programming), 스크럼(scrum), 크리스털(crystal)과 같은 방법론들이다.

④ 애자일은 가벼운 프로세스 방법론의 공통적인 특성을 정의하는 말인데, 2001년 1월에 각 방법론의 전문가들이 모인 ‘애자일 연합(agile alliance)’ 그룹에서 서로의 공통점을 찾아 ‘애자일 선언문’이라는 공동 선언서를 발표한다.



(2) 애자일의 기본 가치
① 프로세스와 도구 중심이 아닌, 개개인과의 상호 소통을 중시한다.
② 문서 중심이 아닌, 실행 가능한 소프트웨어를 중시한다.
③ 계약과 협상 중심이 아닌, 고객과의 협력을 중시한다.
④ 계획 중심이 아닌, 변화에 대한 민첩한 대응을 중시한다.

(3) 애자일의 원칙
① 최우선적인 목표는 고객을 만족시키기 위해 가치 있는 소프트웨어를 빨리, 지속적으로 제공하는 것이다.
② 개발 후반에 새로 추가되는 요구 사항도 기꺼이 받아들인다. 애자일 프로세스는 고객의 경쟁력을 위해 요구 사항의 변경을 받아들인다.
③ 동작 가능한 소프트웨어를 짧으면 2주, 길면 2개월 간격으로 자주 고객에게 전달한다. 이때 간격은 짧을수록 좋다.
④ 프로젝트가 진행되는 동안에 업무 담당자와 개발자는 매일 서로 의견을 주고받으며 함께 참여한다.
⑤ 정보 전달을 위한 전화, 팩스, 인터넷 등 많은 매체 수단이 있으나 가장 효과적인 의사소통 방법은 역시 직접 만나 얼굴을 보면서 대화하는 것이다.
⑥ 진척 사항의 척도를 나타내는 방법은 여러 도구로 표현할 수 있으나, 가장 좋은 방법은 실행 가능한 소프트웨어를 보여주는 것이다.
⑦ 자율적 사고의 자유로운 분위기의 프로젝트 팀에서 최고의 아키텍처, 요구 사항, 설계가 나온다.
⑧ 프로젝트의 효율성을 향상시키기 위해 개발 팀 스스로 정기적인 미팅을 진행하여 자신들의 행동을 되돌아보고 조율 및 수정한다.


애자일(Agile) 방법론
애자일 방법론은 소프트웨어 개발 방법에 있어서 아무런 계획이 없는 개발 방법과 계획이 지나치게 많은 개발 방법들 사이에서 타협점을 찾고자 하는 방법론이다.
계획을 통해서 주도해 나갔던 과거의 방법론과는 다르게 앞을 예측하며 개발을 하지 않고, 일정한 주기를 가지고 끊임없이 프로토타입을 만들어내며 그때그때 필요한 요구를 더하고 수정하여 하나의 커다란 소프트웨어를 개발해 나간다.
애자일 개발 프로세스의 대표적인 방법으로 익스트림 프로그래밍(XP : eXtreme Programming)이 있다.



애자일의 여러 개발 방법론

• 스크럼(scrum)
• 익스트림 프로그래밍(XP : eXtreme Programming)
• 적응형 소프트웨어 개발 방법론(adaptive software development)
• 린 소프트웨어 개발 방법론(lean software development)
• 크리스털 패밀리(crystal family)
• 기능 주도 개발 방법론(FDD : Feature Driven Development)
• 동적 시스템 개발 방법론(DSDM : Dynamic System Development Method)
• 애자일 UP(AUP : Agile Unified Process)

6. XP(eXtremne Programming)

(1) XP 특징
① XP는 '고객의 요구사항은 변경된다.'는 가정으로 두고, 여러 번의 '릴리스(Release)' 및 '반복(Iteration)'을 통해 고객의 피드백을 수용해야 함을 주장한다.
② 이를 위해 고객과 개발팀이 함께 상주하여 필요한 경우 언제라도 커뮤니케이션(Communication)이 가능해야 한다고 주장한다.
③ 일반으로는 적은 수의 개발자로 구성된 웹 기반 소프트웨어 개발 팀에 적합한 개발방법론이라고 할 수 있다.

(2) XP 용어
| 용어 | 설명 |
| :--- | :--- |
| 스토리(Story) | 고객이 직접 작성하는 사용자 요구사항 |
| 스토리 추정 | 개발자가 고객이 제시한 스토리가 어느 정도의 난이도 또는 기간인지를 결정하는 것 |
| 릴리즈(Release) | 고객에게 구현된 제품을 배포하는 것 |
| 반복(Iteration) | 하나의 릴리즈 안에 반복되는 작업 |
| 드라이버(Driver) | 짝 프로그래밍에서 키보드를 치면서 코드를 작성하는 사람 |
| 파트너(Partner) | 짝 프로그래밍에서 드라이버를 도와 코드의 구조 및 결함에 대한 조언을 하는 사람 |

(3) XP 실천사항
① 계획 게임(The Planning Game) : 일반적인 프로젝트에서는 프로젝트 초기에 고객의 요구사항을 바탕으로 전체 일정을 정의하는 것과 달리 프로젝트 시작 시 고객의 스토리를 바탕으로 몇 번의 릴리즈와 반복을 할 것인지 결정을 하고, 매 릴리즈와 반복의 시작 시 구현해야 하는 스토리를 고객과 개발팀이 함께 결정하는 것을 말한다.
② 짧은 릴리즈 주기(Smell Release) : 프로젝트 종료 후 전체 시스템을 고객에게 인도하는 것과는 달리, 프로젝트를 몇 번의 릴리즈와 반복으로 나누고, 각 반복의 종료마다 완성된 시스템을 고객에게 인도하고 고객의 피드백을 받음으로써 프로젝트가 의도된 방향에서 벗어나는 것을 방지하는 것이다.
③ 메타포(Metaphor) : 전체 시스템을 대상으로 사용할 수 있는 상징적인 내용을 찾음으로써 개발팀이 시스템에 대해 쉽게 이해하여 단순한 설계를 가능하도록 한다.
④ 단순설계(Simple Design) : 일반적인 개발에서 설계서의 작성 완료 후 구현하는 것과 달리 현재 구현하는 스토리에 필요한 부분만 설계하는 것을 의미한다.

스크럼(Scrum)
스크럼 개발 프로세스는 소프트웨어 개발보다는 팀의 개선과 프로젝트 관리를 위한 애자일 방법론으로, 경험적 관리 기법에 해당한다.
[처리해야 할 업무 검토] -> [항목 선정] -> [스프린트 계획] -> [스프린트] -> [스프린트 검토]
(제품 백로그, 스프린트 백로그, 잠재적으로 전달가능한 소프트웨어)

전산직 대비 컴퓨터일반

⑤ 테스트 우선 개발(Test-First Development) : 스토리를 명확히 이해하고 결함이 없는 코드를 작성하기 위하여 테스트케이스(테스트코드)를 구현 전에 작성하는 것이다. 일반적으로 테스트 우선 개발을 위해서 JUnit과 같은 테스트 프레임워크를 사용한다.
⑥ 리팩토링(Refactoring) : 이미 구현한 코드에 대해서 개선이 필요할 경우 개발 기간 중 언제라도 코드를 수정하고 개선하여 코드의 품질을 높이는 것이다.
⑦ 짝 프로그래밍(Pair Programming) : 드라이버 혹은 파트너 역할을 가진 2명의 개발자가 한 팀이 되어 코드를 구현하는 것을 말한다. 드라이버는 코드를 직접 작성하는 역할을 담당하며, 파트너는 드라이버의 실수 방지를 위해 조언 및 리뷰를 담당한다. 이를 통해 코드의 결합률을 낮추고 코드 구조를 명확히 한다.
⑧ 지속적인 통합(Continuous Integration) : 개발자가 구현한 단위시스템을 지속적으로 전체 시스템에 통합하는 것이다.
⑨ 주당 40시간 작업(40 Hour Week) : 개발자가 최적의 상태에서 개발할 수 있도록 야근 등의 추가 작업을 하지 않고 일과 시간에만 개발을 하는 것을 말한다.
⑩ 고객의 참여(On Site Customer) : 요구사항에 대한 원활한 소통을 위해 고객이 개발 팀에 상주하는 것이다.
⑪ 코딩표준(Coding Standard) : 효과적인 공동 작업을 위하여 개발 팀이 코딩할 때 지켜야 하는 띄어쓰기 규칙과 변수, 메소드 등의 명명 규칙을 정하는 것이다. 이를 통해 '코드 공동 소유'의 실천사항을 수행하는데 도움이 된다.
⑫ 전체 팀(Whole Team) : 원활한 의사소통을 위해 프로젝트에 참여하는 대부분의 사람들이 같은 공간에서 함께 개발하도록 하는 것을 의미한다.

보충학습
XP의 가치
① 단순성(Simplicity) : 요구사항 정의 및 명세, 상위 및 하위 설계 등과 같이 설계를 위한 많은 양의 문서를 작성하여야 하는 다른 개발방법론과는 달리, 시스템 구조에 대한 큰 그림에 대해 개발팀이 합의한 후 구현하여 설계의 단순함을 실현하는 가치이다.
② 의사소통(Communication) : 고객 및 동료 개발자와의 원활한 의사소통을 위해 고객이 상황 개발팀에 상주하여야 하며 문서보다는 구두에 의한 의사소통을 중요시하는 가치이다.
③ 피드백(Feedback) : 개발자가 수행하는 지속적인 단위테스트와 릴리즈를 위한 고객의 인수테스트 시 발견된 부적합 사항에 대해, 개발팀이 피드백을 받는 것을 의미한다.
④ 용기(Courage) : 위의 세 가지 가치들을 꾸준히 이행할 수 있도록 개발팀이 가져야 하는 마음가짐의 가치를 의미한다.
⑤ 존중(Respect) : 프로젝트에 참여하는 모든 사람이 프로젝트에 기여함을 인정하고 존중하는 것을 의미한다.

심화학습
통합 프로세스(Unified Process)
UP는 Jacobson, Booch, Rumbaugh에 의해 1999년에 개발된 객체지향 소프트웨어 개발 방법론이다.

1. UP의 특징
① UP는 반복적(Iterative)이고 점진적(Incremental)인 개발 방법이다.
② 유스케이스(Use Case)를 기반으로 한다.

01 프로젝트 관리의 개념

1. 프로젝트 관리의 개요
① 계획수립이란 누가, 언제, 무엇을, 어떻게 할 것인지를 사전에 결정해 볼 수 있는 작업이다.
② 프로젝트 계획은 관리자가 자원, 비용, 일정을 합리적으로 측정할 수 있는 체계를 제공하며, 합리적 측정을 위한 정보발견 과정을 통해 달성될 수 있다.
③ 프로젝트 계획서를 수립함으로써 경비절감과 경영 합리화를 꾀할 수 있다.

보충학습
효과적 프로젝트 관리 구조(3P)
① 사람(People) : 프로젝트 관리에 있어 가장 기본이 되는 인적요소
② 문제(Problem) : 처리해야 할 사항을 사용자 입장에서 분석하고, 기획하는 것
③ 프로세스(Process) : 소프트웨어 개발에 필요한 골격 제공

2. 문제 정의
① 계획의 수립 이전에는 시스템 정의 단계가 필요하며, 계획 수립 이후에 요구 분석을 한다.
② 소프트웨어 개발에 대한 목표가 시스템 정의서로 기술되어야 한다.

3. 프로젝트 개발 계획서
시스템 정의를 타당하게 실현할 수 있는 최적의 개발전략을 인적·기술적 자금투자 등으로 구체화시키는 작업으로, 프로젝트 계획서를 산출한다.

프로젝트(project)
특정 목적 달성을 위해 개발 계획을 수립하고, 프로그램의 분석 및 구현 등의 작업을 수행하는 것

PMBOK 지식영역
1. 프로젝트 통합 관리(project integration management) : 프로젝트의 여러 요소를 적절하게 통합하기 위한 프로세스들로 구성된다.
2. 프로젝트 범위 관리(project scope management) : 프로젝트를 성공적으로 완료하기 위해 필요한 모든 작업을 프로젝트에 포함시키기 위해 요구되는 프로세스들로 구성된다.
3. 프로젝트 일정 관리(project time management) : 프로젝트를 주어진 기간 내에 완료하기 위해 요구되는 프로세스들로 구성된다.
4. 프로젝트 원가 관리(project cost management) : 주어진 예산 범위 안에서 프로젝트를 완료하기 위해 요구되는 프로세스들로 구성된다.
5. 프로젝트 품질 관리(project quality management) : 사용자의 품질 요구를 만족시키기 위해 요구되는 프로세스들로 구성된다.
6. 프로젝트 자원 관리(project resource management) : 프로젝트 참여 인력을 어떻게 관리해야 프로젝트를 성공시킬 수 있는가에 관한 내용으로 참여 인력들이 능력을 최대한 발휘할 수 있게 지원하고, 팀워크를 통해 프로젝트를 잘 수행할 수 있게 팀 환경을 만들어주는 프로세스이다.
7. 프로젝트 의사소통 관리(project communication management) : 이해관계자 간의 메시지를 누구에게, 언제, 어떻게 보낸 것인가를 결정하고 관리하는 프로세스이다.
8. 프로젝트 위험 관리(project risk management) : 프로젝트의 위험을 식별, 분석, 대응하기 위해 요구되는 프로세스들로 구성된다.
9. 프로젝트 조달 관리(project procurement management) : 조직의 외부에서 물품과 서비스를 조달하기 위해 요구되는 프로세스들로 구성된다.
10. 프로젝트 이해관계자 관리(project stackholder management) : 잠재적 이해관계자들을 식별하고 이들의 식별정보, 관심사항, 상호 의존성, 태도 및 영향력, 프로젝트에 미치는 잠재적 영향, 주요 교류 관계 등을 분석한다.

02 프로젝트 계획 및 예측

개발 과정에서의 제품 비용 초과, 품질 저하 등에 영향을 미치므로 개발 공정과 제품생산에 대한 계획을 신중히 세워야 한다.

1. 노력 추정
(1) COCOMO(Constructive Cost Model)
① Boehm(1981)이 제안한 산정기법으로 원시 프로그램의 규모에 의한 비용예측 모형이다.
② 소프트웨어 개발비 견적에 가장 널리 이용되고 있는 방법이다.
③ 미리 준비된 식과 표를 이용하여 비용을 산정할 수 있는 알고리즘 방식(algorithmic) 기법이다.

보충학습
COCOMO의 프로젝트 모드(제품의 복잡도에 따른 프로젝트 개발 유형)
① 단순형(organic model)
5만 라인 이하로 소규모 팀이 수행할 수 있는 아주 작고 간단한 소프트웨어 프로젝트
② 중간형(semi-detached model)
30만 라인 이하의 프로젝트
단순형과 내장형의 중간형으로 트랜잭션 처리 시스템이나 운영체제, 데이터베이스 관리 시스템
③ 내장형(embedded model)
30만 라인 이상의 프로젝트
하드웨어가 포함된 실시간 시스템, 미사일 유도, 신호기 제어 시스템

④ 비용 요소의 통제가 가능하며 노력승수 조정도 가능하다.
⑤ 소프트웨어 라인 수 예측 자체가 힘들기 때문에 라인수를 입력으로 요구하는 것은 큰 약점으로 지적된다.

(2) 기능 점수(Function Point) 모델
① 소프트웨어의 각 기능에 대하여 가중치를 부여하여 요인별 가중치를 합산해서 소프트웨어의 규모나 복잡도, 난이도를 산출하는 모형이다.
② 소프트웨어 생산성 측정 위해 개발됐으며, 자료의 입력·출력, 알고리즘을 이용한 정보의 가공·저장을 중시한다.

원시코드 라인 수(Line of Code) 기법
LoC = LoC/PM * Person * Month
* LoC : 원시코드 라인 수
* LoC/PM : 개발자 한 명이 개발기간 동안 달성할 수 있는 라인 수

데이터 기능 측정

2. 일정 계획

보충학습
일정 계획 순서
① 시스템을 소작업들로 분해하여 WBS로 표현한다.
② 소작업들 간에 상호 의존관계를 분석하여 CPM 네트워크로 작성한다.
③ 최소 소요기간을 구하고 CPM 수정한다.
④ 각 작업의 일정을 Gantt Chart로 작성한다.

(1) WBS(Work Break-down Structure, 업무 분류 구조)
① WBS는 도표 내부에 있는 각 관리 단위의 성분을 밝힌다.
② WBS의 각 노드에 작업 소요일, 책임자, 작업시작 및 마감일을 표시하여 쉽게 확장할 수 있다.
③ WBS는 일정 계획 작업의 입력이 된다.

(2) CPM(critical path method)
① 경비(예산)와 개발일정 (기간) 최적화하려는 일정계획 방법으로, 임계경로(critical path) 방법에 의한 프로젝트 최단 완료시간을 구한다.
② 작업의 의존관계를 파악하여 각 작업이 최대로 빨리 끝날 수 있는 시간, 최대로 늦추어 시작할 수 있는 시간, 최대로 늦추어 끝날 수 있는 시간을 계산할 수 있다.

전체 프로젝트의 작업공정은 여러 가지 경로가 형성되는데, 이 경로들 중 소요기간이 가장 많이 소요되는 경로가 임계경로이다.

2. 구조적 분석 도구
(1) 자료 흐름도(Data Flow Diagram, DFD)
① 자료 흐름도는 가장 보편적으로 사용되는 시스템 모델링 도구로서 기능 중심의 시스템을 모델링하는 데 적합하다.
② 자료 흐름도는 프로세스(process), 흐름, 자료 저장소(data store), 자료출처(data source)와 도착지(data sink)의 네 가지 요소로 구성된다.

[프로세스]

[자료출처와 도착지]
자료 흐름도의 구성요소

(2) 자료 사전
① 자료 흐름도에 있는 자료 흐름이나 자료 저장소들의 의미를 서술한다.
② 자료 흐름이나 저장소가 어떤 요소들로 구성되는지를 서술한다.
③ 자료 흐름이나 저장소 내의 정보에 관련된 값이나 단위들을 서술한다.
④ 저장소 사이의 관련성을 서술함으로써 개체 관계와 연결한다.

2. 절차
① 액터 찾기 : 시스템을 개발한 후 이 시스템을 사용할 여러 타입의 사용자를 발견하는 작업

③ 사용사레 찾기 : 사용자와 개발자가 시나리오에 동의하면 시나리오로부터 일반적인 사용사례를 추출한다.
④ 사용사례 구체화 : 각 사용사례를 구체화하고 시스템의 동작을 오류와 예외 조건을 포함하여 기술해서 시스템의 명세를 완성한다.
⑤ 사용사례의 관계 찾기 : 사용사례 모형에서 중복되는 부분을 삭제하여 다듬는다.
⑥ 비기능적 요구 찾기 : 시스템의 성능, 문서화, 자원, 보안, 품질과 같이 시스템의 기능과 직접적으로 관련이 없는 요구사항을 찾는다.

[보충학습]
포함 관계
① 포함 관계(include)는 하나의 사용사례를 수행할 때, 다른 사용사례의 행동을 포함하는 관계를 말한다.
② 여러 사용사례에 중복적으로 나타나는 이벤트 흐름을 별도의 사용사례로 표현하여 이벤트의 중복을 방지한다.

[보충학습]
확장 관계
① 확장 관계(extend)는 특정한 조건에서 다른 사용사례 행동으로 확장되는 관계이다.
② 기본 사용사례는 단독으로 수행되다가 특정한 조건을 만족하게 되면 확장 사용사례로 확장되는데, 확장될 때의 조건을 확장점(extension point)이라 하고 기본 사용사례에 표시한다.
③ 확장 관계를 설정할 때의 화살표 방향은 기본 사용사례에서 확장 사용사례 방향이 아닌, 확장 사용사례에서 기본 사용사례 방향이다.

03 요구 분석의 명세화

1. 명세화의 원리
① 요구되는 기능의 명세화는 구현과 독립시켜야 한다.
② 절차지향적인 명세화 언어가 필요하다.
③ 소프트웨어 자체는 물론이고, 정보처리시스템의 전체 영역, 이용 환경을 전반적으로 명세화한다.
④ 각 요구명세는 개념적 모형이며 운용 가능해야 한다.

2. 좋은 요구 분석 명세서의 요건
① 일정한 양식을 갖추어야 한다. (Formality)
② 작성이 용이한 형태이어야 한다. (Constructibility)
③ 이해하기가 쉬워야 한다. (Comprehensibility)
④ 최소의 정보만을 포함해야 한다. (Minimality)
⑤ 설계와 구현에 적용 가능해야 한다. (Applicability)
⑥ 확장 가능해야 한다. (Extensibility)

[보충학습]
요구 분석 명세가 갖추어야 할 특성
① 무결성(correctness)과 완벽성(completeness) : 요구 분석서는 사용자의 요구를 오류 없이 완벽하게 반영하고 있어야 한다.
② 일관성(consistency) : 요구 분석서 안에 서로 모순되는 부분이 없어야 한다.
③ 명확성(unambiguous) : 요구 분석서의 내용은 모호한 점이 없고 간결하고 명쾌해야 한다.
④ 기능적(functional) : ‘어떻게’보다 ‘무엇을’에 관점을 두고 기술되어야 한다.
⑤ 검증 가능성(verifiable) : 사용자의 요구를 만족시키고 있는지 검증하고, 개발된 시스템이 요구 분석의 내용과 일치하는지를 검증할 수 있어야 한다.
⑥ 추적 가능성(traceable) 및 변경 용이성 : 요구 분석서의 내용은 체계적으로 정리되어 찾기 쉽도록 한다.

③ 계층적 조직이 제시되며, 모듈적이어야 한다.
④ 요구사항분석에서 얻은 정보를 이용하여 반복적 방법을 통해 이루어져야 한다.

02 디자인 패턴

1. 디자인 패턴 개요
① 디자인 패턴은 자주 사용하는 설계 형태를 정형화해서 이를 유형별로 설계 템플릿을 만들어둔 것을 말한다.
② 디자인 패턴을 사용하면 효율성과 재사용성을 높일 수 있다.
③ 디자인 패턴으로 만들려면 유사한 프로젝트를 수행하면서 적용한 설계 노하우를 분류하여 정리하고 이름을 붙여, 나중에 초보자도 쉽게 재사용할 수 있도록 사용지침 등도 포함하여 저장해 놓아야 한다.
④ 디자인 패턴은 알고리즘처럼 프로그램 코드로 변환하여 바로 사용할 수 있는 것은 아니지만 유사한 상황에서 구조적인 문제를 해결할 수 있는 방안을 제시해준다.
⑤ 디자인 패턴은 많은 개발자들이 경험으로 체득한 설계 지식을 검증하고 이를 추상화하여 일반화한 템플릿이라 하겠다.

2. 디자인 패턴의 장점
① 개발자(설계자) 간의 원활한 의사소통 : 설계자들은 여러 가지 디자인 패턴의 특성을 잘 알고 있어 문제 해결을 위해 서로 대화를 나눌 때 어떤 디자인 패턴을 사용하면 좋을지 충분한 해결책을 논의할 수 있다.
② 소프트웨어 구조 파악 용이 : 개발자들은 디자인 패턴의 특성을 잘 알고 있기 때문에 어떤 디자인 패턴이 설계할 때 사용되었는지 알면 소프트웨어 전체 구조를 쉽게 파악할 수 있다.
③ 재사용을 통한 개발 시간 단축 : 이미 만들어 놓은 디자인 패턴을 사용하므로 처음부터 만들어야 하는 수고를 덜기 때문에 그만큼의 개발 시간을 줄일 수 있다.
④ 설계 변경 요청에 대한 유연한 대처 : 사용자의 지속적인 기능 추가 요청, 환경 변화 등의 여러 가지 이유로 설계를 변경해야 할 때가 많다. 이때 디자인 패턴을 사용하여 설계했다면 설계 변경 요청에 대해 쉽고 빠르게 대처할 수 있다.

3. 디자인 패턴의 단점
① 객체지향 설계/구현 위주 : 디자인 패턴은 객체지향 설계/구현에 많이 사용된다. C언어를 주로 사용하는 구조적 설계/구현에서도 사용할 수 있지만 너무 복잡해서 큰 도움이 되지 않는다.
② 초기 투자비용 부담 : 디자인 패턴을 적용하여 설계하면 디자인 패턴을 사용하지 않는 경우보다 초기에 시간과 노력이 많이 든다.


PART 06

[심화학습] GoF 디자인 패턴

1. 생성 패턴
(1) 기능
① 객체를 생성하는 것과 관련된 패턴으로, 객체의 생성과 변경이 전체 시스템에 미치는 영향을 최소화하도록 만들어주어 유연성을 높일 수 있고 코드를 유지하기가 쉬운 편이다.
② 객체의 생성과 참조 과정을 추상화함으로써 시스템을 개발할 때 부담을 덜어준다.
(2) 종류
① factory method 패턴
• 상위 클래스에서 객체를 생성하는 인터페이스를 정의하고, 하위 클래스에서 인스턴스를 생성하도록 하는 방식이다.
• 객체를 생성하는 인터페이스와 실제 객체를 생성하는 클래스를 분리할 수 있다.
• 팩토리 메서드는 별도로 객체 생성 메서드를 두어 기본 클래스로부터 파생 클래스를 생성하도록 한다.
• 팩토리 객체는 특정 객체를 사용하고자 하는 일반 객체들에게 자기가 생성한 특정 객체를 반환하는 인터페이스를 갖는다.
• 사용하는 객체에 변경이 있거나 다른 객체로 대치가 되어도 일반 객체는 변경할 필요가 없고 객체를 반환하는 팩토리 객체만 변경하면 된다.
② singleton 패턴
• 특정 클래스의 객체가 오직 한 개만 존재하도록 보장한다.
• 클래스의 객체를 하나로 제한한다.
• 동일한 자원이나 데이터를 처리하는 객체가 불필요하게 여러 개 만들어질 필요가 없는 경우에 주로 사용한다.
③ prototype 패턴
• 일반적인 prototype(원형)을 만들어놓고, 그것을 복사한 후 필요한 부분만 수정하여 새롭게 객체를 생성하는 것보다 편리하게 사용할 수 있다.
• 인스턴스를 복제하여 사용하는 구조이므로 생성할 객체의 원형을 제공하는 프로토타입 인스턴스로부터 생성할 객체의 타입이 결정되도록 한다.
④ builder 패턴
• 복잡한 인스턴스를 조립하여 만드는 구조로, 복합 객체를 생성할 때 객체를 생성하는 방법(과정)과 객체를 구현(표현)하는 방법을 분리한다.
• 동일한 생성 절차에서 서로 다른 표현 결과를 만들 수 있다.
⑤ abstract factory 패턴
• 클래스 집합의 종류를 지정하여 관련된 객체의 집합을 생성할 수 있도록 한다.
• 사용자에게 인터페이스(API)를 제공하고, 인터페이스만 사용해서 부품을 조립하여 만든다.

2. 구조 패턴
(1) 기능
① 프로그램 내의 자료구조나 인터페이스 구조 등 프로그램의 구조를 설계하는 데 많이 활용될 수 있는 패턴이다.
② 클래스나 객체들의 구성(합성)을 통해서 더 큰 구조로 만들 수 있게 해준다.
③ 규모가 큰 시스템은 많은 클래스로 구성되어 복잡한 구조를 갖으며 이로 인해 수정으로 인한 오류도 많이 발생할 수 있다.
④ 이렇게 복잡한 형태의 구조를 갖는 시스템을 개발하기 쉽게 만들어주는 패턴이 바로 이 구조 패턴이다.
⑤ 구조 패턴을 이용하면 새로운 기능을 가진 복합 객체를 효과적으로 작성할 수 있다.
(2) 종류
① composite 패턴
• 사용자가 단일 객체와 복합 객체 모두 동일하게 다루도록 한 것이다.
• 집합 속에 포함될 객체와 집합을 가지고 있는 객체, 이들 모두가 자기 자신과 동일한 타입(메소드와 데이터)의 객체 리스트를 가질 수 있도록 도와준다.
• 컴포지트 패턴을 사용하면, 기본 클래스와 이를 포함하는 컨테이너 클래스를 구분하지 않고 처리하는 재귀적 합성을 할 수 있다.
② adapter 패턴
• 기존 클래스를 재사용할 수 있도록 중간에서 맞춰주는 역할을 한다.
• 즉 호환성이 없는 기존 클래스의 인터페이스를 변환해 재사용할 수 있도록 해준다.
• 이미 개발된 클래스, 즉 레거시 시스템의 인터페이스를 다른 클래스의 요구에 맞게 인터페이스를 변환해주는 것이다.
• 이미 만들어져 있는 클래스를 사용하고 싶지만 인터페이스가 원하는 방식과 일치하지 않을 때, 또는 관련성이 없거나 예측하지 못한 클래스들과 협동하는 재사용 가능한 클래스를 생성하고자 할 때 사용한다.
• 클래스 adapter 패턴은 상속을 이용한 것이고, 인스턴스 adapter 패턴은 위임을 이용한다.
③ bridge 패턴
• bridge 패턴은 기능의 클래스 계층과 구현의 클래스 계층을 연결하고, 구현부에서 추상 계층을 분리하여 각자 독립적으로 변형할 수 있게 해준다.
• 구현과 인터페이스(추상화된 부분)를 분리할 수 있고, 추상화된 부분과 실제 구현 부분을 독립적으로 확장할 수 있다.
④ decorator 패턴
• 기존에 구현되어 있는 클래스에 그때그때 필요한 기능을 추가해나가는 설계 패턴이다.
• 기능 확장이 필요할 때 상속의 대안으로 사용한다.
⑤ facade 패턴
• facade 패턴은 서브시스템의 내부가 복잡하여 클라이언트 코드가 사용하기 힘들 때 사용한다.

• 몇 개의 클라이언트 클래스와 서브시스템의 클라이언트 사이에 facade라는 객체를 세워놓음으로써 복잡한 관계를 정리(구조화)한 것이다.
• 모든 관계가 전면에 세워진 facade 객체를 통해서만 이루어질 수 있게 단순한 인터페이스를 제공(단순한 창구 역할)하는 것이다.
• facade 패턴을 이용하면 서브시스템 내부에서 작동하고 있는 많은 클래스들의 관계나 사용법을 의식하지 않고 facade에서 제공하는 단순화된 하나의 인터페이스만 사용하므로, 클래스 간의 의존 관계가 줄어들고 복잡성 또한 낮아지는 효과를 볼 수 있다.
⑥ flyweight 패턴
• flyweight 패턴은 메모리 사용량을 줄이기 위한 방법으로, 인스턴스를 필요한대로 다 만들어 쓰지 말고, 가능한 것은 공유해서 객체 생성을 줄자는 것이다.
⑦ proxy 패턴
• 일반적으로 프록시는 다른 무언가와 이어지는 인터페이스의 역할을 하는 클래스이다.
• 프록시는 자신이 대변하는 객체와 그 객체에 접근하고자 하는 클라이언트 사이에서 여러 방식으로 작업을 처리한다.
3. 행위 패턴
(1) 기능
① 반복적으로 사용되는 객체들의 상호작용을 패턴화한 것으로, 클래스나 객체들이 상호작용하는 방법과 책임을 분산하는 방법을 정의한다.
② 객체의 기능은 변하지 않지만 일을 처리하는 방식이 달라질 때가 있다. 응용 분야에 따라 행위가 다른 객체로 옮겨 가거나 알고리즘이 대체되는 경우이다. 이런 경우 대부분 상속 개념을 이용해 사용할 수 있다.
③ 행위 패턴은 여러 가지 행위 관련 패턴을 사용하여 독립적으로 일을 처리하고자 할 때 사용한다.
④ 행위 패턴은 메시지 교환과 관련된 것으로, 객체들 간의 행위나 알고리즘 등 관련된 패턴을 말한다.
(2) 종류
① iterator 패턴
• iterator 패턴은 반복이 필요한 자료구조를 모두 동일한 인터페이스를 통해 접근할 수 있도록 iterator 객체 속에 넣은 다음, iterator 객체의 메서드를 이용해 자료구조를 활용할 수 있도록 해준다.
• 반복에 사용되는 자료구조에는 배열, 리스트, Set, Map 등 있다.
• 이들의 특징은 어떤 데이터의 집합체라는 것이다. 이때 데이터들의 집합체를 모두 동일한 인터페이스를 사용하여 조작할 수 있게 하면 데이터들의 집합체를 쉽게 사용할 수 있을 것이다.
② observer 패턴
• 어떤 클래스에 변화가 일어났을 때, 이를 감지하여 다른 클래스에 통보해주는 것이 observer 패턴이다.
• observer 패턴은 어떤 일이 생기면 미리 등록한 객체들에게 상태 변화를 알려주는 역할을 한다.
• 1대 다의 객체 의존관계를 정의한 것으로 한 객체가 상태를 변화켰을 때, 의존관계에 있는 다른 객체들에게 자동으로 통지하고 변경시킨다.
③ strategy 패턴
• 이 패턴을 사용하면 클라이언트와 무관하게 독립적으로 알고리즘을 변경할 수 있고, 클라이언트는 독립적으로 원하는 방식을 사용할 수 있다.
• 클라이언트에게 알고리즘이 사용하는 데이터나 그 구조를 숨겨주는 역할을 한다.
• strategy 패턴은 알고리즘을 사용하는 곳과 알고리즘을 제공하는 곳을 분리시킨 구조로 알고리즘을 동적으로 교체할 수 있다.
④ template method 패턴
• 하나의 틀에서 만들어진 것들은 형태가 다 같다. 이런 틀 기능을 구현할 때는 template method 패턴을 이용할 수 있다.
• 이는 상속의 개념이 있는 상위 클래스와 하위 클래스의 구조에서 표현할 수 있다.
• 일반적으로 상위 클래스(추상 클래스)에는 추상 메서드를 통해 기능의 골격을 제공하고, 하위 클래스(구체 클래스)의 메서드에서는 세부 처리를 구체화한다.
• 상위 클래스에서는 추상적으로 표현하고 그 구체적인 내용은 하위 클래스에서 결정되는 디자인 패턴을 template method 패턴이라고 한다.
• 상속의 개념처럼 template method 패턴도 코드 양을 줄이고 유지보수를 용이하게 만드는 역할을 한다.
⑤ visitor 패턴
• visitor 패턴의 핵심 내용은 각 클래스의 데이터 구조로부터 처리 기능을 분리하여 별도의 visitor 클래스로 만들어놓고 해당 클래스의 메서드가 각 클래스를 돌아 다니며 특정 작업을 수행하도록 하는 것이다.
• visitor 패턴을 이용해 특정 클래스의 데이터 구조와 그 구조 내부를 돌아다니면서 수행하는 특정 작업(로직)을 분리할 수 있다.
• 객체의 구조는 변경하지 않으면서 기능만 따로 추가하거나 확장할 때 많이 사용한다.
⑥ chain of responsibility 패턴
• chain of responsibility는 책임들이 연결되어 있어 내가 책임을 못 질 것 같으면 다음 책임자에게 자동으로 넘어가는 구조를 말한다.
• 소프트웨어 개발에서도 이렇게 자동으로 연결되는 구조로 프로그램을 만들면 매우 유용한데 이 개념을 적용할 수 있는 것이 바로 chain of responsibility 패턴이다.
• 이 구조는 추상 클래스를 활용하여 설계한다.
⑦ command 패턴
• 함수 오버로딩(overloading)과 같은 추상화 개념을 사용한 것이다.
• command 패턴은 단순히 명령어를 추상 클래스(abstract class)와 구체 클래스로 분리하여 단순화한 것으로 끝나지 않고, 명령어에 따른 취소(undo) 기능까지도 포함한다(사용자 입장에서는 해당 명령어를 실행했다가 취소(undo)하기도 하기 때문이다).
• 프로그램의 명령어를 구현할 때는 command 패턴을 활용할 수 있다.


⑧ mediator 패턴
• 객체지향 설계에서는 많은 객체가 존재하고 이들이 서로 관계를 맺으며 상호작용한다.
• 이때 객체의 수가 너무 많아지면 서로 통신하느라 복잡해져 객체지향에서 가장 중요한 느슨한 결합의 특성을 해칠 수 있다.
• 이를 해결하는 한 가지 방법으로 중간에 이를 통제하고 지시할 수 있는 역할을 하는 중재자를 두는 것이다.
• 중재자에게 모든 것을 요구하여 통신의 빈도를 줄여 객체지향의 목표를 달성하게 해주는 것이 바로 mediator 패턴이다.
⑨ state 패턴
• state 패턴은 동일한 동작을 객체 상태에 따라 다르게 처리해야 할 때 사용한다.
• 임베디드 시스템을 포함한 많은 애플리케이션은 이벤트 구동 방식으로 시스템은 이벤트에 의존하여 동작한다. 이런 경우 상태 패턴을 이용하여 디자인한다.
• 상태 패턴을 사용하면 상태와 각 상태 전이를 보다 명시적으로 나타낸다.
• 특정 상태로 전이되는 것에 대해 각 상태 클래스마다 함수를 만들어주면 되므로 훨씬 유연하고 유지보수가 쉬운 구조를 만들 수 있다.
⑩ memento 패턴
• memento 패턴은 undo 기능을 개발할 때 쓸 수 있다.
• 클래스 설계 관점에서 객체의 정보를 저장할 필요가 있을 때 적용할 수 있다.
⑪ interpreter 패턴
• interpreter 패턴은 단어의 의미처럼 무언가를 번역하는 데 사용한다.
• 간단한 언어의 문법을 정의하고 해석하는데 사용한다.
• 주로 SQL 언어나 통신 프로토콜 같은 것을 개발할 때 문법 규칙을 클래스화한 구조를 갖는다.

03 설계의 원리

설계원리의 기능
① 소프트웨어를 구성요소로 나누는데 적용되는 기준
② 기능과 데이터 구조를 소프트웨어에 대한 개념적 표현으로부터 분리하는 방법

설계의 기본원리
(1) 추상화(Abstraction)
① 복잡한 문제를 이해하기 위해서 필요없는 세부 사항을 배제하는 것을 의미한다.
② 복잡한 구조(문제)를 해결하기 위하여 설계 대상의 상세내용은 배제하고 유사점을 요약해서 표현한다.
(2) 정보은닉(Information Hiding)
① 각 모듈이 다른 모듈에 구애 받지 않고 설계되는 것이다.
② 모듈내부의 절차적, 데이터의 내용 등 불필요한 정보를 외부에서 식별할 수 없도록 하며 외부와 인터페이스 정보만 제공하여 처리한다.
(3) 구조화(Structure)
① 문제의 영역들을 각각의 기능 모듈 단위로 세분화하여 모듈간의 관계를 구조적으로 설계하는 과정
② 하나의 설계 대상을 여러 개의 하부구조로 나누어서 계층구조로 설계
(4) 모듈화(Modularity)
① 모듈(module)은 서브루틴, 하부시스템, 소프트웨어 내의 프로그램 혹은 작업 단위를 의미
② 모듈의 개수가 증가하면 전체 개발비용이 감소하지만, 오히려 인터페이스에 대한 비용이 증가하므로 비용에서 최적이 될 수 있도록 모듈의 개수를 찾는 것이 중요하다.

[보충학습]
모듈의 기준
① 모듈간의 결합도는 최소화, 응집력은 최대화한다.
② 프로그램의 규모를 고려한다.
③ 1개의 입구와 1개의 출구를 갖는다.
④ 가급적 기계 종속성은 배제한다.
⑤ 시험 용이성을 향상시킬 수 있어야 한다.

모듈의 특성
① 모듈은 명령어, 처리논리, 데이터구조를 포함한다.
② 각 모듈은 독립적 컴파일 가능하다.
③ 모듈은 다른 프로그램 안에 포함 가능하다.
④ 모듈은 이름을 가지며, 이름과 매개변수 값을 이용하여 상호작용한다.
⑤ 모듈은 다른 모듈을 호출하여 이용할 수 있다.

PART 06

2. 설계평가와 모듈
(1) 결합도(Coupling)
결합도는 모듈들이 서로 관련되거나 연결된 정도를 나타낸다.
낮은 결합도를 유지해야 바람직하다.

① 자료 결합(data coupling) ── 결합도 약함
② 스탬프 결합(stamp coupling)
③ 제어 결합(control coupling)
④ 외부 결합(external coupling)
⑤ 공통 결합(common coupling)
⑥ 내용 결합(contents coupling) ── 결합도 강함

• ① 자료 결합도 : 모듈간의 결합도 중 가장 바람직한 결합도는 자료 결합도이다.
• ② 스탬프 결합도 : 한 그룹의 모듈들이 동일한 비광역 데이터 구조를 사용한다면 스탬프 결합도가 될 수 있다. 스탬프 결합도는 모듈간의 불필요한 연관 관계를 형성하므로 가능한 한 회피하는 것이 좋다.
• ③ 제어 결합도 : 어떤 모듈이 다른 모듈을 호출할 경우, 제어 정보를 파라미터로 넘겨주는 경우 이들 두 모듈은 제어 결합도를 가졌다고 한다.
• ④ 외부 결합도 : 일련의 모듈들이 동일한 광역 데이터 아이템(단일 필드 변수)을 사용하면 외부 결합도가 된다.
• ⑤ 공통 결합도 : 공통 결합도는 하나의 기억 장소에 공동의 자료 영역을 설정한 후, 한 모듈이 그 기억 장소에 자료를 전송하면 다른 모듈은 기억 장소를 조회함으로써 정보를 전달받는 방식을 취할 때 발생된다.
• ⑥ 내용 결합도 : 어떤 모듈을 호출하여 사용하고자 할 경우에 그 모듈의 내용을 미리 조사하여 알고 있지 않으면 사용할 수가 없는 경우에는 이들 모듈이 내용적으로 결합되어 있기 때문이며, 이를 내용 결합도라고 한다.

(2) 응집도(Cohesion)
한 모듈 내에 있는 처리 요소 사이의 기능적인 연관 정도를 나타내며, 응집도가 높아야 좋은 모듈이 된다.
한 모듈 내에 필요한 함수와 데이터들의 친화력을 측정하는데 사용된다.

① 기능적 응집(functional cohesion) ── 응집력 강함
② 순차적 응집(sequential cohesion)
③ 교환적 응집(communication cohesion)
④ 절차적 응집(procedural cohesion)

• ① 기능적 응집도 : 모듈내의 모든 요소가 한 가지 기능을 수행하기 위해 구성될 때, 이들 요소는 기능적 응집도로 결속되어 있다고 한다.
• ② 순차적 응집도 : 모듈 안의 하나의 소작업에 대한 결과가 다른 작업의 입력이 된다.
• ③ 교환적 응집도 : 동일한 입력과 출력을 사용하는 소작업들이 모인 모듈의 경우를 말한다.
• ④ 절차적 응집도 : 모듈 안의 작업들이 큰 테두리 안에서 같은 작업에 속하고 입출력을 공유하지지도 않지만 순서에 따라 수행될 필요가 있는 경우를 말한다.
• ⑤ 시간적 응집도 : 어느 특정한 시간에 처리되는 몇 개의 기능을 모아 한 모듈로 한 경우, 이들 기능은 시간적인 관계로 결속되는 경우가 된다. 예를 들어, 프로그램의 초기화 모듈이나 프로그램 종료 모듈이 이에 해당된다.
• ⑥ 논리적 응집도 : 논리적으로 서로 관련이 있는 요소를 모아 하나의 모듈로 한 경우, 그 모듈의 기능은 이 모듈을 참조할 때 어떤 파라미터를 주느냐에 따라 다르게 된다.
• ⑦ 우연적 응집도 : 우연적 응집도는 모듈 내부의 각 요소들이 서로 관계없는 것들이 모인 경우로 응집력이 가장 낮다.

01 객체지향의 개요

객체지향 기법은 재사용을 가능케 하고, 재사용은 빠른 속도의 소프트웨어 개발과 고품질의 프로그램의 생산을 가능하게 한다. 객체지향 소프트웨어는 그 구성이 분리되어 있기 때문에 유지 보수가 쉽다.

[보충학습]
객체지향의 개요
① 1966년 Simula 67 프로그래밍 언어를 개발하면서, 시스템의 한 구성원으로서 한 행위를 행할 수 있는 하나의 단위로 객체라는 개념을 사용했다.
② 객체지향 기법에서의 시스템 분석은 문제 영역에서 객체를 정의하고, 정의된 객체들 사이의 상호 작용을 분석하는 것이다.
③ 객체지향 기법은 복잡한 시스템의 설계를 단순하게 한다.
④ 소프트웨어 설계 개념의 추상화, 정보은닉, 그리고 모듈성에 기초한다.
⑤ 하나의 객체지향 프로그램은 여러 개의 객체들로 구성되며, 각 객체는 소수의 데이터와 이 데이터상에 수행되는 소수의 함수로 구성된다.

PART 06

02 객체지향의 기본 개념

1. 객체(Object)
① 현실세계에 존재할 수 있는 유형, 무형의 모든 대상을 말한다.
② 속성(attribute)과 메소드(method)로 정의된다.

2. 속성(attribute)
① 객체가 가지고 있는 특성으로, 현재 상태(객체의 상태)를 의미한다.
② 속성은 객체의 상태, 성질, 분류, 식별, 수량 등을 표현한다.

3. 클래스(class)
① 공통된 행위와 특성을 갖는 객체의 집합이다.
② 클래스는 동일한 타입의 객체들의 메소드와 변수들을 정의하는 템플릿(template)이다.
③ 클래스 내의 모든 객체들은 속성 값만 달라서 뿐, 동일한 속성과 행위를 갖게 된다.

[보충학습]
추상 클래스(abstract class)
① 서브 클래스들의 공통된 특성을 하나의 슈퍼 클래스로 추출하기 위한 목적으로 생성된 클래스로 재사용 부품을 이용하여 확장할 수 있는 개념이다.
② 일반 클래스와는 달리 객체를 생성할 수 없다.

4. 메시지(message)
① 한 객체가 다른 객체의 메소드를 부르는 과정으로, 외부에서 하나의 객체에 보내지는 메소드의 요구이다.
② 일반 프로그래밍 과정에서 함수 호출에 해당된다.

5. 메소드(method)
① 메소드는 객체가 어떻게 동작하는지를 규정하고 속성의 값을 변경시킨다.
② 메소드는 메시지에 의해 불리어질 수 있는 제어와 절차적 구성요소이다.

---

전산직 대비 컴퓨터일반

6. 다형성(polymorphism)
① 같은 메시지에 대해 각 클래스가 가지고 있는 고유한 방법으로 응답할 수 있는 능력을 의미한다.
② 두 개 이상의 클래스에서 똑같은 메시지에 대해 객체가 서로 다르게 반응하는 것이다.
③ 각 객체가 갖는 메소드의 이름은 중복될 수 있으며, 실제 메소드 호출은 덧붙여 넘겨지는 인자에 의해 구별된다.

7. 상속성(inheritance)
① 새로운 클래스를 정의할 때 기존의 클래스들의 속성을 상속받고 필요한 부분을 추가하는 방법이다.
② 하위 계층은 상위 계층의 특수화(specialization) 계층이 되며, 상위 계층은 하위 계층의 일반화(generalization) 계층이 된다.
③ 상속을 받은 하위 클래스는 상위 클래스의 속성과 메소드를 자기의 특성에 맞게 수정하거나 확장할 수 있다는 재정의(overriding)와 연관된다.

8. 캡슐화(encapsulation)
① 객체를 정의할 때 서로 관련성이 많은 데이터들과 이와 연관된 함수들을 정보처리에 필요한 기능을 하나로 묶는 것을 말한다.
② 서로 관련있는 데이터구조와 이들을 조작하는 동작들은 하나로 묶어서 하나의 명세나 프로그램 컴포넌트로 재사용을 용이하게 해준다.
③ 내부에 변수, 외부에는 메소드들이 변수들을 둘러싸서 보호하도록 결합시켜 부품화한 것이다.

9. 정보은닉(Information Hiding)
① 객체의 상세한 내용을 객체 외부에 철저히 숨기고 단순히 메시지마저로 객체와의 상호작용을 하게 한다.
② 외부에서 알아야 하는 부분만 공개하고 그렇지 않은 부분은 숨김으로써 대상을 단순화시키는 효과가 있다.
③ 정보은닉은 높은 독립성, 유지보수성, 향상된 이식성을 제공한다.

컴퓨팅 사고력의 구성요소(구글)
1. 분해: 해결할 문제를 작고 다룰 수 있는 부분으로 나눈다.
2. 패턴 인식: 데이터 안에 있는 패턴과 규칙(유사점과 차이점)을 찾는다.
3. 추상화: 패턴을 만드는 일반적인 규칙을 추출한다. 세부적인 것은 생략하고 가장 중심이 되는 것을 의미한다.
4. 알고리즘: 문제를 풀기 위한 절차를 구축한다.

클래스 설계 원칙
• 단일 책임 원칙 (SRP : Single-Responsibility Principle) : 클래스를 변경해야 하는 이유는 오직 하나여야 한다.
• 개방 폐쇄의 원칙 (OCP : Open-Closed Principle) : 확장(상속)에는 열려 있어야 하고 변경에는 닫혀 있어야 한다.
• 리스코프 교체의 원칙 (LSP : Liskov Substitution Principle) : 기반 클래스는 파생 클래스로 대체할 수 있어야 한다.
• 의존 관계 역전의 원칙 (DIP : Dependency Inversion Principle) : 클라이언트는 구체 클래스가 아닌 추상 클래스(인터페이스)에 의존해야 한다.
• 인터페이스 분리의 원칙 (ISP : Interface Segregation Principle) : 하나의 일반적인 인터페이스보다는 구체적인 여러 개의 인터페이스가 낫다.

UML(Unified Modeling Language)
1. UML의 개요
시스템의 여러 다양한 특성을 표현할 수 있는 방법이 있으며, 객체지향 설계의 표현 방법에 대한 표준으로 받아들여지고 있다.

[보충학습]
UML Diagram 분류
① 시스템의 정적인 측면 : Class Diagram
② 시스템의 동적인 측면 : Sequence Diagram, State Diagram
③ 시스템의 기능적 측면 : Use Case Diagram

2. UML Diagram
① Use Case(사용 사례) Diagram
㉠ 시스템이 어떤 기능을 수행하고, 주위에 어떤 것이 관련되어 있는지를 나타낸 모형이다.
㉡ 각 기능을 정의함으로써 시스템에 대한 전반적인 이해를 높이고, 문제 영역에 대해 개발자와 사용자 간에 의사소통을 원활하게 하는데 도움을 줄 수 있다.
㉢ 시스템의 기능을 나타내기 위해 사용자의 요구를 추출하고 분석하는 데 사용한다.

[보충학습]
Use Case(사용 사례) Diagram 특징
① 외부에서 보는 시스템의 동작에 초점을 두며 사용 사례(use case)와 액터(actor)로 구성된다.
② 액터는 시스템 범위 바깥쪽에 있고 사용 사례는 액터에게 보이는 시스템의 기능이다.

② Sequence Diagram
㉠ 순서 다이어그램은 객체간의 메시지 통신을 분석하기 위한 것이다. 이는 시스템의 동적인 모델을 아주 보기 쉽게 표현하고 있기 때문에 의사 소통에 매우 유용하다.
㉡ 시스템의 동작을 정형화하고 객체들의 메시지 교환을 시각화하여 나타낸다.
㉢ 객체 사이에 일어나는 상호 작용을 나타낸다.
③ Collaboration Diagram
㉠ Sequence 다이어그램이 객체간의 메시지 처리에 대한 순서에 중점을 둔 반면, Collaboration 다이어그램은 관련 객체와의 연관성 분석에 중점을 두고 있다.
㉡ Collaboration 다이어그램은 객체들 간의 정적인 상호연결 관계를 표현하고 있기 때문에 객체 간의 결합도나 메시지 처리를 관찰하기 쉽다는 것이 장점이다.
④ Class Diagram
㉠ Class 다이어그램은 객체지향 분석, 설계의 핵심이다.
㉡ Class 다이어그램은 객체, 클래스, 속성, 오퍼레이션 및 연관관계를 이용하여 시스템을 나타낸다.
㉢ Class 다이어그램을 통하여 사용자는 보다 쉽게 원하는 시스템의 구조를 정의할 수 있다.
⑤ Package Diagram
㉠ 분석된 결과를 시스템으로 구현하기 위하여 기존의 구조적 기법에서는 전체시스템을 프로그램 모듈로 나누는 기능 분할 기법을 사용한다.
㉡ 하나의 패키지는 여러 개의 서브패키지나 클래스를 가질 수 있다. 이들은 또한 나중에 하나의 모듈 혹은 컴포넌트가 된다.
⑥ State Diagram
㉠ State 다이어그램은 객체 내의 동적 행위를 모형화하기 위한 것으로, 복잡한 객체 혹은 객체 내부의 프로세스를 표현하고자 할 때 사용된다.
㉡ 어떤 객체의 동적인 행동을 표현하기 위해 사용되며, 여러 Use Case들 사이의 한 객체가 수행하는 기능을 나타낸다.
⑦ Activity Diagram
㉠ Activity 다이어그램은 State 다이어그램과는 달리 시스템의 흐름 전체를 파악하기 용이하도록 행위를 중심으로 흐름을 표현한 것이다.
㉡ 시스템을 액티비티로 표현한 것으로 오퍼레이션의 집합이 수행됨을 나타내는 상태이다.
⑧ Component Diagram
㉠ 시스템을 구성하는 실제 소프트웨어 컴포넌트 간의 구성 체계를 기술하므로 아키텍처 표현에 우수하다.
- 컴포넌트 다이어그램은 각 컴포넌트를 그리고 컴포넌트 간의 의존성 관계를 화살표로 나타낸다.

전산직 대비 컴퓨터일반

⑨ Deployment Diagram
㉠ Deployment 다이어그램은 지금까지 어떤 표준 없이 여러 개발자들이 사용하던 시스템 구조를 하나로 만든 것이라고 볼 수 있다.
㉡ 개발자들은 시스템 구조도를 통하여 서버와 클라이언트간의 통신방법이나 연결 상태, 각 프로세스를 실제 시스템에 배치하는 방법 등을 표현하게 된다.

UML 2.0 다이어그램 분류
• 구조 다이어그램 (Structural Diagram)
  - Class : 클래스, 특징, 관계 (UML 1)
  - Object : 객체 정보(인스턴스) ((Unofficially) UML 1)
  - Composite structure : 복합 구조의 클래스와 컴포넌트 내부 구조 (UML 2)
  - Deployment : 시스템의 물리 구조 (UML 1)
  - Component : 컴포넌트의 구조와 관계 (UML 1)
  - Package : 패키지 구성과 이들 사이의 관계 ((Unofficially) UML 1)

• 행위 다이어그램 (Behavioral Diagram)
  - Activity : 액티비티의 과정이나 연산 수행, 절차적/병렬적 행위 (UML 1)
  - Use case : 사용자 와 시스템 간의 상호 작용 방법 (UML 1)
  - State machine : 이벤트에 의한 객체의 상태들과 변화 표현 (UML 1)

• 상호작용 다이어그램 (Interaction Diagram)
  - Interaction overview : 액티비티와 시퀀스 다이어그램 혼합 (UML 2)
  - Sequence : 시간 흐름에 따른 객체들의 상호작용 (UML 1)
  - Communication : 객체 사이의 관계를 중심으로 상호 작용 표현 (UML 1 (Collaboration))
  - Timing : 객체 상태 변화와 시간 제약을 표현 (UML 2)

01 프로그래밍의 기본개념

1. 프로그래밍의 개요
설계사양을 컴퓨터의 명령코드를 이용하여 원시코드로 변환시키는 것이며, 이 작업을 코딩(coding)이라고 한다.

2. 구조적 프로그래밍
(1) 목적
① 프로그램을 읽기 쉽게 함
② 프로그램의 효율성 증진
③ 프로그램의 품질 향상

(2) 기본 개념
① 프로그램의 제어 흐름의 선형화
② 단일 출입구
③ 한정된 제어구조 사용 : 순차, 선택, 반복
④ 가급적 GOTO문 사용 배제

코드 스멜(code smell)
① 읽기 어려운 프로그램
② 중복된 로직을 가진 프로그램
③ 실행 중인 코드를 변경해야 하는 특별한 동작을 요구하는 프로그램
④ 복잡한 조건문이 포함된 프로그램

02 코딩 방법과 문서화

1. 코딩 방법
(1) 효율적인 코딩 스타일을 위한 지침(R. Fairley)
① 적은 수의 표준화된 제어구조만 사용
② 일관성 있는 GOTO 문의 사용
③ 기능 뒤에 자료를 은폐
④ 사용자 정의 데이터 타입 도입
⑤ 기계 종속적인 코드는 소수의 루틴으로 국한
⑥ 각 프로그램의 내부 문서와는 일정한 격식을 갖출 것
⑦ 5개 미만 25개 이상의 라인으로 된 루틴은 엄밀히 검토
⑧ 원시코드를 이해하기 쉽도록 구조를 효과적으로 구성

(2) 코딩 관점에서 I/O 효율성을 높이기 위한 지침
① 보조기억장치에 대한 I/O는 블록화되어야 한다.
② 단말기와 프린트에 대한 I/O는 질과 속도를 높일 수 있는 장치 특성을 알아야 한다.
③ 모든 I/O는 버퍼링되어야 한다.

2. 문서화
① 괄호를 사용하여 수식 표현의 모호성을 제거한다.
② 가중한 중첩은 가능한 한 사용하지 않는다.
③ 오류를 최소화하기 위해 프로그램을 방어적으로 작성한다.

리팩토링 목적
① 리팩토링은 소프트웨어의 디자인을 개선시킨다.
② 리팩토링은 소프트웨어를 이해하기 쉽게 만든다.
③ 버그를 찾는 데 도움을 준다.
④ 리팩토링은 프로그램을 빨리 작성할 수 있도록 도와준다.

CHAPTER 08 소프트웨어 시험과 디버깅

전산직 대비 컴퓨터일반

01 시험의 기본개념

1. 시험의 개념
(1) 개요
① 소프트웨어 시험이란 결합(fault)을 찾기 위해 소프트웨어를 작동시키는 일련의 행위와 절차를 말한다.
② 디버깅(Debugging)은 소프트웨어가 시험사레 통과시 발견된 결함을 제거시키는 작업을 말한다.

(2) 특징
① 시험은 오류의 유입을 최소화할 수 있으며, 테스트를 개발 초기 단계부터 계획하여 꾸준히 시행하는 것으로 본다면 단순히 오류를 발견하는 작업만은 아니다.
② 완벽한 시험은 불가하며, 시험에서 발견된 문제가 없다고 하여 프로그램에 오류가 없다고 할 수는 없다.

(3) 시험의 경제성
소프트웨어 개발 노력 분포도는 40(분석-설계) - 20(구현) - 40(시험)을 따른다.

시험목적에 의한 분류
① 기능 시험 : 주어진 입력에 대한 기대되는 출력제공 여부 시험
② 성능 시험 : 응답시간, 처리량, 메모리 활용도, 처리속도 등
③ 스트레스 시험 : 정보의 과부하시, 최저조건 미달~최고조건 초과시, 물리적 충격과 변화시 반응 정도
④ 복잡도 시험 : 소프트웨어에 내재되어 있는 논리경로의 복잡도를 평가하는 구조시험

시각에 의한 분류
① 확인(Verification) : 개발자의 시각에서 시스템이 명세서대로 만들어졌는지를 점검하는 것이다. 각 단계에서 입력으로 제공된 제품들과 표준에 기준하여 정확성과 일치성을 보장하기 것이다.
② 검증(Validation) : 사용자의 시각에서 고객의 요구사항이 올바르게 구현되었는지를 점검하는 것이다. 규정된 요구사항에 따르는지를 보장하기 위해 소프트웨어를 평가하는 과정이다.

2. 시험의 종류
(1) 시험 단계에 의한 분류
① 모듈 시험 : 독립적인 환경에서 하나의 모듈만을 테스트
② 통합 시험 : 시스템 모듈간의 상호 인터페이스에 관한 테스트. 즉, 모듈간의 데이터 이동이 원하는 대로 이루어지고 있는가를 확인하는 작업
③ 시스템 시험 : 시스템이 초기의 목적에 부합하는지에 대한 테스트

(2) 시험방법에 의한 분류
① 블랙박스 시험(Black Box Testing) : 소프트웨어 외부명세서를 기준으로 그 기능, 성능을 시험
② 화이트박스 시험(White Box Testing) : 소프트웨어 내부의 논리적 구조를 시험

PART 06

02 소프트웨어 시험 기법

1. 블랙박스 시험
① 프로그램의 논리(알고리즘)를 고려치 않고 프로그램의 기능이나 인터페이스에 관한 외부 명세로부터 직접 시험하여 데이터를 선정하는 방법
② 기능 시험, 데이터 위주(Data-Driven) 시험, 입출력 위주(IO-driven) 시험

[보충학습]
블랙박스 시험에서 찾고자 하는 오류
① 부정확하고 누락된 기능
② 인터페이스 오류
③ 자료구조나 외부 데이터베이스 접근에 있는 오류
④ 성능 오류
⑤ 초기화와 종료 오류

(1) 동등 분할(Equivalence Partitioning, 균등 분할)
프로그램의 입력조건을 중심으로 입력조건에 타당한 값과 그렇지 못한 값을 설정하여 각 동등 클래스 내의 임의의 값을 시험사례로 선정한다.

(2) 경계값 분석
입력조건의 중간값보다는 경계값에서 오류가 발생될 확률이 높다는 점을 이용해서 입력조건의 경계값에서 테스트 사례를 선정한다.

(3) 원인-결과 그래프 기법
① 입력데이터 간의 관계가 출력에 미치는 상황을 체계적으로 분석하여 효용성 높은 시험 사례를 추출하여 시험하는 기법이다.
② 프로그램의 외부 명세에 의한 입력조건(원인)과 그 입력으로 발생되는 출력(결과)을 논리적으로 연결시킨 그래프로 표현하여 시험사례를 유도해 낸다.

(4) 비교검사(Comparison Testing) 기법
① 블랙박스 시험 기법의 기초로 Back-to-Back 시험이라고 한다.
② 소프트웨어의 신뢰성이 절대적으로 중요한 경우, 똑같은 기능의 소프트웨어를 개발하여 비교한다.
③ 시험은 일관성을 보장하기 위해 두 시스템의 결과를 동시에 실시간 비교하면서 진행한다.

| 동등 분할 (equivalence partitioning) | 테스트 대상의 입출력 값을 특정 클래스로 분할한 후 각각의 클래스로부터 대푯값을 추출하여 테스트 케이스를 생성하고 테스트 데이터의 범주를 식별하는 기법 |
| 경계값 분석 (boundary value analysis) | 동등 분할 기법을 확장시킨 것으로 분할된 클래스의 경계에 대한 값들까지 검사하는 기법 |
| 페어와이즈 조합 (pairwise combination) | 입력값 조합의 경우의 수를 줄이기 위해 두 입력값의 조합을 통해 테스트 케이스를 도출하는 기법으로, 모든 경우의 수를 테스트하지 않고 2개 요소의 모든 조합을 확인할 수 있도록 테스트 케이스를 생성 |
| 상태 전이 (finite state machine based testing) | 상태 전이도를 기반으로 상태 전이 테이블을 도출하고 각각의 전이 시나리오로부터 테스트 케이스를 도출하는 기법 |
| 인과 그래프 (cause-effect diagram) | 입력 데이터 간 관계가 출력에 영향을 미치는 상황을 체계적으로 분석하여 테스트 케이스를 도출하는 기법 |
| 결정 테이블 (decision table) | 의사 결정의 여러 조합을 정하는 행위나 결과를 식별함으로써 시스템의 예상되는 행위를 파악하여 테스트 케이스를 도출하는 기법 |

2. 화이트박스 시험
① 프로그램 내의 모든 논리적 구조를 파악하거나, 경로들의 복잡도를 계산하여 시험사례를 만든다.
② 프로그램 내의 허용되는 모든 논리적 경로(기본 경로)를 파악하거나, 경로들의 복잡도를 계산하여 시험사례를 만든다.
③ 기본 경로를 조사하기 위해 유도된 시험사레들은 시험 시에 프로그램의 모든 문장을 적어도 한 번씩 실행하는 것을 보장받는다.

(1) 기초 경로 시험(구조 시험, 복잡도 시험)
① 가장 대표적인 화이트박스 기법으로 McCabe에 의해 제안되었으며, 시험영역을 현실적으로 최대화시켜 준다.
② 상세설계 및 원시코드를 기초로 논리흐름도를 작성하며, 프로그램을 논리적 복잡도를 측정한다.
③ 시험사례 설계자가 절차적 설계의 논리적 복잡도를 측정하여 이 측정을 실행 경로의 기초를 정의하는 데 사용할 수 있게 한다.

순환 복잡도 : CC(Cyclomatic Complexity)
매케이브가 정의한 메트릭으로 원 코드의 복잡도를 정량으로 평가하는 방법이다.
원시 코드가 얼마나 복잡한지를 알아보기 위한 것으로, 얼마나 많은 논리적인 경로를 가지고 있는지 계산한 값이다.
순환 복잡도는 다음과 같이 다양한 공식으로 계산할 수 있다.

<순환 복잡도 공식>
• 순환 복잡도 = 폐쇄 영역의 수
• 순환 복잡도 = 간선 수 - 노드 수 + 2
• 순환 복잡도 = 분기 노드 수 + 1

03 소프트웨어 검사 전략

1. 모듈 시험(단위 시험, Unit Test)
① 단위 테스트에는 정형화되지 않은 기술이 많이 사용된다.
② 코딩이 끝난 후 설계의 최소 단위인 모듈에 초점을 두고 검사하는 단계이다.
③ 주로 화이트박스 검사 기법을 적용한다.
④ 단위 검사는 코딩 단계와 병행해서 수행되며, 모듈은 독자적으로 운용되는 프로그램이 아닌 시스템의 일부이기 때문에 모듈을 가동하는 가동기(Driver)와 타 모듈들을 흉내내는 가짜 모듈(Stub)들이 필요하다.

2. 통합 시험(Integration Test)
① 단위 검사가 끝난 모듈들을 하나로 결합하여 시스템으로 완성하는 과정에서의 검사이다.
② 모듈 간의 인터페이스와 연관된 오류를 밝히기 위한 검사와 함께 프로그램 구조를 구축하는 체계적인 기법이다.
③ 시스템을 구성하는 모듈 사이의 인터페이스와 결합을 테스트하며, 시스템 전체의 기능과 성능을 테스트한다.
④ 통합 시험은 시스템을 구성하는 여러 모듈을 어떤 순서로 결합하여 테스트할 것이냐에 따라 동시식(Big-Bang), 하향식(Top-down), 상향식(Bottom-up), 연쇄식(Threads) 등이 있다.

3. 시스템 시험(System Test)
모든 모듈들은 하나의 시스템으로 작동하게 된다.

4. 인수 시험(Validation Testing, 확인 시험)
(1) 개요
① 사용자측 관점에서 소프트웨어가 요구를 충족시키는가를 평가
② 하나의 소프트웨어 단위로 통합된 후 요구사항 명세서를 토대로 진행한다. 명세서에는 유효성 기준(Validation Criteria)절을 포함하고 있다.
③ 개발 집단이 사용자 집단을 대신하여 검토회(Review, Inspection, Walkthrough) 등 일정한 방법을 사용하면서 품질보증에 임하는 것

표준 프로세스
1. 프로세스 능력 평가 모델
(1) SW-CMM(SW-Capability Maturity Model)
① 프로젝트 개발 조직에서 프로세스 성숙도가 높은 조직이 성숙도가 낮은 조직보다 높은 품질의 소프트웨어를 생산할 수 있다는 모델이다.
② CMM은 소프트웨어 공급자의 강점과 약점을 평가하는 수단으로, 개발자가 프로세스의 능력을 스스로 평가하고 평가 결과에 따른 개선 방향을 설정하는 데도 사용되었다. 이후 여러 모델이 추가 개발되고, 소프트웨어 사용 환경의 변화, 기존 모델 등과의 중복 문제 등을 해결하기 위하여 새로운 모델의 필요성이 대두되었다.
(2) CMMI(Capability Maturity Model Integration)
프로세스 표준화의 기준과 방향을 제시하므로 조직 프로세스에 대한 측정뿐 아니라 평가 지표로도 활용할 수 있는데, 이때 능력을 평가하거나 성숙도를 평가할 수 있다.
① C(능력)(Capability)
• 소프트웨어 개발에서 능력이란 개발 목표(주어진 기간, 정해진 비용, 고품질 등)를 달성할 수 있는 힘이다.
• 능력이 있는 조직은 개발 목표를 달성할 수 있다. 그러나 능력이 없는 조직은 개발 기간이 연장되거나 비용이 더 추가된다거나 품질이 떨어지는 소프트웨어를 개발함으로써 개발 목표를 달성하지 못한다.
② M(성숙도)(Maturity)
• 소프트웨어 개발에서 성숙도가 높은 조직이란 책임감이 있는 조직으로서 사용자가 만족하는 고품질의 소프트웨어를 개발하기 위해 개발 과정에서 객관적이고 정량적인 근거에 따라 프로세스가 측정되고 지속적인 개선이 이루어지는 것을 말한다.
• 성숙하지 못한 조직은 책임감이 떨어지는 서투른 조직으로, 개발 프로세스가 객관적인 근거에 의해 진행되지 않기 때문에 사용자이 만족하는 고품질의 소프트웨어가 만들어질 수 없다.
③ M(모델)(Model)
• 프로세스를 감사(audit)하는 의미로 사용한다.
• 기준대로 하고 있는지, 그렇지 않은지를 검사하는 것이다.
• CMMI는 그 기준을 제시하고 있는데 그것이 ‘수행 지침(best practice)’이라는 모델이다.
• 조직이 프로세스 개선을 원한다면, CMMI는 그 조직이 무엇을 해야 하는지에 대해 ‘수행 지침’을 통해서 알려준다. 그러나 구체적으로 어떻게 할지는 조직의 역량에 맡겨둔다.
④ I(통합)(Integration)
• 여러 가지 프로세스의 기준을 하나로 통합했다는 의미이다.
• 소프트웨어 개발 생명주기의 각 단계, 즉 계획부터 유지보수까지 모든 과정을 통합한 모델이라는 의미가 있다.

프로세스 품질 평가 모델
• 품질 시스템 보증을 위한 ISO 9000 모델
• 소프트웨어 생명주기 프로세스 표준을 위한 ISO 12207 모델
• 소프트웨어 프로세스 능력 평가를 위한 CMM와 SPICE(ISO 15504) 모델

ISO/IEC 12207
• 기본 생명주기 프로세스
• 지원 생명주기 프로세스
• 조직 생명주기 프로세스

| 5 | 최적화(optimizing) 단계 : 프로세스를 지속적으로 개선 | • 프로세스 수행을 최적화함<br>• 지속적 개선을 통해 업무 목적을 만족시킴 |


CHAPTER 09 소프트웨어 유지보수와 형상관리

01 소프트웨어의 유지보수

1. 유지보수의 개념
(1) 개요
① 소프트웨어가 제품으로 개발된 후 사용자가 사용하기 시작하면서 폐기될 때까지 오류를 수정하거나 새로운 기능을 추가하기 위해 소프트웨어를 변경하는 프로세스를 의미한다.
② 소프트웨어의 수명을 연장하기 위한 활동이다.
③ 현재 소프트웨어의 유지보수에 대한 노력은 개발 조직이 소모하는 모든 노력 중 80% 이상을 차지한다.

(2) 유지보수에 따른 문제점
① 이미 만들어져 있는 소프트웨어를 통해 개발 과정을 추적하는 것은 거의 불가능하다.
② 다른 사람이 작성한 프로그램을 이해하기는 매우 어렵다.
③ 문서가 존재하지 않거나 부적하다.
④ 변경을 염두에 두지 않고 설계된 소프트웨어가 많다.
⑤ 유지보수 업무를 기피하는 경향이 있다.

2. 유지보수 작업 과정
(1) 소프트웨어 이해
① 프로그램을 이해하지 못하고 프로그램에 변경을 가한다면 또 다른 오류를 발생하게 할 수도 있다. 문서화가 제대로 되었는가, 소프트웨어 형상 관리가 제대로 되는가에 따라 대규모 프로그램의 이해과정이 달라진다.
② 소프트웨어 형상관리수가 잘 이루어져 프로그램의 동작이 문서에 정확히 반영되어 있다면 우선 분석이나 설계 등의 개발문서나 사용자 매뉴얼 등을 읽어 소프트웨어 전체의 윤곽을 파악한다.

(2) 변경 요구 분석
변경이 불가피한 이유와 요구를 잘 분석하여 이해하여야 한다.

(3) 변경 및 효과 예측
변경이 일어나기 전에 변경으로 인한 이상 효과를 점검할 필요가 있다.

(4) 리그레션 테스트(regression test)
① 변경에 의하여 영향받은 부분만 다시 테스트하는 것을 의미한다.
② 소프트웨어를 변경한 후에도 여전히 같은 기능을 하고 있음을 확인하기 위한 테스트이다.

3. 유지보수 종류
(1) 수정 유지보수(correction)
① 개발된 소프트웨어를 사용자가 인도받은 후 사용하면서 발견되는 오류를 잡는 것이다.
② 테스트의 특성상 충분히 테스트를 해도 발견되지 않는 오류가 있을 수 있다.
③ 수정 유지보수는 개발 과정에서 미처 바로잡지 못한 오류를 유지보수 단계에서 해결하는 것을 말한다.

(2) 적응 유지보수(adaption)
① 개발된 소프트웨어가 처음 설치된 곳에서 문제없이 실행되다가 환경이 바뀌어도 이에 맞도록 수정·보완하는 것이다.
② 환경 변화 요인에는 운영체제, 주변 장치, 네트워크 환경 등 다양한 것이 있을 수 있다.

(3) 기능 보강(완전) 유지보수(enhancement)
① 기존에 없던 새로운 기능을 요구할 수도 있고, 기존 기능을 더 편리하게 바꾸기를 원하기도 하며, 성능 개선을 요구하기도 한다.
② 기능 보강 유지보수는 이런 여러 이유로 인한 변경이 필요할 때 하게 되는 유지보수라 할 수 있다.

(4) 예방 유지보수(prevention)
어떤 문제가 발생했을 때 처리하는 것이 아니라 미리 예상되거나 예측되는 오류를 찾아 수정하는 것이다.

② 설계서
③ 프로그램(원시코드, 목적코드, 명령어 파일, 자료 파일, 테스트 파일)
④ 사용자 지침서

(2) 형상관리(SCM, Software Configuration Management)
① 소프트웨어에 대한 변경을 철저히 관리하기 위해 개발된 일련의 활동
② 소프트웨어를 이루는 부품의 Baseline(변경통제 시점)을 정하고 변경을 철저히 통제하는 것

2. 형상관리의 기능
(1) 형상 식별(Identification)
① 형상 식별은 소프트웨어 형상의 모든 항목에 대해 의미 있고 항구적인 명명을 보증하는 소프트웨어 형상관리 활동이다.
② 형상관리 항목(SCI, Software Configuration Item)에 대해 관리 목록 번호를 부여하고 나무 구조를 표현하여 이에 대한 관련 문서에 대한 추적을 용이하게 한다.
③ 버전 관리(Version Control)
 소프트웨어 프로세스 동안에 만들어진 여러 버전의 형상 객체들을 관리하기 위한 절차(Procedures)와 도구(Tools)의 결합으로 형상관리자는 사용자가 적절한 버전을 선택하여 소프트웨어 시스템의 대안 형상을 명세하게 도와준다.

(2) 형상 통제(Control)
 식별된 SCI의 변경요구를 검토하고 승인하여 현재의 베이스라인에 적절히 반영될 수 있도록 통제하기 위한 형상관리 활동이다.

(3) 형상 감사(Auditing)
 변경이 적절하게 시행되었는지 객관적인 검증과 확인(V&V) 과정을 거쳐 새로운 형상의 무결성을 확보하기 위한 활동이다.

(4) 형상 보고(Status Accounting)
 형상 식별, 변경 통제, 형상 감사 기능의 수행 결과를 기록하고 데이터베이스에 의해 관리하며 이에 대한 보고서를 작성하는 활동이다.

형상관리를 위한 조직
(형상관리 위원회(팀))
① 분석가 : 사용자들과 상의하여 무엇이 문제이며 어떤 기능향상 및 개작이 필요한가를 결정한다.
② 프로그래머 : 분석가와 협동하여 문제의 원인을 찾아내고 변경의 형태와 내용을 알아낸다. 실제 프로그램의 수정을 담당한다.
③ 프로그램 사서 : 문서와 코드에 대한 변경을 계속 보관하고 관리한다.

02 신뢰도

1. 신뢰도(Reliability)
① 믿고 사용할 수 있는 정도
② 주어진 시간 동안 주어진 환경에서 소프트웨어가 고장나지 않고 사용될 수 있는 확률

2. 고장(Failure)
① 개발자가 오류를 범했을 때 소프트웨어상의 문제점인 결함으로 생길 수 있는 현상
② 소프트웨어가 수행되면서 사용자가 요구치 않았거나 정당치 못하다고 판단하는 상황이 발생하는 것

3. 신뢰도 측정
① MTBF(Mean Time Between Failure) : 고장과 또 하나의 고장 사이의 평균 시간
② MTTF(Mean Time To Failure) : 주어진 시각에서 고장이 발생할 때까지의 평균 시간
③ MTTR(Mean Time To Repair) : 고장이 발생한 시점에서 결함을 제거 즉, 수리시까지의 평균 시간
   MTBF = MTTF + MTTR
④ 이용도(가용도) : 소프트웨어 가용성은 프로그램에서 시간이 주어진 시점의 요구사항들에 따라 운영되는 확률을 말한다.
   이용도 = MTTF / (MTTF + MTTR) × 100 (%)

02 소프트웨어 재공학

1. 소프트웨어 재공학
(1) 소프트웨어 재공학의 개요
① 소프트웨어 위기의 해결책을 개발의 생산성이 아닌 유지보수의 생산성 재고에서 찾는 새로운 시각이다.
② 기존 소프트웨어의 취약한 부분들을 단계적으로 미화시켜 작업 수행마다 질적 향상을 꾀하는데 있다.

(2) 소프트웨어 재공학의 목적
① 소프트웨어의 유지보수성을 향상시킨다.
② 소프트웨어에서 사용하고 있는 기술을 상향 조정한다.
③ 소프트웨어의 수명을 연장시킨다.

2. 소프트웨어 역공학(Reverse Engineering)
① 소프트웨어 역공학은 소스코드보다 상위 수준의 추상화에서 프로그램 표현을 위해 프로그램을 분석하는 프로세스이다. 즉, 역공학은 설계 복구의 한 프로세스로 기존 프로그램으로부터 데이터, 구조 및 절차적 설계 정보를 추출해낸다.
② 역공학의 핵심은 "추상 추출(Extract Abstractions) 활동"으로서 문서화가 안 된 구프로그램을 평가하며, 소스코드로부터 수행처리의 명세, 사용자 인터페이스, 프로그램 자료구조와 데이터베이스를 추출한다.

역공학의 2가지 개념
① 코드 역공학 : 코드로부터 흐름도, 자료구조도, 자료흐름도를 재생시키는 것
② 데이터 역공학 : 데이터로부터 자료 사전, ERD 등을 재생시키는 것

3. CBD(Component Based Development)
① 소프트웨어 컴포넌트를 조립해 새로운 애플리케이션을 만들 수가 있어 개발기간을 단축할 수 있으며 기존의 컴포넌트를 재사용할 수 있어 생산성과 경제성을 높일 수 있다.
② 컴포넌트를 만드는 데 소요되는 시간은 CBD 케이스 툴의 자동화 기능(마법사 등)을 사용하면 컴포넌트를 만드는 개발기간을 단축시킬 수 있다.
③ 컴포넌트는 독립적인 개발과 배포가 가능해 사용자는, 품질 좋은 컴포넌트를 선택하여 사용할 수 있다. 컴포넌트의 사용은 인터페이스를 통해 이루어지고 실제 구현 과정은 사용자가 알 필요가 없다.

컴포넌트의 특징
① 컴포넌트는 또 다른 컴포넌트를 만들거나 애플리케이션을 만들기 위한 소프트웨어 빌딩 블록이며 독립적으로 개발과 배포가 가능한 소프트웨어 패키지이다.
② 컴포넌트는 캡슐화 되어 스펙만을 참조하도록 되어 있으며, 그 내부 알고리즘은 감추어져 있다. 따라서 전체 소프트웨어에 영향을 주지 않고 컴포넌트의 구현을 변경할 수 있다.

03 CASE(Computer-Aided Software Engineering)

1. CASE
① 소프트웨어 공학의 자동화를 의미하며, 소프트웨어 공학작업 중 하나의 작업을 자동화한 소프트웨어 패키지를 CASE 도구라 한다. 이러한 도구를 한데 모아놓은 것을 소프트웨어 공학환경(Software Engineering Environment)이라 한다.
② 소프트웨어 공학 자동화로 개발비용 절감 및 생산성을 향상시킬 수 있다.

2. CASE의 장점
① 소프트웨어 개발의 모든 단계에 걸쳐 표준화를 지원한다.
② 방법론을 지원하는 도구들의 사용으로 개발 기법을 실용화한다.
③ 자동화된 검사를 통하여 소프트웨어 품질을 향상시킨다.
④ 프로그램의 유지보수를 간편하게 한다.
⑤ 개발기간 단축 및 비용을 절감시킨다.
⑥ 문서화의 용이성을 제공한다.
⑦ 소프트웨어 모듈의 재사용성을 증대시킨다.

01 프로그래밍 언어

1. 프로그래밍 언어
① 컴퓨터 시스템을 동작시키는 프로그램을 작성하기 위한 언어이다.
② 프로그래밍 언어는 사람이 사용하기 편리한 정도에 따라 저급 언어(low level language)와 고급 언어(high level language)로 분류된다.

(1) 저급 언어(low level language)
① 저급 언어는 초기에 사용되던 하드웨어 지향의 기계 중심 언어로, 하드웨어와 밀접한 기능을 제어하는 프로그램을 작성하는데 주로 사용된다.
② 저급 언어에는 기계어와 어셈블리어가 있다.
③ 컴퓨터 기종에 따라 다르게 표현되고 복잡한 단점이 있다.

(2) 고급 언어(high level language)
① 고급 언어는 사람이 사용하는 기호 체계와 매우 흡사하며 기종에 관계없이 거의 동일하게 표현된다.
② 고급 언어에는 C, C++, Java 등의 대부분의 언어가 해당된다.

2. 프로그램 처리 기법
(1) 컴파일 기법
① 고급 언어로 작성된 프로그램을 컴퓨터가 바로 실행할 수 있는 프로그램으로 변환하는 방식이다.
② 컴파일러(compiler)를 이용한다.
③ 번역이 완료되면 빠르게 프로그램을 실행할 수 있다.
④ 컴파일러의 입력은 원시 프로그램(source program)이고, 컴파일의 결과로 생성되는 기계어 프로그램을 목적 프로그램(object program)이라 한다.

[원시 프로그램] -> [어휘 분석 단계] -> [구문 분석 단계] -> [중간 코드 생성 단계] -> [최적화 단계] -> [코드 생성 단계] -> [목적 프로그램]

(2) 컴파일 단계
1) 어휘 분석 단계
① 원시 프로그램을 토큰(token)으로 자르고, 토큰과 관련 정보를 구문 분석 단계로 전달한다.
토큰은 하나의 기호를 표시하기 위해 논리적으로 응집된 문자열이다.
② 토큰의 예로는 명칭, 예약어, 리터럴, 연산자, 구문기호 등이다.
2) 구문 분석 단계
어휘 분석 단계에서 전달받은 토큰들이 문법적으로 옳은지 검사하고, 오류가 없으면 파스 트리 구조를 생성한다.
3) 중간 코드 생성 단계
① 기계어는 아니지만 어느 기계에도 의존적이지 않으면서 기계어에 가까운 중간 코드로 구성된 프로그램을 생성한다.
② 문법적인 오류가 아닌 의미적인 오류를 검사한다.

456



4) 최적화 단계
중간 코드에서 불필요한 코드를 제거하거나 더 효율적인 코드로 개선하여 중간 코드의 크기를 줄이고 실행 속도를 빠르게 한다.

5) 코드 생성 단계
최적화된 중간 코드로부텨 해당 컴퓨터가 인식할 수 있는 목적 프로그램을 생성한다.

(3) 해석 기법
① 고급 언어로 작성된 프로그램을 바로 실행한다.
② 인터프리터(interpreter)를 사용한다.
③ 1960년대 SNOBOL, LISP, Scheme 등이 해석 기법으로 구현되었으나 한동안 사용되지 않다 최근 들어 자바스크립트와 같은 웹 스크립트 언어가 해석 기법으로 구현되고 있다.

(4) 하이브리드 기법
① 컴파일 기법과 해석 기법을 혼합한 형태이다.
② 고급 언어로 작성된 프로그램을 해석이 쉽게 되도록 하기 위해 중간 코드 형태로 번역하고 그것을 해석하여 실행한다.
③ 중간 코드 생성 단계까지는 컴파일 기법으로 동작하고 중간 코드를 실행하는 과정은 해석 기법으로 동작한다.
④ Java는 대표적인 하이브리드 기법을 사용한다.
바이트 코드라 불리는 중간 코드로 번역하고 운영체제마다 별도로 존재하는 자바 가상 기계가 바이트 코드를 실행한다.

심층학습
프로그래밍 패러다임
일반적으로 패러다임은 관련있는 행위의 수집을 안내해주는 사고의 패턴이다. 프로그래밍 패러다임은 특정 장르의 프로그램과 언어에 포함되어 있는 문제 해결을 위한 사고의 패턴이다.

1. 명령형 프로그래밍
① 고전적인 폰노이만의 계산 모델에 기초한 가장 오래된 패러다임이다.
② 명령형 언어는 명령의 순차적인 실행, 메모리 위치를 의미하는 변수의 사용, 변수의 값을 바꾸는 배정문의 사용을 특징으로 갖는다.
③ 저장문, 루프, 문장나열, 조건문장, 예외 처리를 포함한다.
④ Cobol, Fortran, C, Ada, Perl 등이 대표적인 명령형 언어이다.

2. 객체지향형 프로그래밍
① 객체지향형 프로그래밍에서 프로그램은 상태를 변환시키는 메시지를 주고받으며 상호 교류하는 객체의 모임이다.
② 데이터 객체는 메시지를 전달하므로 능동적이라 할 수 있다.
③ 객체 분류, 상속, 메시지 전달은 객체지향형 프로그래밍의 기본적인 구축 블록이다.
④ Smalltalk, C++, Java, C# 등은 대표적인 객체지향형 언어이다.
⑤ 객체지향 언어는 다른 패러다임과는 독립적인 관점의 패러다임으로, 명령형 언어, 함수 어법, 논리 언어 어느 것과도 결합이 가능하다.

3. 함수형 프로그래밍
① 계산 문제를 수학 함수의 집합으로 모델링한다.
② 각 함수는 입력 도메인과 결과 도메인을 갖는다. 이 점이 저장문을 기본으로 하는 언어들과의 차이점이다.
③ 함수는 함수 합성, 조건식, 재귀를 사용하여 서로 교류하고 결합한다.
④ Lisp, Scheme 등이 대표적인 함수형 프로그래밍 언어이다.
⑤ 명령형 언어에서 사용하는 변수, 배정문 등을 사용하지 않고 프로그램을 구성한다.

4. 논리형 프로그래밍(선언형 프로그래밍)
① 어떻게 문제를 풀 것이지 대신, 프로그램이 얻어내야 하는 결과가 무엇인지를 선언하도록 문제를 모델링하여 프로그램을 작성한다.
② 규칙기반 언어라고 한다.
③ 논리 언어는 기호 논리의 원리를 기반으로 하여, 개체에 대한 사실과 개체 사이의 관계 규칙을 이용하여 원하는 결과를 얻어낸다.
④ Prolog는 대표적인 논리형 프로그래밍 언어이다.

3. 프로그래밍 언어의 종류
(1) 시대별 프로그래밍 언어
| 시기 | 특징 | 주요 PL |
| :--- | :--- | :--- |
| 1950년 이전 | 디지털 컴퓨터 이전의 언어 | Plankalkul |
| 1950년대 | 최초의 PL | 어셈블리 언어, Fortran, LISP, APL |
| 1960년대 | PL의 다양화 | ALGOL 60, COBOL, Basic, PL/1 |
| 1970년대 | 단순성, 추상화 | Pascal, C, Smalltalk, Prolog |
| 1980년대 | 객체지향 | Ada, C++, Perl, Python |
| 1990년대 | 통합, 스크립트, 인터넷 | VB, Java, JavaScript |

(2) 인공지능
① Lisp : 최초 AI 언어로 1960년 존 맥카시(John McCarthy)가 설계하였다. 일련의 리스트 형태로 된 데이터를 처리하도록 설계되었다.
② Scheme : MIT에서 개발된 언어로 Lisp 언어의 일종이다.
③ Prolog : 매우 짧은 양의 코드도 효율성을 지니는 논리 기반 프로그래밍 언어이다.


(3) 교육

① Basic
- 프로그램 초급자들이 언어를 쉽게 다룰 수 있도록 고안되었다.
- 최초의 Basic은 간단한 문법 구조로 이루어져 있으며, 제어 구조는 GOTO문과 GOSUB문으로 구성되었다.

② Pascal
- Algol에서 파생하였다.
- 1970년대 프로그래밍 교육용으로 설계되었으며 사용자가 복합적인 구조의 데이터 구조를 정의할 수 있으며, 별명(aliasing), 포인터 등의 특징을 갖는다.

③ Python
- 컴퓨터과학 교과과정에서 원리를 먼저 가르치는데 집중할 수 있을 만큼 언어가 단순하다.
- 객체지향적 언어로서, 높은 효율, 쉬운 사용법, 확장성을 지닌다.

(4) 과학, 공학

① Fortran I
- 과학 계산 목적으로 IBM의 존 백커스가 1954년 설계하였다.
- IF, GO, GOTO 문을 포함하며, 오늘날 언어에서 사용되고 있는 데이터 형식들도 Fortran에서 시작되었다.

② Algol
- 과학 및 수학 알고리즘의 계산과 출판을 동시에 할 수 있는 포트란보다 더 잘 정의된 언어를 만드는 것이 목적이었다.
- Fortran의 많은 특징을 포함하고 있으며, 블록 구조 개념과 재귀호출 기능 등이 추가되었다.
- Algol 60 언어의 구문은 백커스-나우어 형식(Backus-Naur From, BNF) 표기법으로 기술되었는데, 이후 대부분의 프로그래밍 언어 정의에 BNF 표기법이 사용되고 있다.

③ APL(A Programming Language)
- 간결한 체계와 특수한 비ASCII 성질을 가진 수학적 언어로 행렬, 대수 등의 수학 계산을 위한 프로그램을 빨리 작성하기 위한 언어이다.

[참고]

* 파이썬(Python)
- 1991년 귀도 반 로섬(Guido van Rossum)이라는 프로그래머에 의해 개발된 언어이다.
- 가독성이 높고 쉬운 문법 덕분에 다른 프로그래밍 언어보다 빠른 습득이 가능하다.
- 데이터 분석과 모델링을 다루는 통계학부터 딥러닝과 인공지능을 활용하는 의학에까지 다양한 분야에 두루 활용되고 있다.
- 컴파일 과정 없이 인터프리터(Interpreter, 해석기)가 소스 코드를 한 줄씩 읽어 들여 곧바로 실행하는 스크립트 언어(Script language)이다.
- 동적 타입 언어로 변수의 자료형을 지정하지 않고 단순히 선언하는 것만으로도 값을 지정할 수 있다.

* 코틀린(Kotlin)
- Java 플랫폼을 대상으로 하는 새로운 프로그래밍 언어이다.
- Java 코드와의 상호 운용이 가능하며, 간결하고 안전하며 또 실용적이다.
- Java가 주로 사용되는 서버사이드의 개발은 물론 Android 앱을 개발할 때 사용할 수 있다.
- 정적 타입의 언어이다.


(5) 정보 시스템
① Cobol(Common Business Oriented Language)
㉠ 사무처리용으로 만들어진 언어인 미국 국방부를 중심으로 결성된 그룹인 CODASYL(Conference on Data System Language)에 의해 개발되었다.
㉡ 구문의 기반을 영어로 하고, 명령형 프로그래밍 스타일을 지원한다.
㉢ COBOL 프로그램은 보통 식별부(identification), 표지부(environment), 데이터부(data), 절차부(procedure)의 네 부문으로 구성되어 있다.
② SQL
㉠ 데이터베이스 명세, 보고서 생성, 정보 추출 용도로 선언형 프로그래밍 도구로 1980년대 출현했다.
㉡ 관계형 데이터베이스에서 정보를 명세하고 추출하는데 사용되는 언어이다.
③ Java
㉠ 제임스 고슬링(James Gosling)이 설계하였다.
㉡ 단순하고 편리한 객체지향 언어이다.
㉢ 가장 기본적인 구성 요소는 클래스이다. 모든 데이터와 메소드는 클래스와 관련되어 있다.
㉣ 상속, 엄격한 데이터 타입 검사, 모듈 방식, 예외 처리, 다형성, 문자열 처리, 쓰레기 수집 등의 지식을 지니며, 포인터, 다중상속, 매크로 전처리기를 지원하지 않는다.

(6) 시스템과 네트워크

심층학습
촘스키 분류
1950년대 중반 언어학자 촘스키(Chomsky)는 자연 언어에 대해 4가지 언어 유형의 문법을 제안하였다.
가장 간단한 것부터 가장 복잡한 문법 부류의 순서는 다음과 같다.

1. 정규문법(regular grammar)
① 오른쪽 정규 문법은 다음과 같은 형태의 생성 규칙만 가질 수 있다.
   A -> wB
   A -> w
   ㉠ w는 단말들의 스트링이고 B는 비단말자이다.
   ㉡ 생성규칙의 각 선택절은 많아야 하나의 비단말자를 가질 수 있고, 이 때 비단말자는 반드시 맨 오른쪽에 나타나야 한다.
   ㉢ 직접적인 순환이 허용된다.
② 왼쪽 정규 문법은 선택절에 단 하나의 비단말자가 맨 왼쪽에 나타날 수 있다는 것만 다르다.
   A -> Bw
   A -> w

2. 문맥자유 문법(context-free grammar)
문법 생성규칙은 A -> w의 형태로 쓴다. A는 비단말자 기호, w는 비단말자와 단말자 기호로 구성된 스트링이다.

3. 문맥민감(의존) 문법(context-sensitive grammar)
① a -> b로 정의되는 생성규칙을 갖는다.
② 좌변의 기호가 단 하나의 비단말자로 제한되지 않는다. 단말자와 비단말자를 모두 사용해서 만든 스트링이 나올 수 있다.
③ 우변의 길이가 좌변의 길이보다 크거나 같다.



4. 무제한 문법(unrestricted grammar)
① 우변의 길이에 대한 제한도 없다.
② 무제한 문법은 튜링 기계와 표현력이 같으며 모든 계산 가능 함수를 처리할 수 있다.

보충학습
문법의 구성요소
문법은 생성규칙의 집합과 비단말자 기호의 집합 N, 단말자 기호의 집합 T, 비단말자인 시작 기호 S로 구성된다.
촘스키 분류에서 각 문법 부류는 생성 규칙의 형태만 다르며, 단말자, 비단말자, 시작 기호 등의 개념은 모두 같다.

1. 정규 문법
① 정규 문법은 가장 간단한 부류로 표현력에 있어서 정규식(regular expression)이나 유한상태 오토마타(finite-state automata)와 동일하다.
② 정규 문법은 문맥자유 문법이나 BNF 문법에 비해 표현력이 떨어진다.

• 정규식(regular expression)
프로그래밍 언어를 어휘 수준에서 정형적으로 명세하는 정규 문법을 대신할 수 있다.

| 정규식 | 의미 |
| :--- | :--- |
| x | 문자 x |
| \x | 확장 문자 |
| {name} | 명칭 참조 |
| M|N | M 또는 N |

유한상태 오토마타(finite state automata)
컴퓨터 프로그램과 전자 논리 회로를 설계하는 데 쓰이는 수학적 모델이다. 한 번에 오로지 하나의 상태만을 가지게 되며, 현재 상태(Current State)란 임의의 주어진 시간의 상태를 칭한다. 어떠한 사건(Event)에 의해 한 상태에서 다른 상태로 변화할 수 있으며, 이를 전이(Transition)라 한다. 특정한 유한 오토마톤은 현재 상태로부터 가능한 전이 상태와, 이러한 전이를 유발하는 조건들의 집합으로서 정의된다.

2. 문맥 자유 문법
① 문맥 자유 문법은 생성규칙의 집합 P, 단말자 기호의 집합 T, w비단말자 기호의 집합 N, (비단말자 기호 중의 하나로 따로 구별하는) 시작 기호 S로 구성된다.
② 문법 생성규칙은 A -> w의 형태로 쓴다. A는 비단말자 기호, w는 비단말자와 단말자 기호로 구성된 스트링이다.

02 파스 트리(parse tree)

심층학습
1. 파스 트리 정의
① 임의의 문장을 정의된 BNF 문법에 적용하여 유도하는 과정을 이해하기 쉬운 구조로 나타낸 것이다.
② 파스 트리란 유도 과정을 이해하기 쉬운 트리 형태의 계층적 구조로 나타낸 것이다.

2. number '123' 유도하는 과정
<number> -> <number><digit>
         -> <number><digit><digit>
         -> <digit><digit><digit>
         -> 1<digit><digit>
         -> 12<digit>
         -> 123

① 1단계 : <number>는 <number><digit>으로 대치된다.
② 2단계 : 첫 번째 유도 결과의 <number>는 <number><digit>으로 대치된다.
③ 3단계 : <number>를 <digit>으로 대치한다.
④ 4단계 : <digit>을 1, 2, 3으로 대치한다.
⑤ 파스트리에서 내부 노드들은 비단말 기호로 표시되고, 리프 노드들은 단말 기호로 표시된다.

3. BNF(Backus-Naur Form) 표기법
① BNF(Backus-Naur Form) 표기법은 ALGOL 60 언어의 구문 형식을 정의할 때 최초로 사용되었다.
② 한 프로그래밍 언어의 구문에 대한 생성 규칙(production rule)들의 집합이다.
③ 모든 정상적인 프로그램을 이 생성규칙들을 가지고 산출한다는 것이 이론적으로 가능하다.
④ 생성 규칙은 작성된 프로그램이 구문에 맞는지 여부를 인식하기 위한 구문 규칙(syntax rule)으로도 사용된다.
⑤ 생성규칙의 왼쪽에는 정의될 대상(object)이 표시되며, 오른쪽에는 그 대상에 대한 정의가 나타난다.

| :--- | :--- |

| \| | 선택 |
| <> | 비단말 기호 |
| <>로 묶이지 않은 기호 | 단말 기호 |

07 함수

1. 함수
① 함수는 특정한 기능을 수행하고, 그 수행 결과로 어떤 값을 반환하는 부프로그램이다.
② 프로그램 실행 중 함수명과 동일한 부분을 만나면, 해당 함수로 분기하여 함수를 실행하고, 함수의 실행이 끝나면 다시 메인 함수로 되돌아온다.

2. 사용자 정의 함수

[함수 정의]
반환되는 자료형 함수명(입력)
{
    기능
    ....
    return 반환값;
}

[예시]
int TwoSum(int a, int b)
{
    int result;
    result = a + b;
    return result;
}

① 함수명 : 식별자 작성 규칙과 동일하게 작성한다.
② 입력 : 함수의 입력으로 어떤 매개변수가 들어오는지를 나타낸다.
   배열을 함수의 매개변수로 사용할 수 있다. 이때 배열의 크기는 배열명과 함께 기록하지 않고 배열명에는 빈 대괄호를 사용하고 배열의 크기는 또 다른 매개변수로 전달한다.
③ 반환값 : 함수가 입력을 받아 기능을 수행한 후 반환되는 결과값이다.

3. 매개변수 전달 방법
(1) 값에 의한 호출(call by value)
① 함수가 호출되면, 매개변수 값을 스택 기억장소 영역에 복사한다.
② 값을 복사하기 때문에 호출된 함수에서 매개변수값을 바꾸더라고 main() 함수에는 전혀 영행을 주지 않으므로 두 함수는 독립적이며 안전하다.

(2) 주소에 의한 호출(call by reference)
① 전달하고자 하는 값의 주소를 함수에 전달한다.
② C 언어에서는 포인터를 사용한다.
③ 호출하는 쪽에서는 주소에 의한 호출 효과가 필요한 변수의 주소값을 주소 연산자(&)를 이용하여 함수에 넘겨주고, 그 주소값을 받는 함수의 몸체 부분에서는 간접 연산자(*)를 사용하여 이 주소값의 값을 읽거나 값을 저장하게 된다.

④ 지역변수로 선언한 변수명은 서로 같을 수 있지만 서로 별개의 변수이다.

3. 변수의 우선순위
① 지역변수가 전역변수보다 우선순위가 높다.

4. 정적변수(static variable)
① 프로그램의 실행이 끝날 때까지 메모리에 계속 보존되는 변수로 전역변수와 생명력이 동일하다.
② 변수가 사용될 수 있는 유효 영역은 선언되는 위치에 따라 다르다.
③ 전역변수 위치에서 선언되면 파일 내부에서 사용할 수 있고, 지역변수 위치에서 선언되면 선언된 블록 내에서만 사용할 수 있다.
static int n = 10; // 외부 정적변수
int main()
{
    static int count = 1; // 내부 정적변수
    .....
}
④ 외부 정적변수 : 변수의 생명력은 전역변수와 같고, 유효 영역은 전역변수와 달리 변수가 선언된 파일에서만 사용할 수 있다.
⑤ 내부 정적변수 : 변수의 생명력은 전역변수와 같고, 유효 영역은 지역변수와 같이 변수가 선언된 블록 내부이다.

5. 레지스터 변수(register variable)
① 기억장소를 CPU 내에 있는 일반 레지스터를 사용하여 연산의 속도 향상을 추구하는 것을 목적으로 하는 변수이다.
register int count = 1;
② 레지스터 변수의 자료형은 int, char, short 및 포인터 형만 사용할 수 있다.
③ 레지스터 변수는 CPU의 레지스터에 저장되므로 처리 속도가 일반 변수보다 빠르다.
④ 반복문의 첨자를 레지스터 변수로 사용하는 경우가 많다.

(1) 메소드의 분류
① 객체 메소드 : static 선택항목을 갖지 않는 메소드로 객체를 통하여 접근한다.
② 클래스 메소드 : static으로 선언하며 클래스 이름을 통하여 접근한다.
③ 종단 메소드 : final로 선언하며 종단 메소드를 포함하는 클래스로부터 하위 클래스를 생성할 때, 하위 클래스에서 종단 메소드를 재정의(overriding)하여 사용할 수 없다.
④ 추상 메소드 : abstract로 선언하며 public만을 사용할 수 있다. 추상 메소드는 메소드의 실행문을 가지지 않으므로, 반드시 하위 클래스에서 재정의하여 사용해야 한다.

보충학습
자바의 접근지정자
* public : 모든 클래스에서 접근할 수 있다.
* protected : 같은 클래스 내부와 같은 패키지 내의 클래스에서 접근할 수 있고 다른 패키지라도 자식 클래스에서는 접근 가능하다.
* default : 접근 지정자를 생략하면 같은 클래스 내부와 같은 패키지 내의 클래스에서 접근할 수 있다.
* private : 같은 클래스 내부에서만 접근할 수 있기 때문에 다른 클래스에서는 접근이 불가능하다.

유효성: 명령은 종이, 연필로 수행 가능
