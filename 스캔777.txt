

PART 07
네트워크 정보보호

01 침입 차단 시스템 : 방화벽(Firewall)

(1) 침입 차단 시스템의 목적

① 외부 네트워크와 내부 네트워크 사이에 일종의 보호막을 제공하여 내부의 네트워크가 안전하게 유지될 수 있도록 보장한다.
② 정당하지 않은 사용자가 중요한 데이터에 접근하는 것을 막고, 정당한 사용자가 네트워크 자원을 방해 없이 접근하도록 하는 것이다.
③ 침입 차단 시스템은 접근 제어 목록(ACL : Access Control List)을 통해 네트워크에 접속되는 트래픽에 대한 보안정책을 설정한다.
④ 일반적으로 보호하고자 하는 네트워크는 사용자가 속한 기관의 네트워크이고, 불법 사용자는 외부의 네트워크에 있는 사용자로 간주한다.
⑤ 완벽하게 조직의 보안을 보장하지는 않지만, 비교적 적은 비용으로 효과적인 차단이 가능하다.

방화벽
인터넷과 같은 외부 통신 체제로부터 네트워크를 보호해주는 H/W, S/W

보충학습

방화벽(firewall)

침입 차단 시스템은 방화벽(firewall)이라고도 불리며, 빌딩 공사에서 빌딩의 일부분에서 다른 부분으로 불이 번지는 것을 막기 위해서 주변과의 모든 연결 통로를 차단하는 방화벽에서 유래한 것으로, 컴퓨터 네트워크 환경에서 네트워크의 보안 사고가 주변 혹은 내부로 확대되는 것을 막기 위해 내부 네트워크와 외부 네트워크 사이의 정보 흐름을 안전하게 통제하는 시스템을 의미한다.

패킷 필터링

ACL을 생성해두고 네트워크 패킷 헤더 내의 정보(발신지/목적지 프로토콜)를 기준으로 지나가는 임의의 패킷을 선택적으로 허용/거부하여 트래픽을 제어한다.

(2) 침입 차단 시스템의 기능

1) 접근 통제

① 침입 차단 시스템은 기본적으로 외부 네트워크에서 내부 네트워크로 유입되는 메시지를 미리 정해진 규칙에 따라 차단하거나 혹은 허용하는 기능을 제공한다.
② 침입 차단 시스템은 허용된 서비스와 전자 우편 서버나 공개 정보 서버와 같은 특정한 호스트를 제외하고는 외부에서 내부 네트워크에 접속하는 것을 패킷 필터링 등을 이용하여 통제한다.
③ 패킷 필터링은 내부 네트워크로 들어오는 패킷의 IP주소 혹은 서비스 포트 번호 등을 분석한 후, 외부 또는 내부 네트워크에 대한 접근을 통제하는 기능을 제공한다.
④ 서비스의 원활한 사용과 보안성을 고려하여 외부 네트워크에서 내부 네트워크로 들어오는 패킷에 대해서 접근 통제를 더욱 강화하여야 한다.

2) 사용자 인증

① 침입 차단 시스템은 내/외부 네트워크 사이의 접속점이기 때문에 침입 차단 시스템을 지나가는 트래픽에 대한 사용자들의 신분을 증명하는 기능이 필요하다.
② 사용자 인증은 ID/Password나 공개키 인증서를 이용하여 사용자에 대한 식별기능과 이를 검증하는 인증 과정으로 이루어진다.
③ 메시지 인증은 가상사설망(VPN : Virtual Private Network)과 같은 신뢰할 수 있는 통신회선을 통해 전송되는 메시지의 신뢰성을 보장한다.






3) 감사 및 로그 기능

① 침입 차단 시스템은 모든 트래픽에 대한 접속 정보 및 네트워크 사용에 따른 유용한 통계 정보를 기록하는 감사 및 로그 기능이 있어야 한다.
② 감사 로그는 침입 차단 시스템의 규칙 집합에 접근한 사람과, 내용 변경 시점, 침입 차단 시스템 서비스의 시작시간, 중지 시간 등을 기록한다.
③ 운영 로그는 실제 침입 차단 시스템이 운영되면서 차단 또는 허용된 네트워크 메시지에 대한 정보 등을 기록한다.
④ 감사 증적(audit trail)은 감사 추적 또는 책임 추적성을 의미하며, 시스템 내의 사용자를 식별하고 행동을 기록하여 추적할 수 있게 한다.
⑤ 침입 차단 시스템의 관리자는 사용자들의 활동이나 인가되지 않은 외부로부터의 접근이나 침입 사건 등에 대한 로그 파일을 바탕으로 보안 기능과 보안 관련 데이터에 대한 안전한 보안 관리 기능을 제공해야 한다.

4) 프라이버시 보호

내부 네트워크의 정보유출 방지, 이중 DNS(Dual Domain Name System) 기능과 프락시 기능 등을 제공함으로써 프라이버시와 관련된 정보의 노출을 막거나 공격자로부터 보호되어야 한다.

5) 서비스 통제

안전하지 못하거나 위험성이 존재하는 서비스를 필터링 함으로써 내부 네트워크의 호스트가 갖고 있는 취약점을 감소시켜 준다.


[보충학습]
침입 차단 시스템의 특성

1. 기본적으로 불안전한 서비스에 대한 접근을 차단함으로써 내부 네트워크에 있는 호스트들이 위험에 노출되는 것을 감소시킨다.
2. 인증 소프트웨어를 설치하여 외부에서 내부로 접근을 시도하는 사용자의 신분을 증명하는 사용자 인증 기능을 수행한다.
3. 보안을 위해 추가되는 보안 소프트웨어를 여러 호스트에 분산시키는 것과는 달리 침입 차단 시스템에 집중 설치하여 효율적인 관리를 할 수 있다.
4. 침입 차단 시스템의 보안 설정을 통해 확장된 개인 정보보호 기능을 수행할 수 있다.
5. 모든 트래픽이 방화벽을 통하여 전송된다면, 전송되는 트래픽에 대한 정보를 기록하여 이후 침입 판단에 활용할 수 있는 감사 통계 자료로 사용할 수 있다.


[오른쪽]

로깅(logging) 및 감사추적

인터넷으로부터의 모든 접근이 방화벽을 통한다면, 방화벽은 접근 내용을 기록하여 접속정보 및 네트워크 사용에 따른 유용한 통계정보를 제공하는 사후추적 기능을 제공하고, 망 사용에 대한 가치있는 통계를 제공할 수 있다.

NAT(Network Address Translation)

비공인 IP를 사용하는 내부망 사용자가 외부 서비스 접속 시 사실 IP 주소를 공개된 IP로 변환시킴으로써 방화벽 내부에 존재하는 시스템들의 IP를 외부에 공개되지 않게 한다.

방화벽 설치 시 고려사항

• 설치환경과 환경에 맞는 방화벽을 설치하여 내부보안을 증가시킬 수 있다.
• 방화벽 시스템의 운영 정책을 설정한다.
• 방화벽을 설치해야 할 기관의 네트워크 환경과 방화벽에서 제공하는 업체의 사후 기술 지원을 고려해야 한다.


(3) 침입 차단 시스템의 단점

① 폐쇄부를 이용하여 접근 통제를 수행함으로써 Telnet, FTP, POP 서비스와 같은 사용자들이 자주 사용하는 특정 서비스에 대하여 장애를 일으킬 수 있다.
② 침입 차단 시스템을 통과하지 않고 백 도어(Back Door)를 통하는 트래픽은 막을 수 없다.
③ 수신된 패킷의 내용에 대한 검색이 불가능하므로 전자우편을 통하여 유입되는 바이러스를 검색할 수 없다.
④ 악의적인 내부 사용자나 스파이 등에 의한 보안 침해를 방어하지 못한다.
⑤ 네트워크에 대한 모든 접속이 침입 차단 시스템을 경유하므로 시스템의 부하가 증가하고, 속도가 저하된다.

(4) 침입 차단 시스템의 차단 방법에 따른 분류

1) 패킷 필터링 시스템

① 패킷 필터링 시스템은 내부 호스트와 외부 호스트들 사이에서 패킷을 선택적으로 통제하는 네트워크 보안 메커니즘이다.
② 일반적으로 패킷 필터링 침입 차단 시스템에서 사용되는 라우터는 스크린 라우터 혹은 패킷 필터링 라우터라고 불린다.
③ 패킷 필터링 시스템의 발신지 주소와 목적지 주소, 그리고 사용되고 있는 세션과 어플리케이션 프로토콜에 기반해서 데이터의 흐름을 통제한다.
④ 패킷의 헤더에 저장된 정보를 이용함으로써 필터링 처리가 비교적 간단하며 응용 게이트웨이 시스템 등과 달리 어떤 특정한 사용자 소프트웨어나 클라이언트 컴퓨터에 대한 복잡한 환경 설정이나 절차가 필요하지 않다.


[보충학습]

패킷 필터링 시스템의 보안 정책

1. 디폴트 허용(Default Accept) 정책
   디폴트 허용 보안 정책은 기본적으로 거부할 패킷에 대한 정의가 사용되고, 나머지 정의되어 있지 않은 모든 패킷은 허용한다는 정책이다.

2. 디폴트 거부(Default Deny) 정책
   디폴트 거부 보안 정책은 기본적으로 수신된 패킷은 거부한다는 원칙하에 허용할 패킷을 정의하는 정책이다.
   일반적으로 보안 정책 측면에서는 허용된 패킷만을 통과시키는 디폴트 거부 방침이 더 안전하다.


[왼쪽]

스크리닝 라우터
• 구조가 간단하다.
• 장비 추가 비용 소요가 없다.
• 라우터에 복잡한 패킷 규칙 설정이 필요하고 인증 기능 수행은 불가능하다.
• 내부 구조를 숨기기 어렵다.

라우터(Router)
인터넷상에서 정보를 전송하기 위해서는 IP 네트워크 상의 패킷이라는 데이터를 형식으로 사용한다. 이러한 데이터를 서로 연결시켜주는 기본 장치이다.
라우터는 RIP(Routing Information Protocol)이나 OSPF(Open Shortest Path First)와 같은 라우팅 프로토콜을 사용하는 라우터끼리의 통신을 이용하여 수신한 각 패킷에 대한 라우팅을 결정한다.






[보충학습]

패킷 필터링 접근규칙 예

No.    From           Service    To             Action
1      192.168.1.11   25         10.10.10.21    Allow
2      Any            21         10.10.10.21    Allow
3      Any            80         Any            Allow
4      192.168.1.11   143        10.10.10.21    Allow
5      Any            Any        Any            Deny

1. 내부 서버(192.168.1.11)에서 외부 서버(10.10.10.21)로 가는 SMTP 패킷을 허용한다.
2. 내부 Any IP대역에서 외부 서버(10.10.10.21)로 가는 FTP 패킷을 허용한다.
3. 내부 Any IP대역에서 외부 Any IP대역으로 가는 패킷 중 80번 포트를 목적지로 하는 패킷을 허용한다.
4. 내부 서버(192.168.1.11)에서 외부 서버(10.10.10.21)로 가는 IMAP 패킷을 허용한다.
5. 이들 규칙에 해당하지 않는 패킷은 접근을 거부한다.


[오른쪽]

ingress 필터링

라우터 외부에서 라우터 내부로 유입되는 패킷을 필터링하는 것

egress 필터링

라우터 내부에서 라우터 외부로 나가는 패킷의 소스IP를 제한하여 필터링

Blackhole filtering(Null routing 필터링)

특정 IP 대역에 대해서 Null인 인터페이스로 보내도록 함으로써 패킷의 통신이 되지 않도록 한다.


[보충학습]

패킷 필터링 방법의 단점

1. 응용 서비스 별로 정교한 제어가 불가능하다.
2. 로그 기능과 감사 기능이 부족하다.
3. 원격 관리 기능이 없다.
4. 필터링 규칙을 설정하기 어렵고 설정된 규칙을 시험하기 어렵다.
5. 패킷 필터링 시스템은 UNIX 시스템의 원격 명령어(rсp, rlogin, rdist, rsh 등)와 같은 명령어에 대해서는 잘 적용되지 않는다.


[심화학습]

스테이트풀 패킷 검사 방화벽(Stateful packet inspection Firewall)

① 상태 조사 방화벽은 네트워크 계층에서 프로토콜의 패킷을 대상으로 전송 여부를 판단하는 시스템이다.
② 패킷 필터링 기능뿐만 아니라 상태 테이블(state table)에 기반을 둔 애플리케이션 접근 제어에도 적용한다.
③ 네트워크 계층 이하에서 동작하는 Stateful packet Inspector 모듈을 통하여 전체 계층에 대한 상태를 조사할 수 있으며 사용자의 특별한 설정 없이 투명성을 제공한다.
④ 패킷 필터링 방화벽과 마찬가지로 동일한 패킷 정보를 검토하지만, TCP 연결에 관한 정보를 기록한다.
⑤ 스테이트풀 방화벽은 TCP 순서번호를 추적해서 순서번호를 이용한 세션하이재킹 같은 공격을 막는다.

2) 응용 게이트웨이 방화벽

① 응용 게이트웨이 방식의 침입 차단 시스템은 외부 또는 내부 네트워크상의 호스트나 서비스에 대한 접속을 중간에서 처리하는 프락시 서비스(proxy service)를 사용한다.
② 내·외부 간의 모든 응용 계층의 트래픽에 대한 로깅이나 telnet, FTP 등에서 사용자 인증이 필요한 경우에 엄격한 인증 방법을 사용한다.
③ 두 개의 네트워크 간의 모든 접속은 응용서비스별로 제공되는 프락시 서비스 기능을 이용하여 허가되지 않은 사용자나 호스트 명령어들의 접근이나 수행을 막을 수 있다.
④ 프락시 서버를 통해 외부의 네트워크와의 직접적인 연결을 피할 수 있고 내부 네트워크의 IP주소를 노출시키지 않음으로써 내부 네트워크 정보를 보호할 수 있다.
⑤ 응용계층 게이트웨이는 응용 서비스마다 각각 다른 응용 게이트웨이를 구현하여 보다 안전하게 시스템을 보호한다.
⑥ 사용되는 응용 서비스가 증가할수록 구축 비용 부담이 커진다.


[왼쪽]

프락시 서버

외부 네트워크와 내부 네트워크의 경계선에 위치한 배스천 호스트를 설치하여 두 개의 네트워크 간의 중계 기능을 제공한다.


배스천 호스트-프락시 서비스

• 세션에 포함되어 있는 정보의 유해성 검사
• 방화벽에서 세션 종료하고 새로운 세션 형성
• 출발지에서 방화벽까지의 세션과 방화벽에서 목적지까지의 세션으로 구성
• 검사 수행 기능


[보충학습]

배스천 호스트(Bastion Hosts)

배스천(bastion)이란 중세 성곽의 외부 방어에 대한 강화된 독립부에서 유래된 이름이다. 이는 외부 공격에 대하여 가장 중요한 수비 부분을 뜻하며 침입 차단 시스템 관리자가 중점 관리해야 될 부분이다.

배스천 호스트는 외부 네트워크에서 내부 네트워크의 호스트로 직접 접속을 허용하지 않으므로 외부에서 내부 네트워크로 접속하기 위해서는 배스천 호스트를 접속해야 한다.
배스천 호스트는 ftp, telnet, DNS, SMTP, HTTP 등의 네트워크 서비스를 간접적으로 허용하거나 제한할 수 있다.


[보충학습]

프락시 서비스(proxy service)

프락시란 대리인의 의미를 가지고 있으며, 프락시 서비스는 클라이언트의 서비스(FTP와 Telnet 등의 서비스) 요청을 받아, 사이트의 보안 정책에 따라서 실제 서비스를 수행하는 서버로 그 요청을 전달하고, 실제 서버로부터 실행 결과를 수신하여 마치 자신이 수행한 것처럼 사용자에게 전달하는 기능을 한다.


회로 레벨 게이트웨이 방화벽

1. 외부와 내부 네트워크 사이에 안전한 프락시 데이터 채널을 설정하기 위한 메커니즘을 구축하고 내부 네트워크에 있는 호스트를 보호하는 목적으로 사용한다.
   • 응용 계층 게이트웨이가 내부 네트워크 호스트를 보호하는 목적으로 한다면 회로 레벨 게이트웨이 방화벽은 내부 네트워크 호스트의 보호를 목적으로 한다.

2. 종단-대-종단 TCP 연결을 허용하지 않고 두 개의 TCP 연결을 설정한다.
   • 두 연결이 설정되면 게이트웨이는 일반적으로 내용에 대한 검사를 하지 않고 한 연결에서 다른 연결로 TCP 단편을 중계해서 전달한다.
   • 어느 연결을 허용할 것인지 결정하는 것이 회로레벨 게이트웨이의 보안 기능이다.

3. 서비스마다 개별 프락시 서버를 두지 않고 공유하므로 서비스에 대해 유연하게 대처할 수 있다.

4. 시스템 관리자가 내부 사용자를 신뢰할 경우에 일반적으로 사용한다.

5. 회로레벨 게이트웨이 구현의 한 예가 SOCKS 패키지이다.


(5) 침입 차단 시스템의 구성 방법에 따른 분류

1) 듀얼 홈드 게이트웨이

듀얼 홈드 게이트웨이는 침입 차단 시스템이 설치되는 호스트에 두 개의 네트워크 인터페이스가 설치되어 내/외부 네트워크 간의 직접적인 트래픽을 차단한다.

2) 스크린 호스트 게이트웨이

① 스크린 호스트 게이트웨이는 베스천 호스트와 스크린 라우터라는 분리된 라우터를 혼합하여 사용한 침입 차단 시스템이다.

② 외부 네트워크와 내부 네트워크가 완전히 분리되어 외부로부터의 직접적인 접근이 허용되지 않으며 응용 서비스 종류에 따라 종속적이기 때문에 스크리닝 라우터보다 안전하다.

㉠ 스크린 라우터 : 외부 네트워크와 베스천 호스트 사이에 위치하며 정해진 정책에 따라 내부로 전달되는 트래픽을 차단한다.

㉡ 베스천 호스트 : 내부 네트워크와 스크린 라우터 사이에 위치한다.

• 스크린 라우터 내부 네트워크와 외부네트워크 사이 시스템을 설치해 놓고 시스템의 TCP/IP 포워딩 기능을 막음으로써 구현된다.

세션

베스천 호스트의 구별

1. 싱글 홈드 베스천 호스트(single-homed bastion host)
   ① 외부에서 내부로 전송되는 패킷을 일차적으로 패킷 필터링 라우터에서 필터링 규칙을 적용하여 제어한다.
   ② 베스천 호스트에서 IP주소, 요청 서비스 제공 여부 확인, 사용자 인증 과정을 점검한다.
   ③ 내부에서 외부로 전송되는 트래픽은 베스천 호스트에서 IP 패킷만 전송된다.
   ④ 외부에서는 베스천 호스트에 대한 정보만 알 수 있고 내부 네트워크에 대한 정보를 알 수 없다.

2. 듀얼 홈드 베스천 호스트(Dual-homed Bastion Host)
   ① 싱글 홈드 베스천 호스트 기능을 유지하면서 두 개의 네트워크 인터페이스를 가진 베스천 호스트로 구성되어 있다.
   ② 하나의 네트워크 인터페이스는 인터넷 등 외부 네트워크에 연결되어 있고 다른 하나는 보호하고자 하는 내부 네트워크가 연결되어 있다.

3) 스크린 서브넷 게이트웨이

스크린 서브넷 게이트웨이는 스크린 호스트 게이트웨이와 듀얼 홈드 게이트웨이의 변형으로, 외부 네트워크 및 내부 네트워크와 분리되어 있는 네트워크를 구성한다.

Normal NAT

① 클라이언트는 내부 IP주소를 출발지 주소로, 접속하고자 하는 외부 IP주소를 목적지 주소로 하는 패킷을 생성하여 방화벽으로 보낸다.
② 방화벽은 규칙에 따라 패킷의 출발지 주소 즉, 내부 IP주소를 방화벽 IP주소로 바꿔 전송한다.
③ 원격지 서버는 바뀐 방화벽 IP주소로 응답을 보낸다.
④ 방화벽은 규칙에 따라 목적지 주소를 클라이언트의 내부 IP주소로 변경한 후 응답을 클라이언트에게 전송한다.


(6) 개인 방화벽(personal firewall)

① 한쪽이 개인 컴퓨터이고 다른 한쪽이 인터넷이거나 기업 네트워크일 경우 이들 사이의 트래픽을 제어한다.
② 개인 방화벽 기능을 가정용 환경이나 회사 인트라넷 환경에 활용할 수 있다.
③ 전형적으로 개인 방화벽은 개인용 컴퓨터상의 소프트웨어 모듈이다.
④ 개인 방화벽의 주요 역할은 허가받지 않은 컴퓨터로부터의 원격 접속을 차단하는 것이다.
⑤ 웜이나 기타 악성 소프트웨어를 탐지하고 차단하기 위해 밖으로 나가는 패킷 활동을 모니터링한다.


(7) DMZ 네트워크

① 외부 방화벽은 인터넷이나 다른 WAN으로 연결되는 경계 라우터의 바로 안쪽 LAN이나 기업 네트워크의 끝에 위치하며 한 개 이상의 내부 방화벽이 기업 네트워크 집단을 보호한다.
② 외부 방화벽과 내부 방화벽 사이에는 DMZ 네트워크 영역이 존재한다.
③ 외부에서 접속할 수 있어야 하며 보호되어야 하는 시스템은 주로 DMZ 네트워크에 배치한다.
④ 일반적으로 DMZ 안에 있는 시스템은 회사의 웹 서버, 이메일 서버, DNS 서버 등으로 반드시 외부로 연결할 수 있어야 한다.


웹 방화벽(Web firewall)
웹 해킹을 방어하기 위한 웹서버에 특화된 방화벽에서 탐지하는 웹 관련 공격경로를 감시하고 공격이 웹서버에 도달하기 전에 차단하는 보안제품이다.

02 침입 탐지 시스템(Intrusion Detection System)

(1) 침입 탐지 시스템의 정의

① 침입 탐지 시스템은 내부 시스템에서 악의적인 공격을 발견하고 이를 보고하는
   보안 솔루션을 말한다.

② 침입 탐지 시스템은 컴퓨터나 네트워크 자원에 대한 악의적인 행위들에 대해 확인
   하고 그에 대해 응답하는 것을 말한다.


(2) 침입 탐지 시스템과 침입 차단 시스템과의 차이점

① 침입 차단 시스템은 단순히 IP 주소와 포트 번호만으로 차단 여부를 결정하지만
   침입 탐지 시스템은 전달되는 메시지 내용을 분석하여 정상적인 트래픽인지 또는
   비정상적인 공격인지를 판단한다.

② 침입 차단 시스템은 공격 자체를 차단하지만 침입 탐지 시스템은 공격 그 자체를
   차단하는 것은 아니며 시도된 공격에 대해 탐지하고 이를 알려주는 역할만 한다.


보충학습
침입 차단 시스템의 취약점

1. 터널링 공격
   침입 차단 시스템에 의해 차단되어야 할 패킷이 다른 네트워크 프로토콜에 의해 캡슐화
   되어 공격에 사용될 때에는 침입 차단 시스템이 이를 차단시킬 수 없게 된다.

2. 응용 기반 공격
   응용 기반 공격이란 응용 개체 간의 직접적인 통신 방식으로 패킷을 전송하는 경우에
   응용 모듈에 포함된 취약성에 의해 발생되는 것을 의미한다.
   만약 침입 차단 시스템이 공격에 사용될 수 있는 명령어를 통과시킬 수 있도록 설정되어
   있을 경우 차단할 수 없게 된다.


보충학습
침입 탐지 시스템을 구축하는 이유

침입을 빠르게 탐지할 경우 침입자를 식별할 수 있고 시스템에 해를 주거나 데이터가 위험
당하기 전에 시스템으로부터 격리시킬 수 있다.
효과적인 침입탐지 시스템을 갖추고 있으면 침입을 하려는 의도를 단념시키게 되어 침입을
예방하는 효과가 있다.
침입탐지를 통해 침입 예방 시설을 강화하는 데 사용할 침입 기술에 관한 정보를 수집할
수 있다.


침입 탐지 시스템의 기능

① 사용자와 시스템 행동에 대한 모니터링 및 분석
② 시스템 설정과 취약성에 대한 감사 기록
③ 중요 시스템과 데이터 파일에 대한 무결성 평가
④ 알려진 공격에 대한 행위 패턴 인식
⑤ 비정상적 행위 패턴에 대한 통계적 분석
⑥ 보안 정책을 위배하는 사용자의 행위를 인식함으로써 운영 체제 감사 추적 관리


침입 탐지 시스템에 의해 탐지 가능한 공격

① 스캐닝 : 시스템의 상태와 취약점을 찾기 위해 여러 패킷을 보내고 그에 대한 응답을 수집하는 수동적 공격

② DoS 공격 : 가용성을 해치기 위해 보내는 일련의 공격

③ 침투 공격 : 버퍼 오버플로 공격과 같이 허가받지 않은 방법을 사용하여 시스템 자원과 권한을 획득한다.


(3) 침입 탐지 시스템의 구성

1) 모니터링부

정보 수집 단계(Raw Data Collection)이다.

2) 분석 및 조치부

① 정보 가공 및 축약 단계(Data Reduction and Filtering) : 수집된 정보에 대한 분석은
   시스템 설정과 패턴 생성기에 의해서 생성된 패턴 데이터베이스의 설정에 따라
   정보 분석기에서 수행된다.

② 분석 및 침입 탐지 단계(Analysis and Intrusion Detection) : 침입 탐지 시스템이
   핵심적인 단계로 기존의 가공된 정보와 축약을 거친 데이터를 기반으로 침입 여부를
   결정한다.

③ 보고 및 조치 단계(Report and Response) : 보고 및 조치는 침입으로 규정된
   행위가 발생할 경우 수행되는 역할로서 실제적인 관리자에게 보고된다.

3) 관리부

관리부는 모니터링부와 분석 및 조치부에 대한 통제 및 관리 기능과 이들에 대한
보안 정책을 제공하는 기능을 한다.


(4) 모니터링 방법에 따른 침입 탐지 시스템의 분류

1) 호스트 기반(Host-based) 침입 탐지 시스템

① 호스트의 자원 사용 실태를 분석하여 호스트에 대한 침입 여부 및 실제 침입 성공
   여부를 식별하는 시스템이다.

② 시스템 무결성 검사를 통해 트로이 목마, 백도어, 루트킷, 내부자에 의한 공격이
   해당 호스트에서 발생했는지 탐지할 수 있다.

③ 호스트 기반 탐지 시스템은 분석 대상이 자신이 설치된 호스트 한 대이며, 무결성
   검사 등을 이용하기 때문에 비교적 정확한 탐지가 가능하다.

④ 각각의 호스트마다 설치하고 관리하므로 네트워크 기반 침입 탐지 시스템보다
   관리 비용이 많고 관리가 힘들다.


2) 네트워크 기반(Network-based) 침입 탐지 시스템

① 탐지 대상이나 목적에 따라 내부 네트워크의 토폴로지(topology) 상의 여러 위치에
   각각 설치한다.

② 방화벽 외부에 설치할 경우 외부 네트워크로부터의 모든 침입에 대한 탐지가 가능
   하며, 방화벽 자체에 대한 침입 탐지가 가능하다.

DMZ(demilitarized zone)
외부 인터넷에 서비스를 제공하는 서버가 위치하는 네트워크로 외부와 내부
모두로부터 보호되어야 하므로 매우 높은 보안 수준을 요구한다.
DMZ 내 서버로는 회사의 웹 서버, 이메일 서버 또는 DNS 서버와 같이 반드시
외부로 연결할 수 있어야 한다.


③ 방화벽 내부에 설치할 경우 주로 DMZ 내의 주요 공개 서비스 서버인 웹 서버
   혹은 FTP 서버 등에 대한 공격을 탐지하며, 방화벽에 대한 접근 통제 규칙의 정확성을
   평가할 수 있다.
④ 백본 네트워크에 설치할 경우 내부 사용자의 악의적 사용 또는 오남용을 감시할
   수 있다.
   주요 서브넷에 설치할 경우 주요 시스템과 자원에 대한 침입 탐지가 가능하다.

(5) 침입 탐지 시스템의 분석 형태

1) 시그니처 분석(Signature Analysis) 방법
   ① 시그니처는 알려진 공격이나 시스템 오용과 관련된 것을 규정한 패턴이다.
   ② 시그니처 분석은 시스템 설정과 알려진 데이터베이스 공격에 대한 사용자의 행위에
      대한 패턴 일치이다.
   ③ 시그니처 분석의 장점은 센서가 목표로 하는 시스템 데이터에 대한 정보를 보다
      밀접하게 수집할 수 있게 함으로써 시스템 오버헤드를 감소할 수 있도록 해준다는
      점이다.
   ④ 시그니처 데이터베이스가 매우 커도 일반적으로 부동 소수점 연산방식을 사용하는
      통계적 분석보다 효율적인 방식이다.
   ⑤ 시그니처 분석의 단점은 정의된 시그니처 데이터베이스에 해당되지 않는 공격
      방법에 대해서는 대처할 수 없다는 점이다.

2) 통계적 분석(Statistical Analysis) 방법
   ① 통계적 분석은 정상적 행위 패턴으로부터 그 편차를 찾아내는 것이다.
   ② 통계 프로파일은 정상적 사용에 대한 다양한 속성들을 판정하여 시스템 객체에
      대해 생성이 된다.
   ③ 평균 빈도와 다양성에 대한 측정은 각각의 정상적 사용 형태에 대해 계산한다.
   ④ 관찰된 값이 정상적인 범위에 속하지 않을 경우 침입 가능성 신호가 발생된다.

침입 탐지 기본 원리
① 침입 탐지는 침입자의 행동 패턴이 일반 사용자와는 다르고 그 차이가 수량화될 수
   있다는 전제에 기반하고 있다.
   False Positive(오탐) : 실제 침입이 아니지만 침입이라고 탐지한다.
   False Negative (미탐) : 실제 침입이지만 침입이 아니라고 탐지한다.
② 침입자 행동의 느슨한 해석은 더 많은 침입자를 탐지할 수 있지만, 동시에 많은 false
   positive를 야기해서 많은 합법적인 사용자들이 침입자로 간주될 수 있다.
③ 침입자 행동의 엄밀한 해석은 false negative를 증가시켜 침입자들이 침입자로 인식되지
   않게 된다.

PART 07

(6) 침입 탐지 시스템의 종류

1) 비정상 탐지 모델(이상 탐지)
   ① 비정상적인 침입이란, 컴퓨터 자원의 비정상적인 행위나 사용에 근거한 침입을
      말한다.
   ② 비정상 탐지를 위해 사용되는 방법으로는 통계적(Statistical) 방법, 특성 추출
      (Feature Selection) 방법, 비정상적인 행위 측정(Anomaly Measure) 방법, 예측
      가능한 패턴 생성(Predictive Pattern Generation), 신경망(Neural Network)
      등이 있다.
   ③ 통계적인 탐지 방법은 과거의 경험적인 자료를 바탕으로 침입을 탐지하기 때문에 정보의
      양이 많을수록 정확한 침입탐지가 가능하며 가장 많이 사용된다.
   ④ 이외의 방법들은 다른 방법이나 매개체를 사용하여 비정상적인 침입을 탐지할 수
      있다는 가능성을 보이는 것에 대한 의의가 있을 뿐, 현실적으로 사용하기에는 많은
      문제점을 가지고 있다. 이 방법들은 각각 독립적으로 사용하기보다 서로의 단점을
      보완하기 위해 결합하여 사용하는 것이 현실적으로 많은 장점을 제공할 수 있다.

2) 오용 탐지 모델
   ① 오용 침입이란, 시스템이나 응용 소프트웨어의 약점을 통하여 시스템에 침입할
      수 있는 공격 형태를 말한다.
   ② 오용 탐지를 위해 사용되는 방법으로는 조건부 확률(Conditional Probability),
      전문가 시스템(Expert System), 상태 전이 분석(State Transition Analysis),
      키 스트로크 모니터링(Keystroke Monitoring), 모델 기반 침입 탐지(Model-
      based Intrusion Detection), 패턴 일치(Pattern Matching) 등이 있다.

호스트
기반
(HIDS)

장점
• 서버에 직접 설치됨에 따라 네트워크 환경과는 무관하다.
• 감사자료가 다양해서 정확한 침입탐지가 가능하다.
• 네트워크 트래픽에 독립적으로 대규모 네트워크에 적용이 쉽다.
• 침입에 대한 빠른 대응이 가능하다.

단점
• 개별 서버에 설치되므로 다소의 시스템 부하가 있다.
• 모든 운영체제에 따라 개발되어야 하므로 개발이 어렵다.
• 탐지가 필요한 서버에 모두 설치해야 하므로 비용이 많이 든다.

네트워크
기반
(NIDS)

장점
• 네트워크 세그먼트 당 하나의 탐지기만 설치하면 되므로 설치가 용이하다.
• 감사자료가 네트워크 패킷이며 표준화되어 개발이 용이하다.
• 독립적으로 실행되어 개발 서버의 성능저하가 없다.

단점
• 네트워크 패킷이 암호화되어 전송될 경우 침입 탐지가 불가능하다.
• 네트워크 트래픽이 크게 증가함에 따라 성능 문제를 야기한다.
• 침입 대응이 늦거나 어렵다.


이상 탐지
• 오탐률이 높다.
• 임계치 설정이 힘들다.

PART 07

03 허니팟(Honeypot)

(1) 허니팟의 개요

① 비교적 최근에 개발된 침입 탐지 기술은 허니팟(Honeypot)이다.

② 허니팟은 공격성향이 있는 자를 중요한 시스템으로부터 다른 곳으로 끌어내도록 설계한 유도시스템이다.

③ 허니팟은 중요한 정보처럼 꾸며진 위조된 정보로 채워진다.
   합법적인 사용자는 이곳에 접근하지 않는 시스템이기 때문에 허니팟에 접근하는 것은 의심스러운 행동이다.

④ 민감한 모니터를 갖추고 있고 이런 접근을 감지하고 공격자의 동작에 관한 정보를 수집하는 사건 기록기(event loggers)를 구비하고 있다.

⑤ 허니팟에 대한 어떠한 공격도 성공적으로 보이도록 만들어졌기 때문에 관리자는 자원을 동원할 시간을 가질 수 있고 진짜 시스템을 노출하지 않고 공격자를 추적하고 기록할 수 있다.

(2) 허니팟의 설계 목적

① 중요한 시스템에 접근하는 공격자를 다른 방향으로 돌린다.

② 공격자의 동작에 관한 정보를 수집한다.

③ 관리자가 반응할 수 있도록 공격자로 하여금 시스템에 충분히 오랜 시간동안 머무르기를 유도한다.

04 침입 방지 시스템(Intrusion Preventing System)

(1) 침입 방지 시스템의 정의

시스템이나 네트워크에 대한 불법 침입 행위를 실시간 탐지, 분석하여 비정상적인
패킷을 자동으로 차단하는 시스템이다.

(2) 침입 차단 시스템, 침입 탐지 시스템과의 비교

① 침입 차단 시스템(방화벽)은 단순 차단 기능, 알려진 공격 패턴 감시 등을 통해
   공격을 감지하지만 변종 원에 의한 공격을 막기 어렵다.

② 침입 탐지 시스템은 알려지지 않은 공격과 내부 공격에 대한 탐지가 어려우며
   침입 탐지의 오판에 따른 시간, 인적, 비용 낭비가 발생한다.

③ 침입 방지 시스템은 웜과 바이러스 등의 침입을 네트워크에서 차단시킴으로써
   보안 인프라와 네트워크의 위험을 제거하고 공격에 대한 사후 조사로 인해 소요되는
   관리자의 운영 부담을 줄인다.

  사용자화 정보를 탐지, 통제하여 외부로의 유출을 사전에 차단한다.

PART 07

05 가상 사설망(VPN : Virtual Private Network)

(1) 가상 사설망의 개요

① PSTN(Public Switched Telephone Network), ISDN(Integrated Services
   Digital Network), xDSL('x' Digital Subscriber Line), 인터넷 등의 ISP
   (Internet Service Provider)의 공중망 서비스를 이용하여 전용선처럼 사용하는
   네트워크이다.

② 전용선 대신 인터넷과 같은 공중망 서비스에 터널링(tunneling) 기법을 이용하여
   전용선에서 유지될 수 있었던 보안과 서비스 품질을 보장한다.

③ Virtual(가상)은 공중망을 이용하여 필요시에만 전용선과 같이 사용할 수 있음을
   의미한다.

④ Private(사설)은 사용자의 데이터 또는 호스트에 대해 타인이 접근하지 못함을
   의미한다.

⑤ Network(네트워크)는 지역적, 기능적 분산 네트워크의 통합을 의미한다.


                암호화                         복호화
PC(지사) → VPN 장비(지사) → 인터넷 → VPN 장비(본사) → 서버(본사)

                암호화                         복호화
PC(인터넷) → 인터넷 → VPN 장비(본사) → 서버(본사)

VPN 접근


(2) 가상 사설망의 특징

① 가상 사설망은 응용 프로그램 하단 계층에서 작동하므로 응용 프로그램을 수정할
   필요가 없다.

② 중간의 네트워크 매니저가 보안에 관련된 키나 네트워크 관리 등에 대해 책임을
   갖기 때문에 사용자가 보안을 위해 수행할 요소가 없다.

가상 사설망

별도의 사설 전용망 없이 암호 기술에 기반한 터널링 프로토콜을 이용해 지점 간을
연결함으로써 저렴한 비용으로 원거리 통신을 가능하게 한다.
• 터널링 기술과 보안과정을 거쳐 내부 기밀을 유지할 수 있고, 공중망을 공유하기
  때문에 낮은 비용으로 고객의 네트워크 성능을 이용할 수 있다.
• 전용 시스템으로 만드는 경우
• 라우터 장비에 두는 경우
• 방화벽에 두는 경우
• MPLS 라우터 도입으로 IPSec지원 장비 주도에서 탈피해 MPLS VPN으로 옮겨간다.


전산직/정보직 대비 정보보호론

③ 사용자가 필요에 따라 자체적으로 보안성을 적용한 네트워크를 구축할 수 있다.
   IPSec이나 SSL/TLS 등의 보안 프로토콜을 네트워크 관리자의 구성이 아닌 사용자의 요구로 적용시킬 수 있다.
④ 이미 구축되어 있는 사설망과의 연결, 모바일 환경, 외부와의 보안 통신이 가능하여 추가적인 구축비용이 적다.
⑤ 중앙 관리를 통해 전체 네트워크에 대한 관리가 쉽다.
⑥ 인터넷이 연결된 곳이라면 동일한 사설망 내의 효과를 얻을 수 있다.

(3) 가상 사설망의 구현

1) 원격 접속(Remote Access) 방식
① 재택 근무자 및 이동 사용자 등과 같이 원격지에서 업무 서버 접근이 많은 경우
   적합한 VPN 구성 방식이다.
② 사용자는 PC 및 노트북에 VPN 클라이언트 제품을 설치한 후 자사 게이트웨이를
   통해 인증 단계를 거친 후 VPN 통신을 통해 자사 내의 서버와 접속한다.
③ PPTP, L2TP, IPSec, SSL 기술 등으로 구현 가능하다.

2) 인트라넷(Intranet) 방식
① 기업 내부를 LAN으로 연결하고 본사와 지사 간 또는 본사와 협력사 간 등산만
   그 지역에서 제공하는 인터넷 기반의 가상 사설망을 이용하여 접속하는 방식이다.
② IPSec, MPLS VPN 기술 등으로 구현 가능하다.

3) 엑스트라넷(Extranet) 방식
① 인트라넷 방식과 원격 접속 방식이 결합된 형태로 각각 접근하기 쉬운 인터넷
   망을 이용하여 하나의 형태로 묶는 방식이다.
② 서로 다른 네트워크 환경을 상호 연결시켜야 하므로 상호 연동을 위해 표준 보안
   프로토콜을 사용해야 한다.
③ IPSec, MPLS VPN 기술 등으로 구현 가능하다.

(4) 가상 사설망의 구현 기술

1) 터널링 기술

터널링은 사용자에게 투명한 통신 서비스를 제공하고 인터넷과 같은 안전하지 못한
네트워크 환경에서 강력한 보안을 제공한다.

① L2TP(Layer 2 Tunnel Protocol)
   ㉠ 마이크로 소프트 사의 PPTP(Point-to-Point Tunneling Protocol)는 원격지
      사용자와 로컬 네트워크 간 또는 로컬 네트워크와 로컬 네트워크 간의 2계층에서
      터널링 기능을 제공한다.

[가상 사설망의 구현 기술]
① 터널링 기술 : 전송망 환경에서 단대단(end-to-end)으로 회선을 연결한 것과 같은 효과를 위해 두 호스트 사이에 가상 경로를 설정해준다.
② 암호화/인증 기술 : 가상 경로를 다른 이용된 사용자들로부터 격리시켜 안전한 통로를 만들어준다.
③ 접근 제어 기술 : 가상 사설망 내의 자원에 대한 접근 통제를 통해 보안 정책을 구현한다.

L2TP
터널 인증 기술은 제공하나 패킷인증,
패킷 암호화, 기밀성은 제공하지 못한다.


PART 07

㉡ 시스코의 L2F(Layer 2 Forwarding)는 원격 호스트가 공중망을 통해 인트라넷에
   접속할 수 있는 기능을 제공한다.
㉢ PPTP와 L2F의 장점을 결합하여 만든 프로토콜이다.
㉣ 원격 접속 방식의 VPN을 구성하는데 사용되는 클라이언트/서버 기반 터널링
   프로토콜이다.

② IPsec
   ㉠ IPsec은 IP 계층에서의 암호화를 통하여 기존의 네트워크상에서 자신의 IP를
      숨기고 상대방에게 IPsec VPN을 통해서만 접속할 수 있는 기능을 제공한다.
   ㉡ IP계층 또는 그 상위 계층의 프로토콜을 보호하기 위해 IP계층에서의 기밀성,
      데이터 인증, 연결의 무결성을 제공한다.
   ㉢ IPsec은 원격접속 방식, 인트라넷, 엑스트라넷 방식 모두에 적용된다.

③ SOCKSv5
   ㉠ 상호간 인증을 거친 침입 차단 시스템간의 표준 프로토콜이다.
   ㉡ 강력한 접근 통제 특성으로 보안성이 매우 높은 가상사설망을 구현할 수 있다.
   ㉢ SOCKSv5는 OSI 5계층인 세션 계층에서 데이터의 흐름을 통제한다.

④ TLS(Transport Layer Security) VPN
   ㉠ IPsec VPN을 적용할 수 없는 구간에 사설 네트워크에 접속할 수 있는 방법을
      제공한다.
   ㉡ 전송 계층의 암호화를 통해 데이터를 전송한다.
   ㉢ TLS는 전용 애플리케이션을 사용하여 메시지를 암호화하고 복호화가 가능한
      애플리케이션만 메시지에 접근하게 하여 보안성을 높인다.

⑤ MPLS(Multi Protocol Label Switching) VPN
   ㉠ IP 기반 VPN에 비해 서비스 품질, 보안성, 신뢰성이 보장된 데이터 포워딩을
      제공하며 확장성이 뛰어나다.
   ㉡ 여러 지역에 분산되어 있는 인트라넷 사이트에 대한 관리가 편리해지며, 높은
      서비스 품질을 제공한다.

2) 암호화 기술
① 데이터 기밀성을 위해 암호화 기술을 사용한다.
② 대칭키 암호화 알고리즘으로는 DES, RC5, SEED, AES 등이 이용된다.
③ 공개키 암호화 알고리즘으로는 RSA, ElGamal 등이 이용된다.

[보충학습]
PPTP와 L2TP의 비교
① PPTP는 IP 기반 네트워크가 필요한 데 비해, L2TP는 X.25, Frame relay,
   ATM 네트워크 등 다양한 프로토콜 상에서부터 연결을 캡슐화할 수 있다.
② PPTP는 두 시스템 사이에 하나의 터널만 지원하는데 비해, L2TP는 여러 개의 터널을 허용한다.
③ PPTP는 암호화와 인증에 해당하는 기술이 없는데 비해, L2TP는 헤더 암호화와
   터널에 대한 인증 기능을 제공한다.

SOCKS(Socket Secure)
• 클라이언트/서버 환경에서 이용되는 프록시 접속 프로토콜
• 기업 내 네트워크의 클라이언트가 기업 외부의 웹 서버에 접근할 때 방화벽 기능을
  실현하는 프로토콜이다.
• 인증 처리에 의한 접근 제어 기능 포함
  시스템 관리자가 내부 사용자를 신뢰할 경우 일반적으로 사용

MPLS
• 데이터 패킷에 IP주소 대신 별도의 라벨을 붙여서 라우팅하고 라벨을 기반으로 하는
  데이터 전송 방식
• 패킷이 발생하면 기존 라우터 기반 백본에서는 IP를 보고 패킷을 전달했으나 MPLS
  네트워크에서는 2계층 기반의 라벨을 보고 스위칭한다.
• 다양한 프로토콜을 수용하므로 IP망, ATM, 프레임 릴레이에도 적용할 수 있다.
• 소프트웨어 기반 처리에서 하드웨어 기반 처리로 바꾸면서 고속 스위칭을 가능하게한다.
• MPLS은 다양한 프로토콜을 수용하기 때문에 IP망은 물론 ATM, 프레임 릴레이에도 적용할 수 있다.
• 각 네트워크에서 모든 트래픽을 융합해 단일 네트워크를 결합함으로써 운용비를 절감할 수 있다.

PART 07

06 IP 보안(IPSec)

(1) IP 보안(IPsec)

① IP 보안(IPsec)은 현재 사용 중인 인터넷 프로토콜(IPv4나 IPv6)에 추가적인 헤더를
   붙여서 보안 기능을 제공한다.
② IPsec은 인증, 기밀성과 키 관리 등 3개의 영역에서 활용될 수 있다.
③ 인증에서는 HMAC 메시지 인증 코드를 사용한다. 인증은 원래 IP 패킷 전체에
   적용할 수 있거나(터널 모드) IP 헤더를 제외한 나머지 부분에 적용(전송 모드)할
   수도 있다.
④ 캡슐화 보안 페이로드(ESP)라고 알려진 암호형식을 이용하여 기밀성을 제공한다.
   터널모드와 전송 모드 두 가지에 모두에 적용할 수 있다.
⑤ IKE는 여러 가지 키 관리 기술을 정의한다.

(2) IPsec 문서

IPsec은 인증, 비밀성, 키 관리의 3가지 기능 영역을 포함한다.

1) 구조(Architecture)
① IPsec 기술을 정의하는 일반적인 개념, 보안 요구사항, 정의 그리고 메커니즘을
   다루고 있다.
② 현재 명세는 RFC 2401, 인터넷 프로토콜을 위한 보안 구조(Security Architecture
   for the Internet Protocol)이다.

2) 인증 헤더(AH : Authentication Header)
① AH는 메시지 인증을 제공하는 확장 헤더이다.
② 현재 명세는 RFC 2402, IP 인증 헤더(IP Authentication Header)이다.

3) 캡슐화 보안 페이로드(ESP : Encapsulating Security Payload)
① ESP는 암호화 또는 암호화/인증의 결합을 제공하기 위해 사용되는 캡슐화 헤더와
   트레일러로 구성된다.
② 현재 명세는 RFC 2406, IP 캡슐화 보안 페이로드(IP Encapsulating Security
   Payload)이다.

4) 인터넷 키교환(IKE : Internet Key Exchange)
① IPsec 사용을 위한 키 관리를 기술하는 문서의 모임이다.
② 주요 명세는 RFC 2409, 인터넷 키 교환 프로토콜(Internet Key Exchange(IKEv2)
   Protocol)이지만 많은 관련 RFC 문서가 있다.


IPsec의 응용

① 인터넷을 통한 안전한 지사 사무실 연결 : 회사는 인터넷이나 공공 WAN을 통해
   안전한 가상사설망을 구축할 수 있다.
   이를 이용하면 인터넷을 적극적으로 사용하고, 사설망의 필요성을 줄여주고,
   비용절감과 네트워크 관리 부담을 줄일 수 있다.

② 인터넷을 통한 안전한 원격 접근 : IP 보안 프로토콜이 장착된 시스템을 사용하는
   중단 사용자는 인터넷 서비스 제공자(ISP : Internet service provider)로 시내
   전화를 걸어 회사 네트워크에 안전하게 접근할 수 있다.
   이를 이용하면 출장 중인 직원과 재택 근무자의 전화통신비용을 줄일 수 있다.

③ 협력업체와의 인트라넷과 엑스트라넷 구축 : IPsec을 이용하면 인증과 기밀성을
   보장할 수 있다. 키 교환 메커니즘을 제공하여 다른 기관과의 통신을 안전하게
   할 수 있다.

④ 전자상거래 보안 강화 : 웹 전자상거래 응용 프로그램에는 보안 프로토콜이 내장되어
   있어 IPsec을 사용하게 되면 보안성을 더 강화할 수 있다.

⑤ IPsec이 여러 응용을 지원할 수 있는 이유는 모든 트래픽에 대한 암호화와 인증을
   IP 계층에서 할 수 있는 기능을 갖고 있기 때문이다. 이로 인해 원격접속, 클라이언트/서버,
   전자메일, 파일 전송, 웹 접근 등을 포함하는 모든 응용이 안전하게 될 수 있다.

② 비연결 무결성(Connectionless integrity)
③ 데이터 발신처 인증(Data origin authentication)
④ 재전송 공격 거부(Rejection of replayed packets)

(4) IPsec의 보안 메커니즘

1) AH(Authentication Header)

① 인증 헤더 프로토콜(AH Protocol: Authentication Header Protocol)은 발신지 호스트를 인증하고 IP패킷으로 전달되는 페이로드의 무결성을 보장하기 위해 설계되었다.

② 메시지 다이제스트를 만들기 위해 해시함수와 대칭키를 사용하며 다이제스트는 인증 헤더에 삽입된다.

③ AH 구성 요소

IP 헤더
AH
Payload

Next Header
Payload Length
Reserved
Security Parameter Index(SPI)
Sequence Number Field
IP Authentication data

㉠ 다음 헤더(Next header) : 8비트로 IP 데이터그램에 의해 전달되는 페이로드의 유형을 정의한다(TCP, UDP, ICMP, 또는 OSPF).

㉡ 페이로드 길이(Payload length) : 8비트로 실제 페이로드의 길이를 정의하는 것이 아니라 인증 헤더의 길이를 4바이트 배수로 정의한 것이다.

㉢ 보안 매개변수 색인(Security parameter index) : 32비트로 가상회선 식별자의 역할을 하며 보안 연관이라는 연결 동안에 보내진 모든 패킷에 대해 동일하다.

㉣ 순서 번호(Sequence number) : 32비트로 데이터그램의 순서를 위한 순서 정보를 제공하여 재전송(playback)을 방지한다.

㉤ 인증 데이터(Authentication data) : IP 데이터그램에 해시 함수를 적용한 결과이다.

보충학습
보안 연관과 인터넷 키 교환

1. 보안 연관(SA : Security Association)
   당사자들이 AH 또는 ESP와 같은 서로 다른 프로토콜을 위한 특정 알고리즘과 특정
   매개변수들을 사용할 필요가 있을 때 필요한 데이터를 정하고 두 호스트 사이의 논리적
   관계를 설정한 것이다.

2. 인터넷 키 교환(IKE : Internet Key Exchange)
   내부적 및 외부적 보안 연관을 생성하기 위해 설계된 프로토콜이다.
   즉, IKE는 IPsec을 위한 SA를 생성하는 것이다.
   ISAKMP(Internet Security Association and Key Management Protocol)는 IKE에서
   정의된 교환을 실제로 실행하는 미국 국가 보안국(NSA)에 의해 설계된 프로토콜로
   IKE가 SA를 생성하기 위해 표준화되고 형식화된 메시지가 되도록 허용하는 여러 개의
   패킷, 프로토콜 및 매개변수를 정의한다.

3. 보안 연관 데이터베이스(SAD : Security Association Database)
   ① 각 사이트가 양방향 통신을 허용하기 위해 내부적과 외부적 SA를 모두 가져야 할
      필요가 있는 경우가 있다.
   ② SA들의 집합을 데이터베이스로 모아야 하며 이를 보안 연관 데이터베이스라 한다.
   ③ 외부적 SAD : 호스트가 IPsec 헤더를 전달해야 하는 패킷을 보내고자 할 때, 이
      호스트는 그 패킷에 보안을 적용하기 위한 정보를 찾기 위해 외부적 SAD에서 해당
      입력값을 찾아야 한다.
   ④ 내부적 SAD : 호스트가 IPsec 헤더를 전달하는 패킷을 수신할 때 그 호스트는 패킷에
      대한 보안을 확인하기 위해 내부적 SAD에서 해당 입력값을 찾아야 한다.

   ├────────┼────┼────┼─────┼──────┼────┼──────┼────┤
   │ <SPI, DA, P>                                         │
   └────────┴────┴────┴─────┴──────┴────┴──────┴────┘

   • DA : 목적지 주소

심화학습

ESM(Enterprise Security Management)

1. ESM(Enterprise Security Management : 통합보안관리)의 개요
   ① 네트워크를 통해 들어오는 모든 위험요소를 총체적으로 분석하여 미리 사전에 예방
      할 수 있도록 운영자에게 알려주는 시스템이다.
   ② 기능별, 제품별로 모듈화된 보안관리 기능을 통합하여 일관되고, 직관적인 관리자
      및 사용자 인터페이스를 제공하기 위한 개념으로 효율적이고 정책지향성의 체계적
      인 보안관리시스템을 구축하며, 표준 정책기반 하에 모든 시스템의 통합 보안관리를
      이용한 보안 관계의 효율성 제공하기 위한 솔루션이다.
   ③ 침입차단시스템(방화벽), 침입탐지시스템(IDS), 가상사설망(VPN), 안티바이러스
      등 다양한 종류의 보안 솔루션을 하나로 통합해 관리할 수 있다.

2. ESM의 필요성 및 도입 시 고려사항
   ① ESM의 필요성
      ㉠ 보안 시장이 다양해지고 세분화되고 전문화된 솔루션이 요구된다.
      ㉡ 분산된 네트워크 시스템과 보안 시스템의 통합 관리가 필요하다.
      ㉢ 침입차단, VPN, 침입탐지, 시스템 보안, 인증, 바이러스, 데이터 백업, 네트워크
         장비에 이르기까지 전문화되었다.
      ㉣ 시스템 관리 인력이 부족하고 관리 비용이 증가하였다.
      ㉤ 보안 솔루션 및 네트워크 솔루션간의 동적인 데이터 분배와 공유가 필요하다.
      ㉥ 일관된 보안 정책 수립을 통해 네트워크의 보안성이 강화된다.

   ② ESM의 도입 시 고려사항
      ㉠ 정책기반의 관리
      ㉡ 보안 제품과 네트워크 장비간의 연동성
      ㉢ 지원되는 Platform과 보안 제품 및 부수작용(성능, 부하 등) 최소화
      ㉣ ESM은 제품별로 강조되는 특징에 따라 우선적인 기능에 대한 기본적인 검토가
         필요하며 체계적인 위험요소 식별을 통한 적절한 위험 관리(Risk Management)의
         지원 여부를 검토한다.

3. ESM 시스템의 장점
   ① 모든 네트워크상의 보안시스템이 ESM으로 통합 관리된다.
   ② 관리 및 운영이 용이하고 정책 수립의 일관성을 유지한다.
   ③ 시스템 비용과 관리 비용이 절감된다.
   ④ 로그 수집 기능, 보안 정책 관리, 이벤트 분석 기능, 통합 보고서 기능, 보안 사고
      징후의 빠른 탐지가 가능하다.


안티바이러스
• 악성소프트웨어를 찾아내 제거한다.
• 악성코드, 바이러스, 피싱공격, 트로이목마, 웜 등도 검출한다.
• 바이러스 데이터베이스의 정의와 일치하는 바이러스를 확인하기 위해 파일의 내용을 살핀다.
• 감염으로 파괴될 가능성이 있는 컴퓨터 프로그램으로부터 의심행동을 찾는다.

ESM(통합보안관리)
• 통합관리수준을 벗어나 시스템 자원 관리, 네트워크 자원 관리 등 전사적 자원 관리 시스템까지 확대, 개발하고 있다.
• 기업들의 서로 다른 기종의 보안 솔루션 설치에 따른 중복 투자, 자원 낭비를 줄일 수 있다.

NAC(Network Access Control)
사용자 PC 및 네트워크 단말기가 네트워크에 접속하기 전에 보안 정책 준수 여부를 검사하여 네트워크 접속을 통제하는 기술

UTM(Unified Treat Management) :
통합 위협 관리
하나의 장비에 여러 가지 보안 기능을 탑재한 장비이다.
기존의 다양한 보안 솔루션 등의 보안 기능을 하나로 통합한 기술과 장비이다.

SIEM(Security Information event management)
실시간 위협탐지 및 대응을 위해 이벤트 로그 데이터를 실시간으로 수집하고 분석하는 기능을 가지고 있으며, 침해 공격 로그에 대한 포렌식과 법적 조사를 위한 해당 데이터의 신속한 검색 및 리포팅 기능도 제공한다.

심화학습

NAC(Network Access Control)

① 네트워크 접근제어 솔루션으로 물리적 엔드포인트(Endpoint) 단말기가 회사의 내부
   네트워크에 접속을 시도할 때 이를 제어하고 통제한다.

② NAC는 네트워크 제어 및 통제 기능을 통해 사내 네트워크가 바이러스나 웜 등의 보안
   위협으로부터 안전한 단말기들로 이루어지도록 강제하는 역할을 수행한다.

③ 사용자가 정상적인 사용자인지 인증 절차를 거치게 한다.

④ 인증 성공 후 접속을 시도하는 단말기 내에 백신 등이 제대로 설치되어 있는지 무결성을
   검증한다.

⑤ NAC는 사용자 인증을 수행하고 단말에 최신 패치 설치를 강제한다.
⑥ NAC 솔루션은 IP 관리 시스템에서 네트워크에 대한 통제 기능을 더욱 강화한 제품이다.

⑦ NAC는 네트워크에 대한 통제 기능과 관련하여 802.1x라는 네트워크 표준에 기반을
   두고 있다.

⑧ NAC를 구현하는 방식으로 각각의 단말기에 에이전트를 설치해야 하는 에이전트 방식
   과 에이전트가 필요없는 에이전트리스(Agent-less) 방식이 있다.


심화학습

제로 트러스트(Zero Trust) 인증

“그 무엇도 먼저 신뢰하지 않는. 항상 검증한다(Never Trust, Always Verify).”라는
철학을 바탕으로 한 현대적인 사이버·네트워크 보안 접근 방식

① 명시적 검증(Verify Explicitly) : 사용자 아이디와 비밀번호 뿐만 아니라 사용자의 신원
   (Identity), 접속 위치, 기기의 보안 상태(백신 구동 여부 등), 서비스나 데이터의 취약점
   등 사용 가능한 모든 데이터를 기반으로 안전하게 매번 검증한다.

② 최소 권한 부여(Use Least Privileged Access) : 인증에 성공하더라도 해당 사용자가
   ‘지금 당장 업무를 처리하는 데 꼭 필요한 최소한의 권한’만 기간을 한정하여 부여한다.

③ 침해 가정(Assume Breach) : 네트워크가 이미 해커에게 해킹당해 감염되었다고 가정하
   여 모든 세션을 암호화하고, 사용자 행위를 실시간으로 모니터링하여 평소와 다른 이상
   행동을 보이면 즉시 차단한다.



PART 08

웹 보안과 전자상거래 보안


01 웹 보안

(1) 웹 보안 개요

① 웹은 월드 와이드 웹(WWW : World Wide Web)의 줄임말로, 하이퍼 텍스트
   (hyper-text) 문서들이 인터넷을 통해 연결된 시스템을 의미한다.

② 월드 와이드 웹(WWW)은 다양한 형태의 데이터를 손쉽게 검색할 수 있으며 편리한
   사용자 인터페이스를 제공하는 웹 브라우저(Web Browser)로 인해 사용자가 증가
   하였다.

③ 웹을 통한 전자 출판, 인터넷 쇼핑, 인터넷 뱅킹 등 다양한 서비스가 제공되므로
   웹 보안의 필요성이 증가한다.

④ 보안 관점에서 훈련되지 않은 일반 사용자가 웹 기반 서비스를 자주 이용한다.
   이런 사용자는 발생할지도 모르는 보안상 위험이 있다는 것을 알 필요도 없고
   효과적인 방어대책에 대해 도구를 갖추거나 그것에 대한 지식을 가질 필요도 없다.

⑤ 웹상에서 발생하는 보안 문제는 기본적으로 TCP/IP와 웹 프로토콜인 HTTP가
   데이터에 대한 보안 서비스를 제공하지 아니함으로써 비롯된다.

⑥ 웹 서버, 웹 브라우저 및 호스트 등의 안전한 통신을 위해 웹 보안 프로토콜을
   사용한다.

웹 서버와 웹 브라우저 간의 통신

웹 서버는 서버에서 동작하는 프로그램으로, 웹 브라우저의 요청에 의해 HTML 문서를
보내준다.
웹 브라우저와 웹 서버 사이의 통신은 HTTP에 의해 수행된다.


(2) 웹 보안 요구사항

1) 시스템 보안

클라이언트와 서버 애플리케이션이 동작하는 시스템 자체의 보안을 의미한다.


2) 클라이언트 인증

서버의 정보에 접근하는 클라이언트를 식별한다.


3) 서버 인증

① 서비스 제공자의 인증을 의미한다.

② 인터넷은 서로를 직접 확인할 수 없는 공간이므로 주문서나 고문서와 같은 중요한
   정보를 교환하고자 할 때, 클라이언트 인증과 함께 서버 인증을 제공해야 한다.


4) 데이터의 기밀성 보장

TCP/IP 보안 취약성으로 인한 데이터 도청을 방지한다.


5) 데이터의 무결성 보장

TCP/IP 보안 취약성으로 인한 데이터의 변조를 방지한다.


6) 접근 제어

각각의 정보와 시스템에 대해 각 사용자별 접근 권한을 다르게 부여한다.

02 전자우편(이메일) 보안
(1) 전자우편 보안 개요

① 인터넷이 발전하면서 정보 교환을 위해 많이 사용되는 전자우편은 정보 교환을 많이 하기 때문에 보안상의 취약성을 갖는다.

② 보안 요구 사항은 기밀성, 메시지 인증, 사용자 인증, 송수신 부인방지, 메시지 재생 방지 등이다.

③ 대표적으로 PGP와 S/MIME, PEM 등이 있다.

④ 전자메일은 인터넷을 통한 웹 메일 뿐만 아니라 스마트폰의 모바일 기술 연계로 사용이 확대될 전망이다.

인터넷 메일 구조

[그림]

메시지 사용자 에이전트(MUA)

① 사용자 액터(actor)와 사용자 응용 대신에 동작한다.

② 보통 이 기능은 사용자 컴퓨터에 위치하고 클라이언트 이메일 프로그램 또는 로컬 네트워크 이메일 서버로 불린다.

③ 작성자 MUA는 메시지를 구성하고 MSA를 통해 MHS로 초기 제출을 수행한다.

④ 수신자 MUA는 저장하거나 수신측 사용자에게 디스플레이하기 위해 수신 메일을 처리한다.

메일 제출 에이전트(MSA : Mail Submission Agent)

① MUA에 의해 제출된 메시지를 받아들이고 호스팅 도메인의 정책과 인터넷 표준의 요구사항을 시행한다.



전자메일 보안

PGP는 소스가 공개되어 있으며, 무료로 사용할 수 있는 전자우편용 소프트웨어 패키지다. 디지털 서명을 이용하여 인증을 제공하고, 대칭 블록 암호를 이용해서 기밀성을 제공하고, ZIP 알고리즘을 이용해 압축을 제공하고, 기수 -64 부호화 시스템을 이용해 전자우편을 제공하며 길이가 긴 전자우편 데이터를 전송할 수 있도록 단편화와 조립을 제공한다.

PGP는 공개키 신뢰 모델과 공개키 인증서 관리를 개발하기 위해 여러 도구를 활용한다.

S/MIME은 전자우편 보안을 위한 인터넷 표준 프로토콜이며 PGP의 기능과 동일하다.

DKIM은 전자우편 제공자가 발신지 도메인을 대신하여 암호적으로 전자우편 메시지에 서명하기 위한 규약이다.

(2) PGP(Pretty Good Privacy)

1) PGP의 개요

① 필 짐머만(Phil Zimmermann)에 의해 1991년 제안된 전자우편용 보안 프로토콜이다.

② 인터넷에서 전달하는 전자메일을 다른 사람이 받아볼 수 없도록 암호화하고, 받은 전자메일의 암호를 해석해 주는 프로그램이다.

③ 윈도우즈, 유닉스, 매킨토시 등을 포함한 다양한 플랫폼에서 동작되는 여러 버전을 전 세계에 무료로 제공했다.

④ 매우 다양한 영역에 응용할 수 있다. 파일과 메시지 암호화 표준 구조를 설치한 뒤 그 강도를 실험해보고 싶은 기업체부터 인터넷이나 다른 네트워크를 통해 전 세계의 다른 사람과 안전하게 통신을 하고 싶어 하는 개인까지 그 응용 범위가 넓다.

⑤ 엄격하고 공개적인 검증을 거친 알고리즘을 기반으로 하고 있어서 매우 안전한 것으로 여겨진다.

⑥ 인증기관(CA)를 사용하지 않고 공개키의 인증을 사용자 개개인에게 일임하여 각 사용자에게 책임을 준다.


2) PGP의 특징

① 대칭 암호

㉠ 대칭 암호에 의한 암호화와 복호화를 지원한다.

㉡ 단독으로 대칭 암호를 사용할 수도 있고 하이브리드 암호 시스템의 부분으로 이용할 수도 있다.

AES, IDEA, CAST, 3-DES 등의 대칭 암호 알고리즘을 사용한다.


② 공개키 암호

㉠ 평문이 아닌 키를 암호화하는 데 사용하며 하이브리드 암호 시스템의 부분으로 이용된다.

㉡ RSA, ElGamal 등의 공개 키 암호 알고리즘을 사용한다.

③ 전자 서명

㉠ 전자 서명 작성과 검증을 지원한다.

㉡ RSA, DSA 등의 전자 서명 알고리즘을 사용한다.

④ 일방향 해시함수

㉠ 일방향 해시 함수를 이용하여 메시지의 해시 값을 계산한다.

㉡ MD5, SHA-1, RIPEMD-160 등의 일방향 해시 함수 알고리즘을 사용한다.

⑤ 압축

㉠ ZIP 형식을 이용하여 데이터의 압축을 수행한다.

㉡ 압축을 수행한 후 암호화를 함으로써 암호화된 결과를 가지고 평문을 추측하는 것을 어렵게 한다.

⑥ 텍스트 데이터

㉠ PGP는 2진 데이터와 텍스트 데이터의 상호 변환을 수행할 수 있다.

㉡ 2진 데이터를 첨부할 수 없는 메일 소프트웨어를 사용할 때라도 2진 데이터를 텍스트 데이터(ASCII radix-64 형식)로 변환함으로써 메시지를 메일로 보낼 수 있다.

⑦ 큰 파일의 분할과 결합

㉠ 하나의 파일을 여러 개의 파일로 분할하는 기능이 있다.

⑧ 키 고리의 관리

㉠ 자신이 생성한 키 쌍이나 입수한 공개키를 관리한다.

㉡ 키를 관리하는 파일을 키 링(key ring) 또는 키 고리라 한다.

심화학습

1. PGP의 기밀성(Confidentiality) 서비스
① 전송하거나 파일로 저장할 메시지를 암호화하는 방법으로 기밀성을 유지할 수 있다.
② 대칭 암호(CAST-128, IDEA, 3DES)를 사용하며 64비트-CFB 모드를 사용한다.
③ 일회용 키인 세션키를 사용하며, 이 키의 안전한 분배를 위해 수신자의 공개키로 이 키를 암호화한다.
④ 다음은 PGP에 의한 메시지 암호화와 복호화 과정이다.
   ㉠ 송신자는 메시지를 생성하고 이 메시지의 세션키로 사용할 128-비트 랜덤넘버를 생성한다.
   ㉡ CAST-128(혹은 IDEA나 3DES)과 세션키를 이용해 메시지를 암호화한다.
   ㉢ 수신자의 공개키를 이용해서 RSA로 세션키를 암호화한 다음 메시지에 붙인다.
   ㉣ 수신자는 자신의 개인키를 이용해 RSA로 복호화해서 세션키를 회수한다.
   ㉤ 수신자는 세션키를 이용해 메시지를 보호한다.


PGP의 기밀성과 인증

평문에 대한 서명을 생성해서 암호화한 메시지에 첨부한다.
대칭 암호 알고리즘 CAST-128(혹은 IDEA나 3DES)을 이용해서 암호화하고 세션키는 RSA(혹은 ElGamal)로 암호화한다.


PGP의 전자서명, 압축, 암호화 순서
① 전자서명 생성을 압축보다 먼저 한다.
② 암호적 보안성을 높이기 위해 압축을 먼저 하고 그 뒤에 메시지를 암호화한다. 
   압축된 데이터는 원래 평문보다 중복되는 비트가 적기 때문에 암호해독이 어렵다.


2. PGP에 의한 인증 서비스
① SHA-1과 RSA를 병행해서 사용하면 효과적인 전자서명 구조를 만들 수 있다.
② RSA의 강력한 보안성 때문에 수신자는 오직 공개키와 쌍을 이루는 개인키를 소유한 자만이 그 서명을 생성할 수 있다는 것을 확신할 수 있다.
③ SHA-1의 강력한 보안성으로 인해 수신자는 누구도 동일한 해시코드를 갖는 새 메시지를 만들 수 없다는 것을 확신할 수 있다.
④ 하나의 메시지에 기밀성과 인증 두 가지 서비스를 제공할 수 있다.
⑤ 다음은 해시함수를 이용한 전자서명 생성과 검증 과정이다.
   ㉠ 송신자가 메시지를 생성한다.
   ㉡ SHA-1을 이용해서 메시지로부터 160-비트 해시코드를 생성한다.
   ㉢ 이 해시코드를 송신자의 개인키를 이용한 RSA로 암호화하고 그 결과를 메시지에 붙인다.
   ㉣ 수신자는 수신메시지를 송신자의 공개키를 가지고 RSA로 복호화하여 해시코드를 회수한다.
   ㉤ 수신자는 메시지에 대한 해시코드를 새로 생성한 다음 단계 ㉣에서 회수한 해시코드와 비교한다. 만약 두 개가 일치하면 해당 메시지를 인증된 것으로 간주한다.


3. 압축(Compression)
① PGP는 서명 후 암호화하기 전에 메시지를 압축한다.
② 전자메일 전송과 파일 저장에 있어서 저장 공간을 줄일 수 있다.
③ 서명 생성은 압축되지 않은 메시지를 더 선호하므로 압축보다 먼저 수행한다.
④ 암호적 보안성을 높이기 위해 압축을 먼저 하고 메시지 암호화를 수행한다. 압축된 메시지는 원래 평문보다 중복되는 비트가 적기 때문에 암호해독이 어렵다.
⑤ ZIP 압축 알고리즘을 사용한다.


4. PGP의 키 링 구조
① 송수신자의 키 ID는 기밀성과 인증을 제공하는 모든 PGP 메시지에 포함된다.
② 개인키 링 : 사용자가 소유하는 공개/개인키 쌍을 저장한다.
③ 공개키 링 : 사용자에게 알려진 다른 사용자들의 공개키를 저장하므로 각 사용자에게 한 쌍의 자료 구조를 제공한다.
④ 공개키 링에 부정한 공개키가 포함되어 생기는 위협을 최소화하기 위한 대책으로 PGP는 신뢰 고리를 사용한다.


전자메일 호환성
• 기수-64(radix-64) 변환을 이용하면 3개의 옥텟으로 이루어진 2진 데이터 한 세트를 네 개의 ASCII 문자로 변환할 수 있다. 이 형식에는 전송오류를 탐지하기 위해서 CRC를 사용한다.
• 기수-64 변환을 사용하면 메시지 크기가 약 33% 정도 커지게 된다. 다행히 세션키와 메시지의 서명키 부분은 비교적 작고, 평문 메시지를 압축이 된 상태이다. 사실 압축을 했을 때 기수-64로 인해 늘어난 것보다 더 줄여줄 수 있어야만 한다.


단편화와 재조립
전자메일은 보통 최대 메시지 길이에 제약이 있다. 예를 들면, 인터넷을 통해 접속 할 수 있는 많은 메일서비스는 최대길이가 50,000옥텟으로 설정되어 있다. 이보다 더 긴 메시지는 작은 조각으로 잘라서 각각 보내야만 한다.


PGP의 기밀성과 인증
평문에 대한 서명을 생성해서 메시지에 첨부한다. 그 다음 평문 메시지와 서명을 대칭 암호 알고리즘 CAST-128(혹은 IDEA나 3DES)을 이용해서 암호화하고 세션키는 RSA(혹은 ElGamal)로 암호화한다.


PGP의 전자서명, 압축, 암호화 순서
① 전자서명 생성을 압축보다 먼저 한다.
② 암호적 보안성을 높이기 위해 압축을 먼저 하고 그 뒤에 메시지를 암호화한다. 압축된 메시지는 원래 평문보다 중복되는 비트가 적기 때문에 암호해독을 하기가 더 어려워진다.

1. PGP의 기밀성(Confidentiality) 서비스
① 전송하거나 파일로 저장할 메시지를 암호화하는 방법으로 기밀성을 유지할 수 있다.
② 대칭 암호(CAST-128, IDEA, 3DES)를 사용하며 64비트-CFB 모드를 사용한다.
③ 일회용 키인 세션키를 사용하며, 이 키의 안전한 분배를 위해 수신자의 공개키로 이 키를 암호화한다.
④ 다음은 PGP에 의한 메시지 암호화와 복호화 과정이다.
   ㉠ 송신자는 메시지를 생성하고 이 메시지의 세션키로 사용할 128-비트 랜덤넘버를 생성한다.
   ㉡ CAST-128(혹은 IDEA나 3DES)과 세션키를 이용해 메시지를 암호화한다.
   ㉢ 수신자의 공개키를 이용해서 RSA로 세션키를 암호화한 다음 메시지에 붙인다.
   ㉣ 수신자는 자신의 개인키를 이용해 RSA로 복호화해서 세션키를 회수한다.
   ㉤ 수신자는 세션키를 이용해 메시지를 보호한다.

2. PGP에 의한 인증 서비스
① SHA-1과 RSA를 병행해서 사용하면 효과적인 전자서명 구조를 만들 수 있다.
② RSA의 강력한 보안성 때문에 수신자는 오직 공개키와 쌍을 이루는 개인키를 소유한 자만이 그 서명을 생성할 수 있다는 것을 확신할 수 있다.
③ SHA-1의 강력한 보안성으로 인해 수신자는 누구도 동일한 해시코드를 갖는 새 메시지를 만들 수 없다는 것을 확신할 수 있다.

PGP의 키가 가져야 하는 3가지 필수사항
① 추측할 수 없는 세션키 생성방법이 필요하다.
② 사용자가 공개키/개인키 쌍을 여러 개 가질 수 있도록 하고 싶다. 사용자와 사용자 공개키 사이에 꼭 일대일 대응 관계가 성립하는 것은 아니다. 특정 키를 구별할 어떤 방법이 필요하다.
③ 각 PGP 사용자는 상대방의 공개키를 보관하는 파일뿐만 아니라 자신의 공개키/개인키 쌍을 보관하는 파일도 갖고 있어야 한다.


④ 하나의 메시지에 기밀성과 인증 두 가지 서비스를 제공할 수 있다.
⑤ 다음은 해시함수를 이용한 전자서명 생성과 검증 과정이다.
   ㉠ 송신자가 메시지를 생성한다.
   ㉡ SHA-1을 이용해서 메시지로부터 160-비트 해시코드를 생성한다.
   ㉢ 이 해시코드를 송신자의 개인키를 이용한 RSA로 암호화하고 그 결과를 메시지에 붙인다.
   ㉣ 수신자는 수신메시지를 송신자의 공개키를 가지고 RSA로 복호화하여 해시코드를 회수한다.
   ㉤ 수신자는 메시지에 대한 해시코드를 새로 생성한 다음 단계 ㉣에서 회수한 해시코드와 비교한다. 만약 두 개가 일치하면 해당 메시지를 인증된 것으로 간주한다.

3. 압축(Compression)
① PGP는 서명 후 암호화하기 전에 메시지를 압축한다.
② 전자메일 전송과 파일 저장에 있어서 저장 공간을 줄일 수 있다.
③ 서명 생성은 압축되지 않은 메시지를 더 선호하므로 압축보다 먼저 수행한다.
④ 암호적 보안성을 높이기 위해 압축을 먼저 하고 메시지 암호화를 수행한다. 압축된 메시지는 원래 평문보다 중복되는 비트가 적기 때문에 암호해독을 하기가 더 어려워진다.
⑤ ZIP 압축 알고리즘을 사용한다.

4. PGP의 키 링 구조
① 송수신자의 키 ID는 기밀성과 인증을 제공하는 모든 PGP 메시지에 포함된다.
② 개인키 링 : 사용자가 소유하는 공개/개인키 쌍을 저장한다.
③ 공개키 링 : 사용자에게 알려진 다른 사용자들의 공개키를 저장하므로 각 사용자에게 한 쌍의 자료 구조를 제공한다.
④ 공개키 링에 부정한 공개키가 포함되어 생기는 위협을 최소화하기 위한 대책으로 PGP는 신뢰 고리를 사용한다.


• 개인키 링 테이블

UserID    KeyID    공개키    암호화된 개인키    timestamp

① UserID : 사용자의 전자우편 주소
② KeyID : 사용자의 공개키 중 64비트를 추출하여 공개키를 유일하게 표현한다.
③ 공개키 : 전자우편 주소에 따른 각 공개키를 저장한다.
④ 암호화된 개인키 : 개인키의 암호화된 값을 나타낸다. 패스워드를 이용한다.
⑤ timestamp : 키 쌍을 생성한 날짜와 시간을 유지한다. 오래된 쌍을 제거하거나 새로운
   쌍을 생성할 때 사용된다.


• 공개키 링 테이블

UserID    KeyID    공개키    생성자 신뢰    인증서    인증서 신뢰    키 적법성    timestamp

① UserID : 전자우편 주소이다.
② KeyID : 공개키의 첫 번째 64비트이다.
③ 공개키 : 개체의 공개키이다.
④ 생성자 신뢰(Producer Trust) : 생성자 신뢰 등급을 정의한다. (None, Partial, Full)
⑤ 인증서(Certificate) : 개체가 다른 개체의 공개키에 인증서를 유지한다.
⑥ 인증서 신뢰(Certificate Trust) : 인증서 신뢰를 나타낸다.
⑦ 키 적법성(Key Legitimacy) : 각각의 인증서 신뢰에 대하여 미리 정의된 중요도와 인증서
   신뢰의 값을 기반으로 한다.
⑧ timestamp : 공개키 링 테이블에 포함된 날짜와 시간을 유지한다.


5. PGP의 공개키 신뢰 구조
① PGP는 인증기관을 구성하는 것이나 신뢰를 구축하는 것에 대한 규율 같은 것은
   없지만, 신뢰를 이용하는 법, 신뢰와 공개키를 연관시키는 법, 신뢰 정보를 이용하는
   방법을 제공하고 있다.
② PGP는 인증기관(CA)을 가지고 있지 않지만 신뢰를 사용하고 신뢰를 공개키와 연관
   시키고 신뢰 정보를 활용하는 편리한 수단을 제공한다.


• PGP의 신뢰 고리

① A는 B의 공개키에 서명한다.
② A와 C, D는 서로 잘 알고 있으며, 공개키가 틀림없이 본인 것이라는 것을 알고 있다.
③ C, D는 잘 모르는 B의 공개키를 처음 수신한 B의 것으로 신뢰 여부를 결정할 수 없다.
   이때 A의 서명으로 이 공개키는 틀림없이 B의 것이라고 신뢰하게 된다.

(3) S/MIME(Secure / Multi Purpose Internet Mail Extension)

1) S/MIME 개요
① S/MIME은 RSA 데이터 보안 기술을 이용해 MIME 인터넷 전자메일 형식 표준을
   보안적으로 강화시킨 것이다.
② PGP의 단점인 낮은 보안성과 기존 시스템과의 통합의 어려움을 보완하기 위해
   IETF의 작업 그룹에서 RSA-DSI(RSA Data Security Incorporation)의 기술을
   기반으로 개발된 전자 우편 보안 시스템이다.

2) S/MIME 기능
① 메시지에 대해 송수신자에게 전자우편 보안 서비스를 제공할 뿐만 아니라 MIME
   객체를 전송할 수 있는 모든 프로토콜에서 보안 서비스를 이용할 수 있게 한다.
② S/MIME이 제공하는 보안 서비스에는 메시지에 대한 기밀성, 무결성, 사용자 인증,
   송신 사실 부인 방지가 포함된다.
③ 봉함된 데이터(Enveloped data) : 암호화된 임의 유형의 암호화된 내용과 하나
   또는 여러 수신자를 위해 암호화된 내용 암호키로 구성된다.
④ 서명된 데이터(Signed data) : 서명될 내용의 메시지 다이제스트를 구하고 서명자의
   개인키로 그것을 암호화해서 전자서명을 생성한다. 서명된 데이터 메시지는
   S/MIME 기능을 갖춘 수신자만이 볼 수 있다.
⑤ 명문-서명 데이터(Clear-signed data) : 서명된 데이터로서 내용에 대한 전자서명
   을 한다. 전자서명만 base64로 부호화하고 내용은 부호화하지 않는다. S/MIME 기능
   이 없는 수신자가 서명을 검증할 수는 없지만 내용을 볼 수는 있다.
⑥ 서명되고 봉함된 데이터(Signed and enveloped data) : 서명만 되거나 암호화된
   개체는 중첩될 수 있다. 그러므로 암호화된 데이터는 서명될 수 있고, 서명된 데이터나
   명문-서명 데이터는 암호화될 수 있다.


S/MIME이 제공하는 보안 서비스

보안 서비스          보안 메커니즘          암호 알고리즘
메시지 기밀성        암호화                Triple-DES
메시지 무결성        해시함수              SHA-1
사용자 인증          공개키 인증           X.509 V3인증서
송신 부인 방지       전자서명              DSA


3) S/MIME 인증서 처리

① PGP와 달리 사용되는 공개키는 X.509 버전 3 규정을 준수하여 공개키 인증서를
   사용한다.

② S/MIME에서 사용하는 키 관리 시스템은 X.509 원래의 인증서 계층구조와 PGP의
   웹 형태 신뢰구조를 혼합한 형태이다.

③ PGP처럼 S/MIME 관리자와 사용자는 각 클라이언트에게 신뢰할 수 있는 키 목록과
   인증서 취소 목록을 제공하여 클라이언트를 구성해야 한다.

④ 수신된 서명을 확인하고 송신될 메시지를 암호화하는 데 쓸 인증서를 유지, 관리할
   책임은 S/MIME을 사용하는 당사자에 있다.

⑤ 단, 인증서는 인증기관에서 서명한다.


(4) PEM(Privacy Enhanced Mail)

① 인터넷 표준안으로 IETF에서 만든 암호화 기법이다.

② 이진 데이터를 6비트씩 분할하여 아스키 문자로 변환하는 Base64 변환 방식을
   사용한다.

③ 특징

   ㉠ 자동 암호화로 전송 중 유출되더라도 내용 확인이 불가능하다.

   ㉡ PGP에 비해 보안능력이 뛰어나다.

   ㉢ 중앙 집중식 키 인증방식으로 대중적으로 사용되기는 어렵다.


MIME(Multipurpose Internet Mail Extensions)

• SMTP는 실행 파일이나 이진 데이터를 전송하지 못한다.
• SMTP는 국제 언어문자를 포함하는 문서데이터를 전송하지 못한다.
• SMTP는 7비트 ASCII에 국한되어 사용된다.
• SMTP 서버는 특정 크기 이상되는 메일메시지를 처리하지 못하고 거부한다.

03 SSL / TLS 전송 계층 보안

[보충학습]
전송 레벨 보안

1. 안전 소켓 계층(SSL)은 TCP와 TCP를 사용하는 응용 사이에 보안 서비스를 제공한다.
   인터넷 표준 버전은 전송 계층 보안(TLS)이라고 부른다.

2. SSL/TLS는 대칭 암호를 이용해서 기밀성을 제공하고 메시지 인증 코드를 이용해서
   메시지 무결성을 제공한다.

3. SSL/TLS는 두 TCP 사용자로 하여금 그들이 사용할 보안 메커니즘과 보안 서비스를
   결정하도록 하는 프로토콜 메커니즘이 포함되어 있다.

4. HTTPS(SSL위의 HTTP)는 HTTP와 SSL을 합친 것으로서 웹브라우저와 웹서버 사이에
   안전 통신을 구현한다.

5. 안전한 전자거래(SET)는 인터넷상의 신용카드 거래를 보호하기 위해서 사용되는
   개방된 암호 보안 명세이다.


(1) SSL 개요

① SSL/TLS 프로토콜은 인터넷상에서 비밀 통신을 제공하기 위해 제안되었다.

② 도청과 위조로부터 안전하게 데이터를 전송하기 위해 TCP/IP 계층과 응용 계층
   (application layer) 사이에 위치한다.

③ 계층 사이에 위치하는 프로토콜이므로 기존의 프로토콜에 대한 영향을 최소화
   할 수 있다.

④ 다양한 응용 계층의 프로토콜이 SSL/TLS를 이용하여 보안 기능을 수행할 수 있게
   된다.

⑤ 클라이언트와 서버 인증, 무결성 검사, 압축 및 암호화를 제공하는 보안 프로토콜
   이다.

⑥ 넷스케이프(netscape) 사에서 1994년 처음 제안되었다.

⑦ TCP/IP 계층과 응용 계층 사이에 위치하여 종단 간 보안 서비스를 제공한다.

연결(Connection)
연결이란 전송 서비스를 제공하는 전송(OSI 계층 모델의 정의)을 말한다.
SSL의 연결은 대등 대 대등 관계이다.
연결은 일시적이다. 모든 연결은 한 개의 세션과 연관된다.

세션(Session)
실제로 통신이 이루어지는 단위는 연결이고 하나의 세션 안에 여러 개의 연결이 포함된다.
한 SSL 세션이란 한 클라이언트와 한 서버 사이의 연결을 말한다.
세션을 시작하려면 핸드셰이크 프로토콜을 이용해야 한다.
세션은 다수의 클라이언트가 공유하는 암호적 보안 매개변수를 정의한다.
각 연결마다 해야 하는 새 보안 매개변수 협상을 피하기 위해 세션을 사용한다.

① SSL은 신뢰할 수 있는 중단-대-중단의 안전한 서비스를 제공하기 위해 TCP를 사용하도록 설계하였다.
② SSL은 단 하나의 프로토콜로 이루어진 것이 아니라 두 계층의 프로토콜로 이루어졌다.

③ SSL 레코드 프로토콜은 다양한 상위-계층 프로토콜에 기본적인 보안 서비스를 제공한다. 특히 웹 클라이언트/서버 상호교환을 위해 전송 서비스를 제공하는 HTTP(Hypertext Transfer Protocol)는 SSL 위에서 작동할 수 있다.
④ 3개의 상위-계층 프로토콜을 SSL의 일부로 정의하는데 이 3가지는 핸드셰이크(Handshake) 프로토콜, 암호 사양 변경(Change Cipher Spec) 프로토콜 그리고 경고(Alert) 프로토콜이다.

1) 핸드셰이크 프로토콜
① 핸드셰이크 프로토콜을 이용해서 서버와 클라이언트가 서로를 인증하고 암호화 MAC 알고리즘 그리고 SSL 레코드 안에 보낸 데이터를 보호하는 데 사용할 암호키를 협상할 수 있다.
② 핸드셰이크 프로토콜은 모든 응용 데이터를 전송하기 이전에 사용한다.
③ 핸드셰이크 프로토콜을 사용하여 클라이언트와 서버가 합의를 한 후 서로 신호를 전달해서 암호 변경을 수행한다.

SSL과 TLS
• SSL(Secure Socket Layer) :
  안전 소켓 계층
• TLS(Transport Layer Security) :
  전송 계층 보안

HTTP(HyperText Transfer Protocol)
WWW상에서 정보를 주고받을 수 있는 프로토콜이다.
주로 HTML 문서를 주고받는 데 사용된다.
주로 TCP를 사용하고 HTTP/3부터는 UDP를 사용하며, 80번 포트를 사용한다.
HTTP는 클라이언트와 서버 사이에 이루어지는 요청/응답(request/response) 프로토콜이다.
HTTP를 통해 전달되는 자료는 http:로 시작하는 URL(인터넷 주소)로 조회할 수 있다.
HTTP는 상태를 저장하지 않는다.
(Stateless)
전자상거래 장바구니처럼, 일관된 방식으로 사용자가 페이지와 상호작용하려면 매 문제가 될 수 있다. 이를 위해 HTTP 쿠키를 사용하여 상태가 있는 세션을 만들도록 한다.

2) 암호 사양 변경 프로토콜(Change Cipher Spec Protocol)
① 암호 방법을 변경하는 신호를 통신 상대에게 전한다.
② 핸드셰이크 프로토콜에 의해 협상된 압축, MAC, 암호화 방식이 이후부터 적용됨을 상대방에게 알려주는 프로토콜이다.

3) 경고 프로토콜(Alert Protocol)
① 경고 프로토콜은 대등 개체에게 SSL-관련 경고를 할 때 사용한다.
② 핸드셰이크 과정에서 상대방이 제시한 암호화 방식을 지원할 수 없는 경우 등에 대한 오류 정보를 상대방에게 알릴 때 사용되는 프로토콜이다.

4) SSL 레코드 프로토콜
① SSL 연결을 위해 기밀성과 메시지 무결성 서비스를 제공한다.
   ㉠ 기밀성(Confidentiality)을 제공하기 위해 핸드셰이크 프로토콜은 SSL 페이로드를 관용 암호화하는데 대칭키를 정의한다.
   ㉡ 메시지 무결성(Message Integrity)을 제공하기 위해 핸드셰이크 프로토콜은 메시지 인증 코드(MAC)를 생성하는 데 사용할 대칭키를 정의한다.
② SSL 레코드 프로토콜의 동작은 다음과 같다.
   ㉠ 단편화(fragmentation) : 각 상위 계층 메시지는 214 바이트나 이보다 작은 블록으로 단편화한다.
   ㉡ 압축(compression) : 압축으로 인해 손실되는 것이 없어야 한다.
   ㉢ 메시지 인증 코드(MAC) 생성 추가 : 대칭키를 이용하여 메시지 인증 코드를 생성하고 추가한다.
   ㉣ 암호화(encryption) : 압축된 메시지와 MAC를 대칭 암호로 암호화한다.
   ㉤ SSL 레코드 헤더 추가

경고 프로토콜
이 프로토콜 안의 각 메시지는 2바이트로 구성된다. 첫 번째 바이트는 메시지의 엄밀성을 전달하기 위해 경고(warning) 혹은 심각도(fatal)라는 2가지 값을 갖는다. 만일 레벨이 심각(fatal)이라면, SSL은 즉시 연결을 단절한다. 동일한 세션 중의 다른 연결은 계속될 수 있지만 이 세션에서 어떤 새로운 연결을 설정하지는 못한다. 두 번째 바이트에는 특정 경고를 나타내는 코드가 들어있다.

SSL 레코드 프로토콜 헤더 구성요소
① 콘텐츠 유형(Content Type)(8비트)
포함된 단편을 처리할 때 사용하는 상위 계층 프로토콜이다.
② 주 버전(Major Version)(8비트)
사용 중인 SSL의 주 버전을 나타낸다. SSLv3에 대한 필드 값은 30이다.
③ 부 버전(Minor Version)(8비트)
사용 중인 서버버전을 나타낸다. SSLv3에 대한 필드 값은 0이다.
④ 압축된 길이(Compressed Length)(16비트)
평문 단편(혹은 압축을 했다면 압축된 단편)의 바이트 길이로 최대 값은 2¹⁴ + 2048이다.


















마스터 비밀(master secret)
• 마스터 비밀은 TLS의 클라이언트와 서버가 합의한 비밀값이다.
• 사전 마스터 비밀(premaster secret), 클라이언트 랜덤, 서버 랜덤을 기초로 클라이언트에서 비밀키가 각각 계산된다.
① RSA 공개키 암호를 이용하는 경우 :
   클라이언트가 ClientKeyExchange 메시지를 보낼 때 암호화된 사전 마스터 비밀을 함께 보낸다.
② Diffie-Hellman 키 교환을 이용하는 경우 : 클라이언트가 ClientKeyExchange 메시지를 보낼 때 DH 공개값을 함께 보낸다.
   이 값을 기초로 클라이언트와 서버가 사전 마스터 비밀을 만든다.
• 클라이언트 랜덤과 서버 랜덤은 공격자가 사전키를 계산할 수 없도록 하기 위한 솔트 역할을 한다.
• 사전 마스터 비밀로부터 마스터 비밀을 계산할 때는 2개의 일방향 해시함수를 조합해서 만든 의사난수 생성기를 이용한다.

1. 단계 1 : 보안설정 단계
① 이 단계는 논리적 연결을 시작하고 이 연결과 연관된 보안 기능을 설정하는데 사용된다.
② client_hello : 클라이언트는 버전, 랜덤, 세션ID, 암호도구, 압축 방법 등이 포함된 메시지를 서버에게 전송한다.
③ server_hello : 클라이언트는 서버로부터 서버가 선택한 버전, 서버가 생성한 랜덤넘버, 클라이언트가 제안한 것 중 서버가 선택한 암호도구, 압축 방법을 포함한 메시지를 받는다.

2. 단계 2 : 서버 인증과 키 교환
① certificate : 서버는 인증할 필요가 있으면 자신의 인증서를 보내는 것으로 이 단계를 시작한다.
② server_key_exchange : 서버가 필요하다고 생각되면 키 교환을 보낸다.
③ certificate_request : 클라이언트의 인증서를 요청한다.
④ server_hello_done : hello 메시지 단계를 끝내고 서버는 클라이언트의 응답을 기다린다.

3. 단계 3 : 클라이언트 인증과 키 교환
① certificate : 요청이 있었다면 클라이언트는 요청된 인증서를 보낸다.
② client_key_exchange : 클라이언트는 키 교환을 보낸다.
③ certificate_verify : 클라이언트는 서버가 확실한 인증서를 제공했는지 확인한다.

4. 단계 4 : 종료
① change-cipher-spec : 안전한 연결 설정을 완성하는 단계이다.
② finished : 핸드셰이크 프로토콜을 종료한다.


(3) SSL 보안 서비스

① 기밀성 서비스
   ㉠ DES, RC4, IDEA, 3DES 등과 같은 대칭키 암호화 알고리즘을 사용하여 제공된다.
   ㉡ 기밀성 서비스를 제공하기 위해 사용되는 대칭키는 핸드셰이크 프로토콜에 의해 생성된다.
   ㉢ SSL에서는 전자 서명과 키 교환을 위해 RSA 또는 DH 알고리즘을 이용할 수 있고 기밀성을 필요로 하는 다수의 애플리케이션 각각에 대해 다양한 암호 알고리즘을 제공할 수 있다.

② 메시지 무결성 서비스
   ㉠ 안전한 해시 알고리즘을 사용하여 메시지 인증 코드(MAC)를 만들어 메시지에 포함한다. 메시지가 변경되지 않음을 보장한다.
   ㉡ MAC(Message Authentication Code)은 내부적으로 누군가 데이터 전송을 방해할 수 없도록 하거나 재전송 공격에 이용할 수 없도록 데이터의 무결성을 제공한다.

③ 클라이언트와 서버 상호 인증
   ㉠ 연결 설정 과정에서 서로 간에 신뢰할 수 있도록 인증을 사용한다.
   ㉡ RSA와 같은 공개키 암호 알고리즘을 통해 인증할 수 있다.
   ㉢ DSS와 같은 전자 서명 알고리즘을 통해 인증할 수 있다.
   ㉣ X.509 공개키 인증서를 통해 인증할 수 있다.

서버/클라이언트 키 교환 방법
• RSA : RSA 암호화/복호화 공개키 인증서를 보낸다.
• Anonymous DH : Certificate 메시지가 없다. 서버/클라이언트의 DH 매개변수가 서로 간에 의해 서명된 절반-키를 보낸다.
• Ephemeral DH : 서버/클라이언트가 RSA 또는 DSS 디지털 서명 인증서를 보낸다.
• Fixed DH : 서버/클라이언트는 등록된 DH 절반키를 포함한 RSA 또는 DSS 디지털 서명 인증서를 보낸다.

SSL/TLS 인증서
SSL/TLS에서는 인증서로 서버로 인증할 수 있다.
통신 상대의 인증기관(CA)이 확인한 서버임에 틀림없다는 의미이며 인증서는 바라지만 요청하는 상대는 반드시 신뢰할 수 있는 것은 아니다.

Heartbeat 프로토콜

OpenSSL의 Heartbeat 프로토콜은 원래 TLS/DTLS 연결의 생존 여부를 확인하기 위한
확장 기능이다.
RFC 6520에 정의된 TLS/DTLS 확장 규격이다.
클라이언트와 서버가 연결을 유지하고 있는지 확인하기 위해 Heartbeat 요청 메시지를
주고받는다.
클라이언트는 임의의 데이터를 포함한 메시지를 서버에 보내고, 서버는 그 데이터를 그대로
돌려주는 방식이다.

Heartbleed 취약점(CVE-2014-0160)

OpenSSL 1.0.1~1.0.1f 버전에서 클라이언트가 보낸 데이터의 길이를 제대로 검증하지
않고 그대로 응답한 취약점이다. 이로 인해 서버의 민감한 정보(비밀번호, 세션 쿠키, 개인
키 등)가 유출될 수 있었다.

TLS

TLS는 SSL을 인터넷 표준 버전이 되도록 만든 IETF 표준이다. TLS는 RFC2246로 제안된
인터넷 표준(Proposed Internet Standard)으로 정의되었다.

1. 데이터 확장 함수(data-expansion function)
• 비밀(secret)을 보다 길게 확장하기 위해 미리 정의된 HMAC(MD5 또는 SHA-1)을
  사용한다.
• 각 섹션은 비밀과 종자(seed)인 두 개의 HMAC을 이용한다.

             Expanded secret

       Hash  Hash  Hash  ...
         Expanded secret


2. 의사난수 함수(pseudorandom function)
• MD5 또는 SHA-1을 사용하여 2개의 데이터 확장함수의 결합이 되도록 정의한다.
• 의사난수 함수의 입력은 비밀(secret), 레이블(label), 종자(seed)이다.
• 레이블과 종자는 연결되어 있으며, 각 데이터 확장 함수를 위한 종자로 이용된다.
• 비밀은 2개의 절반(Half-secret)으로 나누는데, 각 절반은 각 데이터 확장 함수의
  비밀로 사용된다.

• 2개의 데이터 확장 함수의 출력은 최종적으로 확장된 비밀을 생성하기 위하여 서로
  배타적이 된다.

4. 마스터 비밀
• TLS는 사전 마스터 비밀로부터 마스터 비밀(master secret)을 생성하기 위해 의사난수

DTLS(Datagram Transport Layer Security)

DTLS는 TLS(Transport Layer Security)를 기반으로 한 보안 프로토콜로, UDP와 같은
비연결형 전송 방식에서도 TLS 수준의 보안을 제공하기 위해 설계되었다.

① TLS 기반 : DTLS는 TLS의 구조와 기능을 거의 그대로 유지하면서, 데이터그램 환경
   (UDP 등)에 맞게 조정된 버전이다.
② UDP 지원 : TCP처럼 연결을 유지하지 않는 UDP에서도 암호화, 무결성, 인증 등을 보장
   한다.
③ 패킷 손실 및 재전달 대응 : UDP는 패킷 손실이나 순서 변경이 발생할 수 있기 때문에,
   DTLS는 이를 감지하고 처리할 수 있는 메커니즘을 포함하고 있다.
④ 암호화 및 인증 : TLS와 동일한 수준의 대칭키 암호화, 공개키 기반 인증, 메시지 무결성
   검증을 제공한다.
⑤ 핸드셰이크 신뢰성 보장 : UDP는 신뢰성이 없기 때문에, DTLS는 핸드셰이크 메시지를
   재전송하거나 단편을 재조립하는 기능을 갖고 있다.
⑥ 재생 공격 방지 : 시퀀스 번호와 윈도우 기반의 재생 탐지 기능을 통해 동일한 메시지의
   반복 전송을 방지한다.
⑦ WebRTC, VPN, IoT 기기 통신 등에서 사용된다.

WTLS (Wireless Transport Layer Security)

WTLS는 무선 환경에서 TLS(Transport Layer Security)의 기능을 제공하기 위해 설계된
보안 프로토콜로 주로 WAP(Wireless Application Protocol) 기반의 모바일 기기에서
사용되었다.

① TLS 기반 : WTLS는 TLS를 무선 환경에 맞게 경량화한 버전으로 TLS의 암호화, 인증,
   무결성 보장 기능을 유지하면서도, 낮은 대역폭과 제한된 처리 능력을 고려해 최적화
   되었다.
② UDP/IP 지원 : 무선 네트워크에서 흔히 쓰이는 비연결형 전송 방식(UDP)을 지원한다.
③ 인증서 경량화 : X.509 인증서 외에도 WTLS 전용 인증서 포맷을 사용해 데이터 크기를
   줄였다.
④ 암호화 : 데이터 도청 방지
⑤ 무결성 검증 : 메시지 변조 방지
⑥ 상호 인증 : 클라이언트와 서버 간 신뢰 확보

05 SSH(Secure Shell)

(1) SSH의 개요

① 원격에서 Telnet이나 FTP 등을 이용하여 리눅스/유닉스나 윈도우 시스템에 접근하는 경우 스니핑을 통해 사용자 ID와 암호가 유출될 수 있다.

② 스니핑으로부터 보안 위험을 막기 위해 암호화된 통신 프로토콜을 이용하여 원격에서 접근한다. 이런 암호화된 접근 방식의 대표적인 예가 SSH(Secure Shell)이다.

③ SSH(Secure Shell)은 비교적 쉽게 구현할 수 있고 적은 비용으로 설계한 안전한 네트워크 통신용 프로토콜이다.

④ Telnet이나 보안을 제공하지 않는 다른 원격 로그온 방식을 대체하기 위해 초기 버전의 SSH는 안전한 원격 로그온 기능을 제공하는 데 중점을 두고 개발하였다.

⑤ SSH는 보다 일반적인 클라이언트/서버 기능을 제공하며 파일 전송이나 전자메일 같은 네트워크 기능을 제공할 수 있다.

⑥ SSH2는 IETF RFC 4250부터 4256 문서에 표준으로 제안되었다.

⑦ SSH 클라이언트와 서버 응용은 대부분의 운영체제에서 광범위하게 사용되고 있다.


(2) SSH 구성 프로토콜

SSH는 TCP 상에서 일반적으로 수행되는 3개의 프로토콜로 구성된다.

① 전송 계층 프로토콜(Transport Layer Protocol) : 전방향 기밀(forward Secrecy, 한 세션에서 세션키나 영구 개인키가 손상되더라도 이것은 이전 세션의 기밀성에 영향을 미치지 않는다)을 만족하는 서버 인증, 데이터 기밀성과 데이터 무결성을 제공한다. 전송 계층에서는 옵션으로서 압축을 할 수 있다.

② 사용자 인증 프로토콜(User Authentication Protocol) : 서버에게 사용자를 인증한다.

③ 연결 프로토콜(Connection Protocol) : 하나의 기본 SSH 연결을 사용하여 여러 개의 논리적 통신 채널을 다중화(multiplex)한다.

비밀키가 노출되더라도 그 후의 키 분배 과정에서 얻은 세션키의 안전성에는 영향을 미치지 않는 암호학적 성질. 디피-헬만 알고리즘이 응용되는 것으로, 새로운 키 정보가 수학적으로 예전의 키 정보와 연결되지 않기 때문에 누군가 예전 세션 키를 탐지하더라도 그 키를 사용해서 새로운 세션 키를 추측할 수 없다.


(3) FTP

1) 개요

① FTP는 파일 전송을 위한 가장 기본 프로토콜로, RFC 1140로 1971년에 만들어졌다.

② FTP는 대화형으로 클라이언트와 서버가 통신이 가능하다.
   사용자가 원격 컴퓨터의 디렉터리에 파일 목록을 문의할 수 있고, 명령어 사용법을
   대화식으로 배울 수 있다.

③ 전송되는 파일의 형식을 지정할 수 있다.
   사용 가능한 파일 형식은 텍스트나 바이너리 파일이고, 텍스트 파일은 ASCII나
   EBCDIC 문자로 저장할 수 있다.

④ FTP에서는 파일 전송 전에 먼저 서버에 로그인해야 하며, 사용자는 로그인 이름과
   패스워드를 입력하여 클라이언트를 인증한다.

⑤ 서버는 클라이언트가 검증된 사용자가 아닌 경우 파일 전송을 거부할 수 있으며,
   텔넷과 유사하게 여러 클라이언트가 동시에 서버에 접근할 수 있다.

⑥ 제어 연결을 위해 21번 포트를 사용하고 데이터 연결을 위해 20번 포트를 사용한다.


2) FTP 능동적(Active) 모드

① active 모드는 클라이언트에서 서버측 21번 포트로 접속시도 하고 데이터 포트는
   서버에서 클라이언트로 접속 하여 데이터를 보내는 방식이다.

① 클라이언트에서 서버의 21번 포트로 접속 후 클라이언트가 사용할 두 번째 포트를 서버에
   알려준다.
② 서버는 이에 대해 ack로 응답하고
③ 서버의 20번 포트는 클라이언트가 알려준 두 번째 포트로 접속을 시도한다.
④ 마지막으로 클라이언트가 ack로 응답한다.


② 일반적인 TCP/IP의 특징인 '클라이언트가 서버에 접속을 시도하는 것'이 아니라
   '서버가 클라이언트에 접속을 시도한다'이기 때문에 만약 클라이언트 PC 등에 방화벽이
   설치되어 있거나 FTP를 잘 이해하지 못하는 공유기 등을 사용하여 외부에서의 접속을
   허용하지 않는다면 세 번째 프로세스가 작동하지 않게 되어 FTP 접속이 제대로 되지
   않는 문제점이 있다. 이러한 경우 FTP 접속은 되지만 이후 데이터 목록을 받아오지
   못하여 에러가 발생하게 된다.


3) FTP 수동적(Passive) 모드

① passive 모드는 클라이언트에서 서버측 21번 포트로 접속 시도 하고 데이터 포트도
   클라이언트에서 서버의 포트로 접속하여 데이터를 받아오는 방식이다.

① 먼저 클라이언트가 command 포트로 접속을 시도하면
② 서버에서는 서버가 사용할 두 번째 포트를 알려준다.
③ 클라이언트는 다른 포트를 열어 서버가 알려준 이 포트로 접속을 시도하고,
④ 서버는 ack로 응답한다.

② Passive 모드에서는 두 번째 data포트로서 active 모드가 사용했던 20번을 사용하지
   않고 대신 1024 이후의 임의의 비 특권 포트를 사용하게 된다.

③ 따라서 passive 모드는 서버에서 클라이언트로 연결을 시도하는 active 모드의
   문제점을 해결하기는 했지만, 서버의 비 특권포트(1024~65535)를 방화벽에서
   모두 열어 두어야 한다는 또 다른 문제점이 발생한다.



보충학습
FTP 공격 유형

1. FTP 바운스 공격(FTP Bounce Attack)
① FTP 프로토콜의 취약점을 이용한 공격으로 FTP 서버가 데이터를 전송할 때 목적지를 검사하지 않는다는 점을 이용한 공격이다.
② FTP의 원래 규약을 어느 정도 제한하거나, 인정하여도 다른 서비스에서 20번 포트 접속 요청을 거절하도록 하여 대응한다.

2. 익명(Anonymous) FTP 공격
① FTP의 취약점을 이용한 파일의 불법 전송이나 복제이다.
② 보안 절차를 거치지 않는 익명의 사용자에게 FTP 서버로의 접근을 허용한다. 익명 사용자가 쓰기 권한이 있을 때 악성 코드 생성이 가능해진다.
③ 익명의 사용자의 접속 경로는 쓰기 권한과 실행 권한을 제한함으로써 대응한다.

3. TFTP(Trivial File Transfer Protocol) 공격
① TCP 대신 UDP 프로토콜을 사용한다.
② 클라이언트에서 직접 시 주로 사용되는 프로토콜로 인증 절차를 요구하지 않아 보안에 취약하다.
③ 설정이 잘못될 경우 누구나 호스트에 접근이 가능하여 파일 유출이 가능해진다.


(3) 명령 삽입 취약점

1) SQL 처리
① 클라이언트의 요청을 처리하기 위해 전송받는 인수에는 특정 명령을 실행할 수 있는 코드가 포함되는 경우가 있다.
② 이를 적절히 필터링하는 등의 처리 과정을 수행하지 못하는 경우 삽입 공격에 대한 취약점이 생긴다.
③ 명령 삽입 공격은 웹 서버와 연동되는 데이터베이스에 임의의 SQL 명령을 실행하여 데이터를 수집할 수 있기 때문에 위험도가 매우 높다.
④ 웹 서버는 서비스 이용자에게 인증, 게시판, 검색 등 다양한 정보를 제공하기 위해 대부분 데이터베이스와 연동되어 운영된다.
⑤ 웹 서버는 데이터베이스를 이용하기 위해 SQL 쿼리를 이용한다.
⑥ 웹 서버에서 데이터베이스로 전송되는 SQL 쿼리에는 아이디, 패스워드, 검색어 등 여러 가지 인수가 사용되는데, SQL 삽입 공격은 전송되는 인수에 추가적인 실행을 위한 코드를 넣는 것을 말한다.

2) SQL 삽입(Injection) 공격
① SQL 삽입(Injection)은 사용자가 입력하는 입력 값에 대한 유효성을 검증하지 않고 그대로 사용할 때 발생할 수 있는 데이터베이스와 관련된 보안 취약점이다.
② 데이터베이스로 전달되는 SQL 질의가 악의적으로 변조되어 사용자 인증을 우회하거나 데이터베이스에 저장된 데이터가 변조되거나 파괴될 수 있는 보안 공격이다.
③ 공격자가 웹 서버의 관리자 권한을 획득할 수 있으며 관리자 권한 획득을 이용하여 추가적인 보안 공격이 발생할 수 있다.


<정상적인 경우>
Select * From 학생 Where ID = 'admin' And PW = '진짜암호';

<SQL 삽입>
Select * From 학생 Where ID = "" Or 1=1 And PW = '아무거나';

④ 정상적인 경우 ID와 PW가 틀리면 반환하는 값이 없어야 한다.
⑤ SQL 삽입의 경우 특수 문자열 ‘Or 1=1’에 의해 SQL 질의문이 변조되어 ID와 PW가
   달라도 무조건 값을 반환하게 된다.

3) 보안책
① 매개변수를 이용한 바인딩 기법을 사용한다.
   Select * From 학생 Where ID = ? And PW = ?;

② 입력값에 대한 특수 문자 검증
   사용자 입력이 SQL 삽입을 발생시키지 않도록 사용자 입력 시 특수문자(‘, “, /,
   ;, :, --, +, 공백 등)가 포함되어 있는지 검사하여 허용되지 않는 문자열이나
   문자가 포함된 경우 제거한다.

(4) XSS, 크로스사이트 스크립트 취약점

1) 크로스사이트 스크립팅
① XSS(Cross Site Scripting)는 공격자에 의해 작성된 악성스크립트가 다른 사용자
   에게 전달되는 것이다.
② 웹 브라우저에서 사용자가 입력하는 입력값에 대한 유효성을 검증하지 않고 그대로
   웹 서버에 전송했을 때 발생하는 보안 취약점이다.
③ 공격자가 의도적으로 악성 스크립트를 웹 서버에 저장하는 것이 첫 번째 목적이다.
④ 다른 사용자의 웹 브라우저 내에서 적절한 검증 없이 실행되기 때문에 사용자의
   세션을 탈취하거나, 웹 사이트를 변조하거나 혹은 악의적인 사이트로 사용자를
   이동시킬 수 있다.
⑤ 이런 XSS는 일반적으로 자바 스크립트에서 발생하지만, VB 스크립트, Active
   X 등 클라이언트에서 실행되는 동적 데이터를 생성하는 모든 언어에서 발생할
   수 있다.

2) 동작 순서
① 임의의 XSS 취약점이 존재하는 서버에 XSS 코드를 작성하여 저장한다. 일반적으로
   공격자는 임의의 사용자 또는 특정인이 이용하는 게시판을 이용한다.
② 해당 웹 서비스 사용자가 공격자가 작성해놓은 XSS 코드에 접근한다. 물론 사용자는
   본인이 공격자가 작성해놓은 XSS 코드에 접근하는 것을 인지하지 못한다. 사용자는
   어떤 게시판의 글을 읽는 과정에서 공격자의 XSS 코드에 접근한다.

보충학습

XSS 공격 유형

1. Stored XSS
① 가장 일반적인 XSS 공격 유형으로, 단순히 게시판이나 자료실과 같이 사용자가
   글을 저장하는 부분에 정상적인 평문이 아닌 스크립트 코드를 입력하는 것이다.
② 다른 사용자가 게시물을 열람하는 순간 공격자가 입력해둔 악성 스크립트가 실행되어
   사용자는 자신의 쿠키 정보가 유출되거나 악성 스크립트가 기획한 공격에 당하게
   된다.

2. Reflected XSS
① 반사 XSS 공격은 웹 애플리케이션에 스크립트를 저장하는 것이 아니라 URL의 변수
   부분처럼 스크립트 코드를 입력하는 동시에 결과가 바로 존재하는 공격기법이다.
② 공격자는 스크립트가 포함된 공격 URL을 다른 웹사이트, 이메일 등으로 보내서
   다른 사용자가 그것을 클릭하도록 유도한다.


(5) 취약한 인증 및 세션 관리

1) 인증 기능 취약
① 인증(authentication)은 현재 요청을 보낸 사용자가 시스템의 실제 사용자인지를
   확인하는 과정이다.
② 적절한 인증 없이 중요 기능이 허용되는 경우 보안 위험이 된다.
③ 취약한 인증의 가장 기본적인 문제점은 패스워드 설정이다.
④ 웹뿐만 아니라 패스워드를 사용하는 모든 운영체제와 응용 프로그램에 공통적으로
   해당하는 문제이다.
⑤ 웹에서는 취약한 계정을 사용하는 것이 좀 더 심각한 경우가 많은데, 이는 기본적으로
   개발자와 사용자가 동일하지 않기 때문이다.
⑥ 관리자 패스워드의 변경 인터페이스가 별도로 만들어져 있지 않고, 데이터베이스를
   직접 변경하는 것과 같이 원시적인 형태를 갖는 경우가 많기 때문에 사용자는
   최초 개발자가 설정해놓은 패스워드를 그대로 쓸 때가 많다.
⑦ 개발자 역시 개발 과정에서는 패스워드에 많은 신경을 쓰지 않기 때문에 웹에서는
   의외로 admin/admin과 같이 취약한 패스워드를 많이 발견할 수 있다.

2) 부적절한 인가
① 인가(Authorization)는 사용자의 자원에 대한 접근 혹은 사용을 허용하는 과정
   이다.
② 로그인에 성공한 사용자가 어떤 행위를 하려할 때, 허용을 결정하는 과정으로
   인가 여부를 확인하는 절차가 없을 때 보안 위험이 된다.


DOM 기반 XSS 공격

DOM 기반 XSS 공격은 2005년에 처음으로 아미르 카밀(Amir Kamil)이 관련 취약점
논문을 발표하면서 알려졌다. 피해자의 브라우저가 HTML 페이지를 주문 분석할 때마다
공격 스크립트가 DOM 생성의 일부로 실행되면서 공격한다. 페이지 자체는 변하지 않지만,
페이지에 포함되어 있는 브라우저측 코드가 DOM 환경에서 악성코드로 실행된다.

앞에서 다룬 저장 XSS 및 반사 XSS 공격의 악성 페이로드가 서버 측 애플리케이션
취약점으로 인해, 응답 페이지에 악성 스크립트가 포함되어 브라우저로 전달되면서
공격하는 것이 반면, DOM 기반 XSS는 서버와 관계없이 브라우저에서 발생하는 것이
차이점이다.


(6) 직접 객체 참조

① 직접 객체 참조는 파일, 디렉터리, 데이터베이스 키와 같이 내부적으로 구현된
   객체에 대한 참조가 노출될 때 발생한다.
② 접근 통제에 의한 확인이나 다른 보호조치가 없다면 공격자는 권한 없는 데이터에
   접근하기 위해 노출된 참조를 조작할 수 있다.

1) 경로 조작(Path Traversal)
① 경로 조작(Path Traversal)은 사용자가 입력하는 입력 값에 대한 유효성을 검증
   하지 않고 그대로 사용할 때 발생하는 서버 시스템 자원 접근에 대한 보안 취약점
   이다.
② 경로 조작 취약점을 악의적으로 활용하여 사용자가 접근해서는 안되는 서버의
   중요한 파일을 내려받거나 삭제할 수 있다.
③ 입력값에 부모 폴더를 의미하는 '..'이라는 특수문자열을 사용한다.
④ 사용자에게 내려받을 대상 파일 이름을 매개 변수 값으로 전달받을 경우 공격자가
   파일 이름에 특수 문자열 '..'을 추가하여 시스템 내부의 임의의 파일을 내려 받을
   수 있다.
⑤ 보안책은 입력 값에 대한 특수 문자를 검증하는 것이다.

2) 파일 업로드 제한 부재
① 유효성 점검의 대상이 사용자가 업로드하려는 파일이므로 사용자가 보내는 파일에
   대해 유효성 점검을 하지 않을 때 발생할 수 있는 보안 취약점이다.
② 공격자는 웹서버에 악의적인 파일을 전송하고, 원격지에서 해당 파일을 실행하여
   웹 서버를 장악하며 추가적인 내부 침투 공격을 수행할 수 있게 되기 때문이다.
③ 웹 해킹의 최종 목표인 리버스 텔넷과 같은 웹 서버의 통제권을 얻기 위해 반드시
   성공해야 하는 공격이다.
④ 이런 취약점의 가장 일반적인 형태는 게시판이다.
⑤ 게시판에 첨부파일로 악의적인 파일을 업로드하고 실행시키며 이 때 첨부파일로
   업로드하는 악성코드는 대부분 웹 쉘(Web Shell)이다.
⑥ 웹 쉘은 웹 서버를 기반으로 서버에 파일이 업로드되고 실행되기 때문에 서버
   쪽에서 실행되는 파일을 말한다.
⑦ 화이트리스트 방식으로 업로드가 가능한 파일 형식을 미리 정의해 놓고 허용된
   형식의 파일에 대해서만 업로드가 가능하도록 한다.
⑧ 일차적으로 웹 쉘 파일의 업로드를 막는다.

웹쉘(Webshell)

1. 특징
① 웹쉘(Webshell)이란 클라이언트의 명령을 서버에서 실행시켜주는 프로그램이다.
② 웹쉘은 공격자가 악의적인 목적을 가지고 만든 프로그램으로, 주로 주로 ASP, PHP,
   JSP 등을 사용한다.
③ 웹쉘이 완성되면, 취약점이 존재하는 서버에 업로드시키고 공격자가 만든 웹쉘이
   성공적으로 서버에 업로드가 된다면, 공격자는 자신이 서버에서 실행시키고자 하는
   명령어를 전송하여, 서버에서 실행이 되게 한다.
④ 즉, 공격자는 해당 서버의 모든 제어권을 장악하고, 정보탈취, 변조, 악성코드
   삽입 등 각종 악성행위를 한다.
⑤ 웹쉘공격은 HTTP서비스를 통하여 통신을 하기 때문에 탐지가 어려우며, 제작이 비교적
   쉽고 서버에서 관리자용 용이하기 때문에 흔히 사용되는 공격방법이다.

2. 예방책
① 시큐어 코딩
② 취약점 패치
③ 키워드/명령어 필터링
④ 업로드 파일의 확장자 및 실행권한 제한





3) 리버스 텔넷

① 리버스 텔넷(Reverse Telnet)은 웹 해킹을 통해 시스템의 권한을 획득한 후 해당 시스템에 텔넷과 같이 직접 명령을 입력하고 확인할 수 있는 쉘을 획득하기 위한 방법으로, 방화벽이 존재하는 시스템을 공격할 때 자주 사용된다.

② 일반적으로 웹 서버는 방화벽 내부에 존재하는데, 웹 서버는 80번 포트를 이용한 웹 서비스만 제공하면 되기 때문에 방화벽은 외부 인터넷을 사용하는 사용자에 대해 80포트만을 허용한다. 이런 경우에는 웹 서버의 텔넷이 열려 있어도 방화벽으로 인해 공격자가 외부에서 접근할 수 없다.

③ 보안측으로 파일 업로드를 먼저 막아야 한다.

④ 외부에서 내부로의 접속뿐만 아니라 내부에서 외부로의 불필요한 접속도 방화벽으로 막는 것이 좋다.

⑤ 서버에서 본인의 컴퓨터로 원격접속하게 하는 기술이다.


(7) CSRF 취약점

① CSRF(Cross Site Request Forgery)는 특정 사용자를 대상으로 하지 않고, 불특정 다수를 대상으로 로그인된 사용자가 자신의 의지와는 무관하게 공격자가 의도한 행위(수정, 삭제, 등록, 송금 등)를 하게 만드는 공격이다.

② CSRF는 기본적으로 XSS 공격과 매우 유사하며 XSS 공격의 발전된 형태라고 보기도 한다. 하지만 XSS 공격은 악성 스크립트가 클라이언트에서 실행되는 데 반해, CSRF 공격은 사용자가 악성 스크립트를 서버에 요청한다는 차이가 있다.

07 코드 공격

(1) 버퍼 오버플로 공격

1) 버퍼 오버플로 개요
① 버퍼는 하드웨어 장치나 프로그램이 사용하는 임시 메모리 공간을 말한다.
② 운영체제의 통제 하에 프로그램이 메모리에 적재되어 프로세스로서 작성된 코드를 실행할 때, 메모리 공간을 여러 목적의 구역으로 나누어 사용하는데 이 중 일부가 버퍼에 해당한다.
③ 버퍼 오버플로는 버퍼로 사용하는 메모리 공간의 관리 문제로 일어나는 문제로, 프로세스가 버퍼를 사용할 때 원래 할당받은 영역에 대한 관리나 통제 소홀로 인해 그 경계를 초과한 공간으로 데이터가 침범하는 상황을 말한다.
④ 이를 악의적으로 이용할 경우 특정 동작을 수행하도록 흐름을 제어할 수도 있다.
⑤ 스택 구역은 프로그램을 함수라는 모듈의 집합으로 볼 때, 함수의 진행에 따라 함수 내에서 사용할 데이터, 함수에 필요한 인자, 함수의 결과 등을 저장할 공간으로 사용한다.
⑥ 스택에는 프로그램 진행의 흐름과 내용이 담겨있다.

2) 셸과 SetUID

버퍼 오버플로를 이용한 기법은 운영체제의 허점 등의 비정상적인 경로를 사용하는 방법이다.

① 셸과 셸코드
㉠ 셸(shell)은 사용자가 운영체제를 사용하기 위한 인터페이스로, 입력받은 명령어를 해석하여 실행하는 역할을 한다.
㉡ 일단 셸이 실행되면, 해당 계정의 권한에 허용된 모든 프로그램을 실행할 수 있다.
㉢ 일반 사용자라면 시스템 환경설정이나 프로그램 설치 등에 상당한 제약을 받지만, 관리자 계정의 셸 실행이 가능하다면 어떤 제약도 없으므로 이는 버퍼 오버플로를 이용한 기법의 일차적인 목표가 된다.
㉣ 일반적인 프로그램의 내부에서 셸을 직접 실행할 필요가 많지 않기 때문에, 버퍼 오버플로를 이용한 기법에서는 대부분 프로그램의 명령 코드에 셸을 강제로 실행할 수 있는 기계어 코드를 삽입하는데, 이를 셸코드(shellcode)라고 한다.

② SetUID
㉠ 각각 0인 UID와 GID를 갖는 루트 권한은 제약없이 모든 사용자의 파일 및 영역에 접근할 수 있다.
㉡ SetUID가 설정된 파일은 실행 권한 문자가 ‘s’임을 확인할 수 있다.




㉢ SetUID가 설정된 파일은 실행될 때, 실행한 주체에 관계없이 임시적으로 그 실행 파일의 소유자 권한을 갖는다.
㉣ 해당 파일의 소유자가 관리자라면 해당 파일을 실행하는 사람은 임시적으로 관리자의 권한을 얻을 수 있다는 것이다.
㉤ SetUID는 해당 파일의 소유자, 또는 관리자 권한을 가진 계정이 설정될 수 있다.

3) 버퍼 오버플로를 이용한 기법
① 스택과 프로그램 흐름을 관리한다면 현재 함수를 종료할 때 돌아갈 위치(RET : return address)가 필수적이다.
② 함수 내에서 사용되는 변수들은 스택 구역에 관리되는데 이러한 변수를 해당 함수의 지역 내에서만 사용한다고 하여 지역 변수(local variable)라고 한다.
③ 지역 변수와 RET 같은 함수 하나에 종속적이므로 체계적으로 관리하기 위해 함수의 구역을 나눠주는 작업이 필요하고, 이러한 구역을 스택 프레임(stack frame)이라 한다.
④ 스택 프레임의 관리를 위해 각 스택 프레임의 시작점 위치(SFP : stack frame pointer)를 따로 두고 지역 변수는 이 위치를 기준으로 번지를 정하여 사용한다.
⑤ 새로운 함수의 스택 프레임에 대한 SFP를 지정하기 위해서는 현재 스택의 크기를 항상 유지해야 한다.
⑥ 따라서 CPU의 스택 포인터 레지스터(SP : stack pointer register)에 항상 스택의 끝 위치 값을 유지하고 있으며, 함수 호출 시 호출 대상 함수의 SFP값으로 사용된다.
⑦ 스택 버퍼 오버플로를 이용한 기법은 함수 호출 시의 이러한 스택 변화 특성을 이용한다.
⑧ 함수의 실행이 종료되면 SFP를 복구하고 RET에 들어있는 주소로 복귀하는 것이 통상적인 흐름이다.
⑨ 그런데 프로그램의 오류에 의해 크기가 정해져 있는 지역 변수에 크기가 벗어난 데이터를 넣어서 RET 영역을 덮어 쓴다면, 통상적으로 RET가 가리키는 곳에 제대로 된 명령이 없기 때문에 프로그램이 비정상 종료될 것이다.
⑩ 스택 버퍼 오버플로를 이용한 기법에서는 이 RET 영역에 의도한 명령을 실행할 코드가 들어있는 주소값을 집어 넣으며, 일반적으로 셸을 실행할 수 있는 셸코드가 들어 있다.
⑪ 만약 관리자 권한으로 SetUID가 설정된 프로그램이라면 해당 프로그램을 결국 관리자 권한을 갖고 있는 셸을 실행하게 될 것이다.














4) 스택 버퍼 오버플로를 이용한 절차

① 셸코드와 같은 특정 코드를 메모리의 임시 공간에 저장한다.
② 여러 방법으로 해당 프로그램의 스택 크기를 추정하여, 버퍼 오버플로에 취약한 함수가 실행될 때, RET 영역을 덮어씌울 수 있는 인자값을 집어 넣는다. 이때 RET 영역에 들어갈 주소는 ①에서 저장한 임시 공간의 주소이다.
③ 해당 함수의 실행이 끝날 때, RET 영역에 들어간 주소의 코드가 실행될 것이다.

5) 정리

① C언어에서는 정수, 실수와 같은 지역 변수의 타입과 크기를 체크하기 때문에 일반적으로 이런 일이 일어날 수 없으나, 특정 함수의 경우 변수를 사용하면서 그 크기를 체크하지 않고 단지 특정 숫자(일반적으로 0)로 끝을 나타내는 방식을 사용하기 때문에 버퍼 오버플로를 이용한 기법의 대상이 된다.
② 문자열을 복사하거나 비교하는 strcpy(), strcat() 함수들이 그 예인데, 최근에는 이러한 함수들을 사용할 때 경고 메시지를 띄우고 다른 함수를 사용하기를 권장하고 있다.
③ 운영체제 차원에서도 스택가드(stack guard)를 두어 스택이 임의의 접근에 의해 조작되었는지 검사하여 실행을 거부한다. 스택가드는 Canary 값을 스택에 넣는다.
④ 스택 조작을 막기 위해 스택 위치를 랜덤으로 위치시키는 방어 기법이 도입되고 있다.
⑤ 스택쉴드(stack shield)는 리턴주소를 다른 곳으로 옮겨 덮어쓰기 힘들게 한다.

[심화학습]
버퍼 오버플로 공격 대응책

1. Non-Executable 스택
스택에서 프로그램을 실행할 수 없도록 한다. 즉 스택에서의 x(execute) 권한을 제거한다.

2. 스택가드(Stack Guard)
컴파일러가 프로그램의 함수 호출 시에 RET 앞에 Canary 값을 주입하고, 종료 시에 이 Canary 값이 변조되었는지의 여부를 확인하여 공격을 탐지한다.

3. 스택쉴드(Stack Shield)
함수 호출 시 RET를 Global RET 스택이라는 특수 스택에 저장하고 함수의 종료 시 Global RET 스택에 저장된 RET 값과 스택의 RET 값을 비교하여 일치하지 않으면 프로그램을 종료한다.

4. ASLR(Address Space Layout Randomization)
스택, 힙, 라이브러리 등의 데이터 영역 주소 등을 난수화하여 프로세스의 주소 공간에 배치하는 것으로 리눅스 커널 2.6.12 이후 적용되었다.



버퍼 오버플로에 취약한 함수

① strcpy(char *dest, const char *src);
② strcat(char *dest, const char *src);
③ getwd(char *buf);
④ gets(char *s);
⑤ scanf(const char *format, ...);
⑥ realpath(char *path, char resolved_path[]);
⑦ sprintf(char *str, const char *format);

Canary 종류

• Random Canary : Canary 값 변경, 이전 사용한 Canary 값 사용 못함
• Null Canary : Canary에 NULL 포함
• Terminator Canary : Canary에 함수 종료값을 조합한 값 포함

힙 버퍼 오버플로

힙(heap)에 저장되는 데이터를 변조하거나, 함수에 대한 포인터 값을 변조함으로써 RET 값을 변조하여 임의의 코드를 실행하는 공격

rtl 공격

스택에 있는 RET 주소를 실행 가능한 임의의 주소(libc 영역의 주소)로 돌려 원하는 함수를 수행하게 만드는 기법이다. 메모리에 적재된 공유 라이브러리는 스택에 존재하는 것이 아니므로 Non-Executable 스택을 우회하는 것이 가능하다.

(2) 포맷 스트링 공격

1) 포맷 스트링 개요

① 포맷 스트링(format string)이란 출력하려는 데이터의 형태를 기술한 문자열이다.
② 포맷 스트링은 %로 시작하는 지시자를 사용함으로써 구성되고, 포맷형에 들어갈 데이터 변수를 설정함으로써 문자열 출력이 구성된다.
③ 포맷 스트링 없이 printf() 계열의 함수를 사용할 경우 데이터 변수를 검사 없이 출력에 적용하게 된다.
④ 이때 데이터 변수 내용에 %로 시작하는 지시자가 있는 경우 printf()는 이를 포맷 스트링으로 해석하여 출력한다.
⑤ printf()는 인자로 필요한 데이터 변수가 지정되지 않더라도 그 위치를 변수 형식에서 자동 계산하여 인자로 집어넣기 때문에 오류가 발생하지 않는다.

2) 포맷 스트링 공격

① printf()라는 출력함수에서 변수의 값을 변경시킬 수 있는 방법을 제공한다고 볼 수 있다.
② 포맷 스트링이 제대로 지정되었다면 문제가 발생하지 않겠지만, 그렇지 않을 경우 printf()에 이 지시자가 포함된 인수를 넣어 스택 버퍼 오버플로를 이용한 기법과 비슷한 효과를 얻을 수 있다.
③ 실행 파일의 기계어 코드를 분석하는 디스어셈블(disassemble)과 포맷 스트링이 없는 printf() 등을 이용해 메모리 내용을 출력하여 코어 덤프(core dump)를 분석하면 main() 함수의 스택 프레임 크기를 추산할 수 있다.
④ 이를 이용하여 printf() 이후에 돌아올 RET의 위치를 알 수 있다.
⑤ %n에 해당하는 인자에 RET의 주소를 넣고, 그 전에 다른 지시자를 다수 조합하여 셸코드가 담긴 주소값만큼 문자열을 출력하게끔 조정하면 RET의 영역에 셸코드의 주소값이 들어가게 된다.
⑥ 포맷 스트링 공격은 데이터의 형태와 길이에 대한 불명확한 정의로 인한 문제점 중 ‘데이터 형태에 대한 불명확한 정의로 인한 것이다.

(3) 레이스 컨디션 공격

1) 레이스 컨디션 개요

① 멀티태스킹을 지원하는 일반적인 운영체제에서는 여러 개의 프로세스를 동시에 실행하는 것과 같은 효과를 얻기 위해, 각 프로세스에 CPU 시간을 배분한다.
② 프로세스 입장에서 보면 한정된 자원인 CPU를 차지하기 위해 동시에 여러 프로세스들이 경쟁을 벌이는 것인데, 이를 레이스 컨디션(race condition)이라 한다.
③ 시스템 위험에서 레이스 컨디션을 이용한 기법은 임시 파일을 생성하면서 SetUID가 설정된 프로그램과 심볼릭 링크를 이용한다.

레이스 컨디션 필요 조건

• 공격대상 프로그램의 소유자가 root여야 한다.
• 공격대상 프로그램이 SetUID 비트를 가져야 한다.
• 생성되는 임시파일의 이름을 알고 있어야 한다.

2) 심볼릭 링크

① 유닉스, 리눅스에서는 하나의 파일에 다른 이름을 주는 다음과 같은 방법이 있다.
㉠ 하드 링크(hard link) : 파일의 상세 정보가 담겨져 있는 메타 정보를 복사하고 파일의 실제 데이터에 연결(link)하는 것이다.
㉡ 심볼릭 링크(symbolic link) : 새로운 파일을 만들고 이 파일은 어떤 경로의 파일에 연결되어 있다는 정보만 기록한다.

② 심볼릭 링크는 원래 파일이 새로운 파일로 변경되어도 경로만 같으면 상관없으므로, 파일의 업데이트를 별다른 변경 절차 없이 이용할 수 있어 많이 사용된다.

3) 심볼릭 링크를 이용한 기법

① 시스템의 어떤 실행 파일에 관리자 권한의 SetUID가 설정되어 있고, 이 파일은 임시 디렉터리에 임시 파일을 생성한다고 가정한다.
② 임시 디렉터리를 관찰하면 임시 파일의 이름을 쉽게 알아낼 수 있으므로, 실행 파일이 임시 파일을 생성하기 전에 해당 파일의 이름으로 심볼릭 링크를 생성한다.
③ 리눅스, 유닉스는 파일을 열 때 생성 단계에서 파일이 존재할 경우 이를 그대로 사용한다.
④ 실행 파일이 심볼릭 링크에 대한 대처를 하지 않을 경우, 실제 조작되는 파일은 심볼릭 링크를 걸어놓은 파일이 된다.
⑤ 중요한 설정 파일을 연결해 놓을 경우 임의의 데이터가 덮어써져서 시스템의 비정상적인 동작을 유발할 수 있고, 관리자 권한으로 어떤 파일을 작성하게 할 수 있다.
⑥ 심볼릭 링크를 이용한 공격을 막기 위해 프로그램 작성자들은 임시 파일을 생성하기 전에 파일이 이미 생성되어 있는지 조사하고, 링크가 걸려있는 파일이면 삭제한다.

• 소스코드 보안약점 진단 및 개선

테스트
• 모의침투 테스트 또는 동적분석을 통한 보안취약점 진단 및 개선

유지보수
• 지속적인 개선

심볼릭 링크를 이용한 레이스 컨디션 공격 절차

2. 생성될 임시 파일과 같은 이름의 파일을 생성한다.
3. 위에서 만든 파일에 심볼릭 링크를 생성한다.
4. 원본 파일을 지우고 취약 프로그램이 심볼릭 링크로 건 파일과 같은 파일을 생성하기를 기다린다.
5. 생성되었을 때, 심볼릭 링크를 이용하여 파일 내용을 변경한다.




심화학습
소프트웨어 개발 보안 적용 사례

① MS-DL(Microsoft-Secure Development Lifecycle)
마이크로소프트사는 보안수준이 높은 안전한 소프트웨어를 개발하기 위해 자체수립한
SDL(Secure Development Lifecycle) 방법론을 적용하였으며, SDL이 적용된 소프트
웨어는 이전 버전에 비해 50% 이상 취약점이 감소하였다고 발표했다.

② Seven Touchpoints
Seven Touchpoints는 실무적으로 검증된 개발보안 방법론 중 하나로서 소프트웨어
보안의 모범 사례를 소프트웨어 개발 라이프사이클에 통합했다.
공통 위협요소를 파악하고 이해하며, 보안을 설계하고 모든 소프트웨어 산출물에 대해
철저하고 객관적인 위험분석 및 테스트를 거쳐 안전한 소프트웨어를 만들어내는 방법을
정의하고 있다.
이러한 보안활동을 수행하는 동안 소프트웨어 위험요소에 대해서 위험관리 프레임워크에
따라 명시적으로 추적하고 모델링을 수행한다.

③ CLASP(Comprehensive, Lightweight Application Security Process)
SW개발보안 방법론 중 하나인 CLASP는 소프트웨어 개발 생명주기(SDLC) 초기단계에
보안강화를 목적으로 하는 정형화된 프로세스로서, 활동중심ㆍ역할기반의 프로세스로
구성된 집합체이다.
이미 운영 중인 시스템에 적용하기 좋다.


심화학습
소프트웨어 보안 취약점

1. 입력데이터 검증 및 표현

① SQL 삽입

㉠ 정의
데이터베이스(DB)와 연동된 웹 어플리케이션에서 입력된 데이터에 대한 유효성
검증을 하지 않을 경우, 공격자가 입력 폼 및 URL 입력란에 SQL 문을 삽입하여
DB로부터 정보를 열람하거나 조작할 수 있는 보안약점을 말한다.

㉡ 보안대책
• Prepared Statement객체 등을 이용하여 DB에 컴파일된 쿼리문(상수)을 전달
  하는 방법을 사용한다.
• Parameterized Statement를 사용하는 경우에는 DB쿼리에 사용되는 외부 입
  력값에 대하여 특수문자 및 쿼리 예약어를 필터링한다.

㉢ 스트러츠(Struts), 스프링(Spring)등과 같은 프레임워크를 사용하는 경우에는
외부 입력값 검증 모듈 및 보안 모듈을 상황에 따라 적절하게 사용한다.

② 자원삽입

㉠ 정의
외부 입력값을 검증하지 않고 시스템 자원(Resource)에 대한 식별자로 사용하는
경우, 공격자는 입력값 조작을 통해 시스템이 보호하는 자원에 임의로 접근하거나
수정할 수 있고 잘못된 입력값으로 인해 시스템 자원간 충돌이 발생할 수
있다.


㉡ 보안대책
• 외부의 입력을(파일, 소켓의 포트 등) 식별자로 사용하는 경우, 적절한 검증을
  거치도록 하거나 사전에 정의된 적합한 리스트에서 선택되도록 작성한다.
• 외부의 입력이 파일인 경우에는 경로순회(Directory Traversal)를 수행할
  수 있는 문자를 제거한다.

③ 크로스사이트 스크립트

㉠ 정의
웹 페이지에 악의적인 스크립트를 포함시켜 사용자 측에서 실행되게 유도할 수
있다. 예를 들어, 검증되지 않은 외부 입력이 동적 웹페이지 생성에 사용될 경우,
전송된 동적 웹페이지를 열람하는 접속자의 권한으로 부적절한 스크립트가 수행
되어 정보유출 등의 공격을 유발할 수 있다.

㉡ 보안대책
• 일반적인 경우에는 사용자가 문자열에 스크립트를 삽입하는 것을 막기 위해
  사용자가 입력한 문자열에서 <, >, &, " 등의 문자 변환 함수나 메소드를
  사용하여 &lt, &gt, &amp, &quot로 치환한다.
• HTML 태그를 허용하는 게시판에서는 게시판에서 지원하는 HTML 태그의 리
  스트(White List)를 선정한 후, 해당 태그만 허용하는 방식을 적용한다.

④ 운영체제 명령어 삽입

㉠ 정의
• 적절한 검증절차를 거치지 않은 사용자 입력값이 운영체제 명령어의 일부 또는
  전부로 구성되어 실행되는 경우, 의도하지 않은 시스템 명령어가 실행되어
  부적절하게 권한이 변경되거나 시스템 동작 및 운영에 악영향을 미칠 수 있다.
• 일반적으로 명령어 라인의 파라미터나 스크립트 입력 등 외부 입력을 사용하여
  시스템 명령어를 생성하는 프로그램이 많이 있다. 하지만 이러한 경우 외부
  입력 문자열은 신뢰할 수 없기 때문에 적절한 처리를 해주지 않으면, 공격자가
  원하는 명령어 실행이 가능하게 된다.

㉡ 보안대책
• 웹 인터페이스를 통해 서버 내부로 시스템 명령어를 전달시키지 않도록 어플리
  케이션을 구성하고, 외부에서 전달되는 값을 검증없이 시스템 내부 명령어로
  사용하지 않는다.
• 외부 입력에 따라 명령어를 생성하거나 선택이 필요한 경우에는 명령어 생성에
  필요한 값들을 미리 지정해 놓고 외부 입력에 따라 선택하여 사용한다.

⑤ 위험한 형식 파일 업로드

㉠ 정의
서버측에서 실행될 수 있는 스크립트 파일(asp, jsp, php 파일 등)이 업로드 가능
하고, 이 파일을 공격자가 웹을 통해 직접 실행시킬 수 있는 경우, 시스템 내부명령
어를 실행하거나 외부와 연결하여 시스템을 제어할 수 있는 보안약점이다.

㉡ 보안대책
• 화이트리스트 방식으로 허용된 확장자만 업로드를 허용한다.
• 업로드 되는 파일을 저장할 때에는 파일명과 확장자를 외부사용자가 추측할
  수 없는 문자열로 변경하여 저장하며, 저장 경로는 ‘web document root’ 밖에
  위치시켜서 공격자의 웹을 통한 직접 접근을 차단한다.
• 파일 실행 여부를 설정할 수 있는 경우, 실행 속성을 제거한다.

⑥ 신뢰되지 않는 URL 주소로 자동 접속 연결

㉠ 정의
• 사용자로부터 입력되는 값을 외부사이트의 주소로 사용하여 자동으로 연결하는
  서버 프로그램은 피싱(Phishing) 공격에 노출되는 보안약점이다.
• 일반적으로 클라이언트에서 전송된 URL 주소로 연결하기 때문에 안전하다고
  생각할 수 있으나, 해당 폼의 요청을 변조함으로써 공격자는 사용자가 위험한
  URL로 접속할 수 있도록 공격할 수 있다.

㉡ 보안대책
자동 연결할 외부 사이트의 URL과 도메인은 화이트 리스트로 관리하고, 사용자
입력값을 자동 연결할 사이트 주소로 사용하는 경우에는 입력된 값이 화이트
리스트에 존재하는지 확인해야 한다.

⑦ XQuery 삽입

㉠ 정의
XQuery를 사용하여 XML 데이터에 대한 동적 쿼리를 생성할 때 사용하는 외부
입력값에 대해 적절한 검증절차가 존재하지 않으면 공격자가 쿼리문의 구조를
임의로 변경할 수 있게 된다. 이로 인해 허가되지 않은 데이터를 조회하거나
인증절차를 우회할 수 있다.

㉡ 보안대책
XQuery에 사용되는 외부 입력데이터에 대하여 특수문자 및 쿼리 예약어를 필터
링하고, XQuery를 사용한 쿼리문은 스트링을 연결하는 형태로 구성하지 않고
파라미터(Parameter)화된 쿼리문을 사용한다.

⑧ XPath 삽입

㉠ 정의
외부 입력값을 적절한 검사과정 없이 XPath 쿼리문 생성을 위한 문자열로 사용
하면, 공격자는 프로그래머가 의도하지 않았던 문자열을 전달하여 쿼리문의 의
미를 왜곡시키거나 그 구조를 변경하고 임의의 쿼리를 실행하여 인가되지 않은
데이터를 열람할 수 있다.

㉡ 보안대책
Xpath 쿼리에 사용되는 외부 입력데이터에 대하여 특수문자(" , [ , ] , / , = , @
등) 및 쿼리 예약어 필터링을 수행하고 파라미터가 쿼리문을 지원하는 XQuery를
사용한다.

⑨ LDAP 삽입

㉠ 정의
• 공격자가 외부 입력을 통해서 의도하지 않은 LDAP(Lightweight Directory
  Access Protocol) 명령어를 수행할 수 있다. 즉 웹 응용프로그램이 사용자가
  제공한 입력을 올바르게 처리하지 못하면, 공격자가 LDAP 명령문의 구성을
  바꿀 수 있다.
  이로 인해 프로세스가 명령을 실행한 컴포넌트와 동일한 권한(Authentication)
  을 가지고 동작하게 된다.
• LDAP 쿼리문이나 결과로 외부 입력이 부분적으로 적절한 처리없이 사용되면,
  LDAP 쿼리문이 실행될 때 공격자는 LDAP 쿼리문의 내용을 마음대로 변경할
  수 있다.


㉡ 보안대책
• DN(Distinguished Name)과 필터에 사용되는 사용자 입력값에는 특수문자가
  포함되지 않도록 특수문자를 제거한다.
• 만약 특수문자를 사용해야 하는 경우에는 특수문자(=, +, <, >, #, ;, ₩
  등)가 실행명령이 아닌 일반문자로 인식되도록 처리한다.


⑩ 크로스사이트 요청 위조

㉠ 정의
• 특정 웹사이트에 대해서 사용자가 인지하지 못한 상황에서 사용자의 의도와는
  무관하게 공격자가 의도한 행위(수정, 삭제, 등록 등)를 요청하게 하는 공격을
  말한다.
• 공격자는 사용자가 인증한 세션이 특정 동작을 수행하여도 계속 유지되어 정상적인
  요청과 비정상적인 요청을 구분하지 못하는 점을 악용하여 공격을 수행한다.
• 웹 응용프로그램에 요청을 전달할 경우, 해당 요청의 적법성을 입증하기 위하
  여 전달되는 값이 고정되어 있고, 이러한 자료가 GET방식으로 전달된다면
  공격자가 이를 쉽게 알아내어 원하는 요청을 보냄으로써 위험한 작업을 요청할
  수 있게 된다.

㉡ 보안대책
• 입력화면 폼 작성 시 GET 방식보다는 POST 방식을 사용하고 입력화면 폼과
  해당 입력을 처리하는 프로그램 사이에 토큰을 사용하여, 공격자의 직접적인
  URL 사용이 동작하지 않도록 처리한다.
• 특히 중요한 기능에 대해서는 사용자 세션검증과 더불어 재인증을 유도한다.

⑪ 디렉터리 경로 조작

㉠ 정의
• 외부의 입력을 통하여 “디렉터리 경로 문자열” 생성이 필요한 경우, 외부 입력
  값에 대해 경로 조작에 사용될 수 있는 문자를 필터링하지 않으면, 의도하지
  않은 접근 제한 영역에 대한 경로 문자열 구성이 가능해져 시스템 정보노출,
  서비스 장애 등을 유발시킬 수 있다.
• 경로 조작을 통해 인가되지 않은 접근 권한을 획득하여, 설정에 관련된 파일을
  변경하거나 실행시킬 수 있다.

㉡ 보안대책
파일경로와 이름을 생성할 때 외부 입력값을 사용하는 경우, 정해진 경로 이외의
디렉터리와 파일에 접근할 수 없도록 처리하고 외부 입력값에 대해 replaceAll()
등의 메소드를 사용하여 의도하지 않은 경로로의 접근을 허용하는 위험 문자(“,
/, ₩, ..)을 제거하는 필터링을 수행한다.

⑫ HTTP 응답분할

㉠ 정의
HTTP 요청에 들어 있는 파라미터(Parameter)가 HTTP 응답헤더에 포함되어
사용자에게 다시 전달될 때, 입력값에 CR(Carriage Return)이나 LF(Line Feed)
와 같은 개행문자가 존재하면 HTTP응답이 2개 이상으로 분리될 수 있다. 이
경우 공격자는 개행문자를 이용하여 첫 번째 응답을 종료시키고, 두 번째 응답에
악의적인 코드를 주입하여 XSS 및 캐시 훼손(Cache Poisoning) 공격 등을 수행
할 수 있다.


ㄴ 보안대책
• 외부에서 입력된 파라미터(Parameter)를 HTTP 응답헤더(Set Cookie 등)에 포함시킬 경우, CRLF 등의 개행문자를 제거한다.

⑬ 정수 오버플로우
㉠ 정의
정수형 변수의 오버플로우는 정수값이 증가하면서, 허용된 가장 큰 값보다 더 커져서 실제 저장되는 값은 의도하지 않게 아주 작은 수이거나 음수가 될 수 있다. 특히 버퍼뿐만 아니라, 메모리 할당, 메모리 복사 등과 같은 조건으로 사용자가 제공하는 입력값을 사용하고 그 과정에서 정수 오버플로우가 발생하는 경우 보안상 문제를 유발할 수 있다.

㉡ 보안대책
• 언어/플랫폼별 정수타입의 범위를 확인하여 사용한다. 정수형 변수를 연산에 사용하는 경우, 결과값의 범위를 체크하는 모듈을 사용한다.
• 특히 외부 입력값을 동적으로 할당하여 사용하는 경우, 변수의 값 범위를 검사하여 적절한 범위에 존재하는지 확인한다.

⑭ 보호메커니즘을 우회할 수 있는 입력값 변조
㉠ 정의
• 응용프로그램이 외부 입력값에 대한 신뢰를 전제로 보호메커니즘을 사용하는 경우, 공격자가 입력값을 조작할 수 있다면 보호메커니즘을 우회할 수 있게 된다.
• 개발자들이 흔히 쿠키, 환경변수 또는 히든필드와 같은 입력값이 조작될 수 없다고 가정하지만, 공격자는 다양한 방법을 통해 이러한 입력값들을 변경할 수 있고 조작된 내용은 탐지되지 않을 수 있다.
• 인증이나 인가와 같은 보안설정이 이런 입력값(쿠키, 환경변수, 히든필드 등)에 기반해 수행되는 경우, 공격자는 이런 입력값을 조작하여 응용프로그램의 보안을 우회할 수 있다. 예로, 충분한 암호화, 무결성체크 또는 다른 메커니즘이 없는 경우에 외부사용자에 의한 입력값을 신뢰해서는 안 된다.

㉡ 보안대책
• 상태정보나 민감한 데이터, 특히 사용자 세션정보와 같은 중요한 정보는 서버에 저장하고 보안확인 절차도 서버에서 실행한다.
• 보안설계 관점에서 신뢰할 수 없는 입력값이 어플리케이션 내부로 들어올 수 있는 지점과 보안결정에서 사용되는 입력값을 식별하고, 제공되는 입력값에 의존할 필요가 없는 구조로 변경할 수 있는지 검토한다.

2. 보안기능
① 적절한 인증없이 중요기능 허용
㉠ 정의
적절한 인증과정 없이 중요정보(계좌이체 정보, 개인정보 등)를 열람(또는 변경)할 때 발생하는 보안약점이다.

㉡ 보안대책
• 클라이언트의 보안검사를 우회하여 서버에 접근하지 못하도록 설계하고, 중요한 정보가 있는 페이지는 재인증을 적용(은행 계좌이체 등)한다.
• 안전하다고 확인된 라이브러리나 프레임워크(OpenSSL이나 ESAPI의 보안 기능 등)를 사용하는 것이 중요하다.


② 부적절한 인가
㉠ 정의
프로그램이 모든 가능한 실행경로에 대해서 접근제어를 검사하지 않거나 불완전하게 검사하는 경우, 공격자는 접근 가능한 실행경로를 통해 정보를 유출할 수 있다.

㉡ 보안대책
• 응용프로그램이 제공하는 정보와 기능을 역할에 따라 배분함으로써 공격자에게 노출되는 공격 노출면(Attack Surface)을 최소화하고, 사용자의 권한에 따른 ACL(Access Control List)을 관리한다.
• 프레임워크를 사용해서 보안약점을 피할 수도 있는데 예를 들면, JAAS Authorization Framework나 OWASP ESAPI Access Control 등이 인증 프레임워크로 사용 가능하다.

③ 중요한 자원에 대한 잘못된 권한설정
㉠ 정의
SW가 중요한 보안관련 자원에 대하여 읽기 또는 수정 권한을 의도하지 않게 허가할 경우, 권한을 갖지 않은 사용자가 해당자원을 사용하게 된다.

㉡ 보안대책
설정파일, 실행파일, 라이브러리 등은 SW 관리자에 의해서만 읽고 쓰기가 가능하도록 설정하고 설정파일과 같이 중요한 자원을 사용하는 경우, 허가받지 않은 사용자가 중요한 자원에 접근 가능한지 검사한다.

④ 취약한 암호화 알고리즘 사용
㉠ 정의
SW 개발자들은 환경설정 파일에 저장된 패스워드를 보호하기 위하여 간단한 인코딩 함수를 이용하여 패스워드를 감추는 방법을 사용하기도 한다. 그렇지만 Base64와 같은 지나치게 간단한 인코딩 함수를 사용하는 것은 패스워드를 제대로 보호할 수 없다.

㉡ 보안대책
• 자신만의 암호화 알고리즘을 개발하는 것은 위험하며, 학계 및 업계에서 이미 검증된 표준화된 알고리즘을 사용한다.
• 기존에 취약하다고 알려진 DES, RC5 등의 암호화알고리즘을 대신하여, 3DES, AES, SEED 등의 안전한 암호알고리즘으로 대체하여 사용한다. 또한, 업무관련 내용, 개인정보등에 대한 암호 알고리즘 적용시, IT 보안인증 사무국이 안전성을 확인한 검증필 암호모듈을 사용해야 한다.

⑤ 사용자 중요정보 평문 저장(또는 전송)
㉠ 정의
프로그램이 개인정보, 인증정보, 금융정보 등의 사용자 중요정보를 평문으로 저장하거나 통신 채널을 통해서 송수신할 경우, 통신채널 스니핑을 통해 인가되지 않은 사용자에게 민감한 데이터가 노출될 수 있는 보안약점이다.

㉡ 보안대책
개인정보(주민등록번호, 여권번호 등), 금융정보(카드번호, 계좌번호 등), 패스워드 등을 저장할 때에는 반드시 암호화하여 저장하고, 통신 채널을 통해 전송할 때에도 암호화한다.


CMVP
암호모듈 검증제도(CMVP, Cryptographic Module Validation Program)는 미국의 NIST(National Institute of Standards and Technology)와 캐나다의 CSEC(Communications Security Establishment Canada)가 공동으로 주관하여 암호모듈 검증을 시행하기 위하여 시작한 제도이다.
암호모듈 검증제도는 민감한 정보의 보호를 위해 양국의 연방 정부가 FIPS 140-1과 FIPS 140-2를 사용하여 암호모듈을 검증을 시작하였다. 현재 암호모듈 검증제도는 미국과 캐나다를 제외하고 여러 국가에서 시행되어지고 있는데 대표적으로 한국, 일본, 영국에서 시행되어지고 있다.
국내에서도 시행되어지고 있는 CMVP의 경우 전자정부법 시행령 제 69조 [암호모듈 시험 및 검증지침]에 의거, 국가·공공기관 정보통신망에서 소통되는 자료 중에서 비밀로 분류되지 않은 중요 정보의 보호를 위해 사용되는 암호모듈의 안전성과 신뢰성을 검증하는 제도이다. 검증대상에 암호모듈은 소프트웨어, 하드웨어, 펌웨어 또는 이들을 조합한 형태로 구현될 수 있으며 소프트웨어 암호모듈을 검증기준 또는 암호모듈 검증기준(KS X ISO/IEC 19790)을 준수하여 시험되고 있다. 국가·공공·민간기관에서 사용하는 매일 암호화 모듈, 구간암호화 모듈, PKI 제품, SSO 제품, 키보드 암호화 모듈 등 보안제품에는 암호모듈검증제도를 통해 검증 받은 암호모듈이 탑재되어야 한다.

⑥ 하드코드된 패스워드
㉠ 정의
• 프로그램 코드 내부에 하드코드된 패스워드를 포함하고, 이를 이용하여 내부 인증에 사용하거나 외부 컴포넌트와 통신을 하는 경우, 관리자 정보가 노출될 수 있어 위험하다.
• 코드 내부에 하드코드된 패스워드가 인증실패를 야기하는 경우, 시스템 관리자가 그 실패의 원인을 파악하기 쉽지 않은 단점이 있다.

㉡ 보안대책
패스워드는 암호화하여 별도의 파일에 저장하여 사용하고 SW설치 시 사용하는 디폴트 패스워드, 키 등을 사용하는 대신 “최초-로그인”모드를 두어 사용자가 직접 패스워드나 키를 입력하도록 설계한다.

⑦ 충분하지 않은 키 길이 사용
㉠ 정의
• 길이가 짧은 키를 사용하는 것은 암호화 알고리즘을 취약하게 만들 수 있다.
• 키는 암호화 및 복호화에 사용되는데 검증된 암호화 알고리즘을 사용하더라도 키 길이가 충분히 길지 않으면 짧은 시간 안에 키를 찾아낼 수 있고 이를 이용해 공격자가 암호화된 데이터나 패스워드를 복호화할 수 있다.

㉡ 보안대책
RSA 알고리즘은 적어도 2,048비트 이상의 길이를 가진 키와 함께 사용해야 하고, 대칭암호화 알고리즘(Symmetric Encryption Algorithm)의 경우에는 적어도 128비트 이상의 키를 사용한다.

⑧ 적절하지 않은 난수 값 사용
㉠ 정의
예측 가능한 난수를 사용하는 것은 시스템에 보안약점을 야기시킨다. 예측 불가능한 숫자가 필요한 상황에서 예측 가능한 난수를 사용한다면, 공격자는 SW에서 생성되는 다음 숫자를 예상하여 시스템을 공격하는 것이 가능하다.

㉡ 보안대책
• 난수발생기에서 시드(Seed)를 사용하는 경우에는 예측하기 어려운 방법으로 변경한다.
• 일반적으로 Java에서는 java.lang.Math.random() 메소드 사용을 자제하고, java.util.Random 클래스를 사용, C에서는 rand() 대신 randomize(seed)를 사용하는 것이 좋다.
• 세션ID, 암호화키 등 보안 결정을 위한 값을 생성하고 보안결정을 수행하는 경우에는 java.security.SecureRandom 클래스를 사용한다.

⑨ 패스워드 평문 저장
㉠ 정의
패스워드를 설정파일에 암호화되지 않은 상태로 저장하게 되면, 암호가 외부에 직접적으로 드러날 위험성이 있다. 따라서 패스워드는 쉽게 접근할 수 없는 저장소에 저장하는지 아니면 암호화한 상태로 저장하여야 한다.

㉡ 보안대책
패스워드를 외부 환경 파일에 저장한다면, 암호화하여 저장한다.


⑩ 하드코드된 암호화 키
㉠ 정의
• 코드 내부에 하드코드된 암호화키를 사용하여 암호화를 수행하면 암호화된 정보가 유출될 가능성이 높아진다.
• 많은 SW 개발자들이 내부의 고정된 패스워드의 해쉬를 계산하여 저장하는 것이 패스워드를 악의적인 공격자로부터 보호할 수 있다고 믿고 있다. 그러나 많은 해쉬 함수들이 역계산이 가능하며 적어도 무차별 대입(Brute-Force) 공격에는 취약하다는 것을 고려해야 한다.

㉡ 보안대책
암호화 알고리즘에서 상수가 아닌 키를 사용해서 암호화를 수행하도록 설계하여야 하며, 암호화되었다고 패스워드를 상수의 형태로 프로그램 소스코드 내부에 저장하여 사용하면 안 된다.

⑪ 취약한 패스워드 허용
㉠ 정의
사용자에게 강한 패스워드 조합규칙을 요구하지 않으면 사용자 계정이 취약하게 된다. 안전한 패스워드를 생성하기 위해서는 숫자/문자/특수문자를 조합하여 9자리 이상으로 해야 한다.

㉡ 보안대책
패스워드 생성 시 강한 조건 검증을 수행한다. 비밀번호(패스워드)는 숫자와 영문자, 특수문자 등을 혼합하여 9자리 이상으로 정하고, 분기별로 1회 이상 주기적으로 변경 사용하도록 해야 한다.

⑫ 사용자 하드디스크에 저장되는 쿠키를 통한 정보노출
㉠ 정의
대부분의 웹 응용프로그램에서 쿠키는 메모리에 상주하며, 브라우저의 실행이 종료되면 사라진다. ‘프로그램을 위한 경우 브라우저 세션이 끝난 후에도 지속적으로 저장되도록 설정할 수 있으며 이것은 디스크에 기록되고 다음 브라우저 세션이 시작되었을 때 메모리에 로드된다.’ 개인정보, 인증정보 등이 영속적인 쿠키(Persistent Cookie)에 저장된다면 공격자는 쿠키에 접근할 수 있는 보다 많은 기회를 가지게 되며, 이는 시스템을 취약하게 만든다.

㉡ 보안대책
쿠키의 만료시간은 세션이 지속되는 시간과 관련하여 최소한으로 설정하고 영속적인 쿠키에는 사용자 권한 등급, 세션ID가 포함되지 않도록 한다.

⑬ 보안속성 미적용으로 인한 쿠키 노출
㉠ 정의
HTTPS로만 서비스하는 경우, 모든 정보가 암호화되어 안전하게 전송된다고 생각한다. 그러나 보안에 민감한 데이터를 브라우저 쿠키에 저장할 때 보안 속성을 설정하지 않으면 공격자에게 단순한 텍스트의 형태로 노출될 수 있다.

㉡ 보안대책
HTTPS로만 서비스하는 경우 브라우저 쿠키에 데이터를 저장할 때, 반드시 쿠키 객체의 setSecure(true) 메소드를 호출하여 보안속성을 설정한다. 한 사이트(도메인)에서 HTTP와 HTTP와 HTTPS를 함께 사용하는 경우 setSecure(true) 메소드를 호출하면 해당 쿠키가 HTTP를 통해서는 서버에 전송되지 않아 장애가 발생할 수 있으므로 주의해야 한다.










⑭ 주석문 안에 포함된 패스워드 등 시스템 주요정보
    ① 정의
        • 패스워드를 주석문에 넣어두면 시스템 보안이 훼손될 수 있다.
        • 소프트웨어 개발자가 편의를 위해서 주석문에 패스워드를 적은 경우, 소프트웨어가 완성된 후에는 그것을 제거하는 것이 매우 어렵게 된다. 또한 공격자가 소스코드에 접근할 수 있다면 아주 쉽게 시스템에 침입할 수 있다.
    ② 보안대책
        주석에는 ID, 패스워드 등 보안과 관련된 내용을 기입하지 않는다.

⑮ 솔트 없이 일방향 해시 함수 사용
    ① 정의
        패스워드 저장시 일방향 해시 함수의 성질을 이용하여 패스워드의 해시값을 저장한다. 만약 패스워드는 솔트(Salt) 없이 해시하여 저장한다면, 공격자는 레인보우 테이블과 가능한 모든 패스워드에 대해 해시값을 미리 계산하고, 이를 이용한 전수조사를 통해 패스워드를 찾을 수 있게 된다.
    ② 보안대책
        패스워드 저장시 패스워드와 솔트를 해시함수의 입력으로 하여 얻은 해시값을 저장한다.

⑯ 무결성 검증없는 코드 다운로드
    ① 정의
        원격으로부터 소스코드 또는 실행파일을 무결성 검사 없이 다운로드 받고 이를 실행하는 제품들이 종종 존재한다. 이는 호스트 서버의 변조, DNS스푸핑(Spoofing) 또는 전송 중의 코드 변조 등의 방법을 이용하여 공격자가 악의적인 코드를 실행할 수 있도록 한다.
    ② 보안대책
        • DNS스푸핑(Spoofing)을 방어할 수 있는 DNS lookup을 수행하고 코드 전송시 신뢰할 수 있는 암호기법을 이용하여 코드를 암호화한다.
        • 다운로드된 코드는 작업을 위해 필요한 최소한의 권한으로 실행하도록 한다. 이와 함께 자일(Jail) 또는 이와 유사한 샌드박스(Sandbox)환경에서 실행되도록 한다.

3. 시간 및 상태
    ① 경쟁조건 : 검사시점과 사용시점(TOCTOU)
        ① 정의
            • 병렬시스템(멀티프로세스로 구현한 응용프로그램)에서는 자원(파일, 소켓 등)을 사용하기에 앞서 자원의 상태를 검사한다.
            • 하지만 자원을 사용하는 시점과 검사하는 시점이 다르기 때문에 검사하는 시점(Time of Check)에 존재하던 자원이 사용하던 시점(Time of Use)에 사라지는 등 자원의 상태가 변하는 경우가 발생한다.
            • 하나의 자원에 대하여 동시에 검사시점과 사용시점이 달라 생기는 보안약점으로 인해 동기화 오류뿐 아니라 교착상태 등과 같은 문제점이 발생할 수 있다.
        ② 보안대책
            공유자원(예 파일)을 여러 프로세스가 접근하여 사용할 경우, 동기화 구문을 사용하여 한 번에 하나의 프로세스만 접근 가능하도록(Synchronized mutex 등)하는 한편, 성능에 미치는 영향을 최소화하기 위해 임계코드 주변만 동기화 구문을 사용한다.

    ② 제어문을 사용하지 않는 재귀함수
        ① 정의
            • 재귀의 순환회수를 제어하지 못하여 할당된 메모리나 프로그램 스택 등의 자원을 과다하게 사용하면 위험하다.
            • 대부분의 경우 귀납조건(Base Case)이 없는 재귀함수는 무한 루프에 빠져 듣게 되고 자원고갈을 유발함으로써 시스템의 정상적인 서비스를 제공할 수 없게 한다.
        ② 보안대책
            모든 재귀 호출시, 재귀 호출 수를 제한하거나 초기값을 설정(상수)하여 재귀 호출을 제한해야 한다.

4. 에러처리
    ① 오류메시지 통한 정보노출
        ① 정의
            • 응용프로그램이 실행환경, 사용자, 관련 데이터에 대한 민감한 정보를 포함하는 오류 메시지를 생성하여 외부에 제공하는 경우 공격자의 악성 행위를 도와줄 수 있다.
            • 예외 발생 시 에이전트이나 스택 트레이스를 출력하는 경우 프로그램 내부구조를 쉽게 파악할 수 있다.
        ② 보안대책
            • 오류메시지는 정해진 사용자에게 유용한 최소한의 정보만 포함하도록 한다.
            • 소스코드에서 예외 상황은 내부적으로 처리하고 사용자에게 민감한 정보를 포함하는 오류를 출력하지 않도록 미리 정의된 메시지를 제공하도록 설정한다.

    ② 오류 상황 대응 부재
        ① 정의
            오류가 발생할 수 있는 부분을 확인하였으나 이러한 오류에 대하여 예외처리를 하지 않을 경우 공격자는 오류 상황을 악용하여 개발자가 의도하지 않은 방향으로 프로그램이 동작하도록 할 수 있다.
        ② 보안대책
            오류가 발생할 수 있는 부분에 대하여 제어문을 사용하여 적절하게 예외처리(C/C++에서 if와 switch, java에서 try-catch 등)를 한다.

    ③ 적절하지 않은 예외처리
        ① 정의
            프로그램 수행 중에 함수의 결과 값에 대한 적절한 처리 또는 예외상황에 대한 조건을 적절하게 검사하지 않을 경우 예기치 않은 문제를 야기할 수 있다.
        ② 보안대책
            값을 반환하는 모든 함수의 결과 값을 검사하여 그 값이 기대한 값인지 검사하고 예외 처리를 사용하는 경우에 광범위한 예외처리 대신 구체적인 예외처리를 수행한다.

퍼징(Fuzzing)

1989년 Wisconsin대학 Madison 캠퍼스의 Barton Miller 교수가 개발한 퍼징(Fuzzing)은 임의로 발생시킨 데이터를 프로그램의 입력으로 사용하는 소프트웨어 테스트 기법이다.
이 방법의 목적은 프로그램 또는 함수가 비정상적인 입력을 올바르게 처리하는지 아니면 종료되거나 적절하지 못하게 반응하는지 등을 확인하는 것이다.
퍼징의 주요 장점은 단순성과 프로그램에 대한 예상 입력에 대한 가정으로부터 자유롭다는 것이다. 테스트를 위한 많은 데이터를 만들어내는 비용도 매우 적다. 각각 이런 테스트 프로그램의 보안 결점뿐만 아니라 신뢰성을 확인하는 데도 도움을 준다.
입력을 완전히 임의로 만들 수도 있지만 어떤 형판에 맞춰 임의로 만들 수도 있다. 이런 형판은 버그가 일어나리라를 검사하기 위해 설계된다. 예를 들면 매우 긴 입력, 공백이나 단어 경계가 없는 텍스트 입력 등이 있다. 네트워크 프로토콜에 대해 사용될 때, 이 형판은 프로토콜의 중요한 부분을 대상으로 할 수 있다. 이러한 형판은 버그를 찾을 가능성을 높여준다. 형판은 단순한 입력에 대한 가정을 한다는 것이다. 다른 형태의 입력에 의한 버그는 놓칠 수 있다. 따라서 이런 기법들의 결함을 통해 합리적인 입력의 범위를 정하는 것이 필요하다. 퍼징은 개념적으로 매우 간단한 테스트 방법이지만 제한적이고 자주 사용되어야 한다.


5. 코드오류
    ① 널(Null)포인터 역참조
        ① 정의
            • 널 포인터 역참조는 ‘일반적으로 그 객체가 널(Null)이 될 수 없다’라고 하는 가정을 위반했을 때 발생한다.
            • 공격자가 의도적으로 널 포인터 역참조를 발생시키는 경우 그 결과 발생하는 예외 상황을 이용하여 추후의 공격을 계획하는 데 사용될 수 있다.
        ② 보안대책
            널이 될 수 있는 레퍼런스(Reference)는 참조하기 전에 널 값인지를 검사하여 안전한 경우에만 사용한다.

    ② 부적절한 자원 해제
        ① 정의
            • 프로그램의 자원 열린 파일디스크립터(Open File Descriptor), 힙 메모리(Heap Memory), 소켓(Socket) 등은 유한한 자원이다.
            • 이러한 자원을 할당받아 사용한 후, 더 이상 사용하지 않는 경우에는 적절히 반환하여야 하는데 프로그램 오류 또는 에러로 사용이 끝난 자원을 반환하지 못하는 경우이다.
        ② 보안대책
            자원을 획득하여 사용한 다음에는 반드시 자원을 해제하여 반환한다.

6. 캡슐화
    ① 잘못된 세션에 의한 데이터 노출
        ① 정의
            • 다중 스레드 환경에서는 싱글톤(Singleton) 객체 필드에 경쟁조건(Race Condition)이 발생할 수 있다.
            • 따라서 다중 스레드 환경인 java의 서블릿(servlet) 등에서는 정보를 저장하는 멤버변수가 포함되지 않도록 하여, 서로 다른 세션에서 데이터를 공유하지 않도록 해야 한다.
        ② 보안대책
            싱글톤 패턴을 사용하는 경우, 변수 범위(Scope)에 주의를 기울여야 한다. 특히 Java에서는 HttpServlet 클래스의 하위클래스에서 멤버필드를 선언하지 않도록 하고 필요한 경우 지역 변수를 선언하여 사용한다.

    ② 제거되지 않고 남은 디버그 코드
        ① 정의
            디버그 코드는 설정 등의 민감한 정보를 담거나 시스템을 제어하게 허용하는 부분을 담고 있을 수 있다. 만일 남겨진 채로 배포될 경우 공격자가 식별과정을 우회하거나 의도하지 않은 정보와 제어 정보를 노출될 수 있다.
        ② 보안대책
            • SW배포 전 반드시 디버그 코드를 확인 및 삭제한다.
            • 일반적으로 Java개발자의 경우 웹 어플리케이션을 제작할 때 디버그용도의 코드를 main()에 개발한 후 이를 삭제하지 않는 경우가 많다. 디버깅이 끝나면 main() 메소드를 삭제해야 한다.

    ③ 시스템 데이터 정보 노출
        ① 정의
            시스템, 관리자, DB 정보 등 시스템의 내부 데이터가 공개되면 공격자에게 또 다른 공격의 빌미를 제공하게 된다.
        ② 보안대책
            일부 개발자의 경우 예외상황이 발생할 경우 시스템 메시지 등의 정보를 화면에 출력하도록 하는 경우가 많다. 예외상황이 발생할 때 시스템의 내부 정보가 화면에 출력하지 않도록 개발한다.

    ④ Public 메소드부터 반환된 Private배열
        ① 정의
            Private 배열을 Public메소드가 반환하면 배열 주소값이 외부에 공개됨으로써 외부에서 배열 수정이 가능해진다.
        ② 보안대책
            Private로 선언된 배열을 Public 메소드를 통해서 반환하지 않도록 하고 필요한 경우 배열의 복제본을 반환하거나 수정을 제어하는 별도의 Public 메소드를 선언하여 사용한다.

    ⑤ Private 배열에 Public 데이터 할당
        ① 정의
            Public으로 선언된 데이터 또는 메소드의 파라미터를 Private배열에 저장하면 Private배열을 외부에서 접근할 수 있다.
        ② 보안대책
            Public으로 선언된 데이터가 Private으로 선언된 배열에 저장되지 않도록 한다.

7. API 오류
    ① DNS lookup에 의존한 보안결정
        ① 정의
            공격자가 DNS엔트리를 속일 수 있으므로 도메인명에 의존해서 보안결정(인증 및 접근 통제 등)을 하지 않아야 한다. 만약 로컬 DNS서버의 캐시가 공격자에 의해 오염된 상황이라면 사용자와 특정 서버간의 네트워크 공격자를 경유하도록 할 수도 있다. 또한 공격자가 마치 동일 도메인에 속한 서버인 것처럼 위장할 수도 있다.
        ② 보안대책
            보안결정에서 도메인명을 이용한 DNS lookup을 하지 않도록 한다.
