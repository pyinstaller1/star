PGP (Pretty Good Privacy)
이메일 보안 표준
CA 없이 공개키 신뢰를 사용자에게 맡김

기밀성
송신자는 세션키로 메시지 암호화
수신자의 공개키로 세션키를 RSA 암호화
수신자는 자신의 개인키로 RSA 복호화 => 세션키
세션키로 메시지 복호화

인증
송신자는 메시지로부터 해시코드 생성
해시코드를 송신자의 개인키로 RSA 암호화(전자서명) => 메시지에 붙인다.
수신자는 송신자의 공개키로 RSA 복호화 => 해시코드
수신자는 메시지의 해시코드를 생성해서 비교


대칭키(세션키) 로 메시지 암호화
공개키 : 세션키 암호화
전자 서명 : 메시지 해시값을 송신자 개인키로 암호화
전자 서명 => ZIP압축 => 암호화
긴 메시지 단편화, 조립

개인키 링: 자신의 공개키, 개인키 쌍 관리
공개키 링: 다른 사용자의 공개키 관리
신뢰 링 : 불법 공개키 차단

(3) 명령 삽입 취약점

1) SQL 처리
① 클라이언트의 요청을 처리하기 위해 전송받는 인수에는 특정 명령을 실행할 수 있는 코드가 포함되는 경우가 있다.
② 이를 적절히 필터링하는 등의 처리 과정을 수행하지 못하는 경우 삽입 공격에 대한 취약점이 생긴다.
③ 명령 삽입 공격은 웹 서버와 연동되는 데이터베이스에 임의의 SQL 명령을 실행하여 데이터를 수집할 수 있기 때문에 위험도가 매우 높다.
④ 웹 서버는 서비스 이용자에게 인증, 게시판, 검색 등 다양한 정보를 제공하기 위해 대부분 데이터베이스와 연동되어 운영된다.
⑤ 웹 서버는 데이터베이스를 이용하기 위해 SQL 쿼리를 이용한다.
⑥ 웹 서버에서 데이터베이스로 전송되는 SQL 쿼리에는 아이디, 패스워드, 검색어 등 여러 가지 인수가 사용되는데, SQL 삽입 공격은 전송되는 인수에 추가적인 실행을 위한 코드를 넣는 것을 말한다.

2) SQL 삽입(Injection) 공격
① SQL 삽입(Injection)은 사용자가 입력하는 입력 값에 대한 유효성을 검증하지 않고 그대로 사용할 때 발생할 수 있는 데이터베이스와 관련된 보안 취약점이다.
② 데이터베이스로 전달되는 SQL 질의가 악의적으로 변조되어 사용자 인증을 우회하거나 데이터베이스에 저장된 데이터가 변조되거나 파괴될 수 있는 보안 공격이다.
③ 공격자가 웹 서버의 관리자 권한을 획득할 수 있으며 관리자 권한 획득을 이용하여 추가적인 보안 공격이 발생할 수 있다.


<정상적인 경우>
Select * From 학생 Where ID = 'admin' And PW = '진짜암호';

<SQL 삽입>
Select * From 학생 Where ID = "" Or 1=1 And PW = '아무거나';

④ 정상적인 경우 ID와 PW가 틀리면 반환하는 값이 없어야 한다.
⑤ SQL 삽입의 경우 특수 문자열 ‘Or 1=1’에 의해 SQL 질의문이 변조되어 ID와 PW가
   달라도 무조건 값을 반환하게 된다.

3) 보안책
① 매개변수를 이용한 바인딩 기법을 사용한다.
   Select * From 학생 Where ID = ? And PW = ?;

② 입력값에 대한 특수 문자 검증
   사용자 입력이 SQL 삽입을 발생시키지 않도록 사용자 입력 시 특수문자(‘, “, /,
   ;, :, --, +, 공백 등)가 포함되어 있는지 검사하여 허용되지 않는 문자열이나
   문자가 포함된 경우 제거한다.

(4) XSS, 크로스사이트 스크립트 취약점

1) 크로스사이트 스크립팅
① XSS(Cross Site Scripting)는 공격자에 의해 작성된 악성스크립트가 다른 사용자
   에게 전달되는 것이다.
② 웹 브라우저에서 사용자가 입력하는 입력값에 대한 유효성을 검증하지 않고 그대로
   웹 서버에 전송했을 때 발생하는 보안 취약점이다.
③ 공격자가 의도적으로 악성 스크립트를 웹 서버에 저장하는 것이 첫 번째 목적이다.
④ 다른 사용자의 웹 브라우저 내에서 적절한 검증 없이 실행되기 때문에 사용자의
   세션을 탈취하거나, 웹 사이트를 변조하거나 혹은 악의적인 사이트로 사용자를
   이동시킬 수 있다.
⑤ 이런 XSS는 일반적으로 자바 스크립트에서 발생하지만, VB 스크립트, Active
   X 등 클라이언트에서 실행되는 동적 데이터를 생성하는 모든 언어에서 발생할
   수 있다.

2) 동작 순서
① 임의의 XSS 취약점이 존재하는 서버에 XSS 코드를 작성하여 저장한다. 일반적으로
   공격자는 임의의 사용자 또는 특정인이 이용하는 게시판을 이용한다.
② 해당 웹 서비스 사용자가 공격자가 작성해놓은 XSS 코드에 접근한다. 물론 사용자는
   본인이 공격자가 작성해놓은 XSS 코드에 접근하는 것을 인지하지 못한다. 사용자는
   어떤 게시판의 글을 읽는 과정에서 공격자의 XSS 코드에 접근한다.

보충학습

XSS 공격 유형

1. Stored XSS
① 가장 일반적인 XSS 공격 유형으로, 단순히 게시판이나 자료실과 같이 사용자가
   글을 저장하는 부분에 정상적인 평문이 아닌 스크립트 코드를 입력하는 것이다.
② 다른 사용자가 게시물을 열람하는 순간 공격자가 입력해둔 악성 스크립트가 실행되어
   사용자는 자신의 쿠키 정보가 유출되거나 악성 스크립트가 기획한 공격에 당하게
   된다.

2. Reflected XSS
① 반사 XSS 공격은 웹 애플리케이션에 스크립트를 저장하는 것이 아니라 URL의 변수
   부분처럼 스크립트 코드를 입력하는 동시에 결과가 바로 존재하는 공격기법이다.
② 공격자는 스크립트가 포함된 공격 URL을 다른 웹사이트, 이메일 등으로 보내서
   다른 사용자가 그것을 클릭하도록 유도한다.


(5) 취약한 인증 및 세션 관리

1) 인증 기능 취약
① 인증(authentication)은 현재 요청을 보낸 사용자가 시스템의 실제 사용자인지를
   확인하는 과정이다.
② 적절한 인증 없이 중요 기능이 허용되는 경우 보안 위험이 된다.
③ 취약한 인증의 가장 기본적인 문제점은 패스워드 설정이다.
④ 웹뿐만 아니라 패스워드를 사용하는 모든 운영체제와 응용 프로그램에 공통적으로
   해당하는 문제이다.
⑤ 웹에서는 취약한 계정을 사용하는 것이 좀 더 심각한 경우가 많은데, 이는 기본적으로
   개발자와 사용자가 동일하지 않기 때문이다.
⑥ 관리자 패스워드의 변경 인터페이스가 별도로 만들어져 있지 않고, 데이터베이스를
   직접 변경하는 것과 같이 원시적인 형태를 갖는 경우가 많기 때문에 사용자는
   최초 개발자가 설정해놓은 패스워드를 그대로 쓸 때가 많다.
⑦ 개발자 역시 개발 과정에서는 패스워드에 많은 신경을 쓰지 않기 때문에 웹에서는
   의외로 admin/admin과 같이 취약한 패스워드를 많이 발견할 수 있다.

2) 부적절한 인가
① 인가(Authorization)는 사용자의 자원에 대한 접근 혹은 사용을 허용하는 과정
   이다.
② 로그인에 성공한 사용자가 어떤 행위를 하려할 때, 허용을 결정하는 과정으로
   인가 여부를 확인하는 절차가 없을 때 보안 위험이 된다.


DOM 기반 XSS 공격

DOM 기반 XSS 공격은 2005년에 처음으로 아미르 카밀(Amir Kamil)이 관련 취약점
논문을 발표하면서 알려졌다. 피해자의 브라우저가 HTML 페이지를 주문 분석할 때마다
공격 스크립트가 DOM 생성의 일부로 실행되면서 공격한다. 페이지 자체는 변하지 않지만,
페이지에 포함되어 있는 브라우저측 코드가 DOM 환경에서 악성코드로 실행된다.

앞에서 다룬 저장 XSS 및 반사 XSS 공격의 악성 페이로드가 서버 측 애플리케이션
취약점으로 인해, 응답 페이지에 악성 스크립트가 포함되어 브라우저로 전달되면서
공격하는 것이 반면, DOM 기반 XSS는 서버와 관계없이 브라우저에서 발생하는 것이
차이점이다.


(6) 직접 객체 참조

① 직접 객체 참조는 파일, 디렉터리, 데이터베이스 키와 같이 내부적으로 구현된
   객체에 대한 참조가 노출될 때 발생한다.
② 접근 통제에 의한 확인이나 다른 보호조치가 없다면 공격자는 권한 없는 데이터에
   접근하기 위해 노출된 참조를 조작할 수 있다.

1) 경로 조작(Path Traversal)
① 경로 조작(Path Traversal)은 사용자가 입력하는 입력 값에 대한 유효성을 검증
   하지 않고 그대로 사용할 때 발생하는 서버 시스템 자원 접근에 대한 보안 취약점
   이다.
② 경로 조작 취약점을 악의적으로 활용하여 사용자가 접근해서는 안되는 서버의
   중요한 파일을 내려받거나 삭제할 수 있다.
③ 입력값에 부모 폴더를 의미하는 '..'이라는 특수문자열을 사용한다.
④ 사용자에게 내려받을 대상 파일 이름을 매개 변수 값으로 전달받을 경우 공격자가
   파일 이름에 특수 문자열 '..'을 추가하여 시스템 내부의 임의의 파일을 내려 받을
   수 있다.
⑤ 보안책은 입력 값에 대한 특수 문자를 검증하는 것이다.

2) 파일 업로드 제한 부재
① 유효성 점검의 대상이 사용자가 업로드하려는 파일이므로 사용자가 보내는 파일에
   대해 유효성 점검을 하지 않을 때 발생할 수 있는 보안 취약점이다.
② 공격자는 웹서버에 악의적인 파일을 전송하고, 원격지에서 해당 파일을 실행하여
   웹 서버를 장악하며 추가적인 내부 침투 공격을 수행할 수 있게 되기 때문이다.
③ 웹 해킹의 최종 목표인 리버스 텔넷과 같은 웹 서버의 통제권을 얻기 위해 반드시
   성공해야 하는 공격이다.
④ 이런 취약점의 가장 일반적인 형태는 게시판이다.
⑤ 게시판에 첨부파일로 악의적인 파일을 업로드하고 실행시키며 이 때 첨부파일로
   업로드하는 악성코드는 대부분 웹 쉘(Web Shell)이다.
⑥ 웹 쉘은 웹 서버를 기반으로 서버에 파일이 업로드되고 실행되기 때문에 서버
   쪽에서 실행되는 파일을 말한다.
⑦ 화이트리스트 방식으로 업로드가 가능한 파일 형식을 미리 정의해 놓고 허용된
   형식의 파일에 대해서만 업로드가 가능하도록 한다.
⑧ 일차적으로 웹 쉘 파일의 업로드를 막는다.

웹쉘(Webshell)

1. 특징
① 웹쉘(Webshell)이란 클라이언트의 명령을 서버에서 실행시켜주는 프로그램이다.
② 웹쉘은 공격자가 악의적인 목적을 가지고 만든 프로그램으로, 주로 주로 ASP, PHP,
   JSP 등을 사용한다.
③ 웹쉘이 완성되면, 취약점이 존재하는 서버에 업로드시키고 공격자가 만든 웹쉘이
   성공적으로 서버에 업로드가 된다면, 공격자는 자신이 서버에서 실행시키고자 하는
   명령어를 전송하여, 서버에서 실행이 되게 한다.
④ 즉, 공격자는 해당 서버의 모든 제어권을 장악하고, 정보탈취, 변조, 악성코드
   삽입 등 각종 악성행위를 한다.
⑤ 웹쉘공격은 HTTP서비스를 통하여 통신을 하기 때문에 탐지가 어려우며, 제작이 비교적
   쉽고 서버에서 관리자용 용이하기 때문에 흔히 사용되는 공격방법이다.

② 취약점 패치
③ 키워드/명령어 필터링

3) 리버스 텔넷

① 리버스 텔넷(Reverse Telnet)은 웹 해킹을 통해 시스템의 권한을 획득한 후 해당 시스템에 텔넷과 같이 직접 명령을 입력하고 확인할 수 있는 쉘을 획득하기 위한 방법으로, 방화벽이 존재하는 시스템을 공격할 때 자주 사용된다.

② 일반적으로 웹 서버는 방화벽 내부에 존재하는데, 웹 서버는 80번 포트를 이용한 웹 서비스만 제공하면 되기 때문에 방화벽은 외부 인터넷을 사용하는 사용자에 대해 80포트만을 허용한다. 이런 경우에는 웹 서버의 텔넷이 열려 있어도 방화벽으로 인해 공격자가 외부에서 접근할 수 없다.

③ 보안측으로 파일 업로드를 먼저 막아야 한다.

④ 외부에서 내부로의 접속뿐만 아니라 내부에서 외부로의 불필요한 접속도 방화벽으로 막는 것이 좋다.

⑤ 서버에서 본인의 컴퓨터로 원격접속하게 하는 기술이다.


(7) CSRF 취약점

① CSRF(Cross Site Request Forgery)는 특정 사용자를 대상으로 하지 않고, 불특정 다수를 대상으로 로그인된 사용자가 자신의 의지와는 무관하게 공격자가 의도한 행위(수정, 삭제, 등록, 송금 등)를 하게 만드는 공격이다.

② CSRF는 기본적으로 XSS 공격과 매우 유사하며 XSS 공격의 발전된 형태라고 보기도 한다. 하지만 XSS 공격은 악성 스크립트가 클라이언트에서 실행되는 데 반해, CSRF 공격은 사용자가 악성 스크립트를 서버에 요청한다는 차이가 있다.

(8) 보안 설정 취약점

1) 디렉터리 리스트

① 디렉터리 리스팅(Directory Listing)은 웹 브라우저에서 웹 서버의 특정 디렉터리를 열면 그 디렉터리에 있는 파일과 목록이 모두 나열되는 것을 의미한다.

② 관리자가 특정 디렉터리를 리스팅이 가능하도록 일부러 설정하는 경우도 있다.


2) 백업 및 임시 파일 존재

개발자들이 웹 사이트를 개발하고 난 후 웹 서버에 백업 파일이나 임시 파일들을 삭제하지 않은 채 방치하는 경우 공격자가 백업 파일을 발견하면 웹 애플리케이션의 내부로직 및 데이터베이스 접속 정보 등 중요한 정보를 획득할 수 있다.


3) 주석 관리 미흡

① 일반적으로 프로그램의 주석은 개발자만 볼 수 있으나, 웹 어플리케이션의 경우에는 웹 프록시를 통해 이용자도 볼 수 있다.

② 주석에는 개발 과정이나 웹 어플리케이션의 관리 목적으로 주요 로직에 대한 설명, 디렉터리 구조, 테스트 소스 정보, 심지어는 아이디와 패스워드 등의 여러 가지 정보가 기록될 수 있다.


[보충학습] 웹 방화벽

웹 해킹을 방어하기 위한 웹 서버에 특화된 방화벽이다.
일반 방화벽에서는 탐지하지 못하는 웹 관련 공격 경로를 감시하고 공격이 웹 서버에 도달하기 전에 차단해 주는 보안 제품이다.
웹 방화벽의 기본 역할은 SQL Injection, Cross-Site Scripting(XSS) 등과 같은 웹 공격을 탐지하고 차단하는 것인데, 직접적인 웹 공격 대응 이외에도, 정보유출방지솔루션, 부정로그인방지솔루션, 웹사이트 위변조방지 솔루션 등으로 활용이 가능하다.
애플리케이션의 계층 분석 기술과 정규화 기술을 바탕으로 한 특화된 검사 엔진을 탑재한 보안 구성 요소이다.
URL에 따른 접근 제어 기능과 SSL 트래픽을 자체적으로 복호화 검사하여 기존의 보안 시스템을 보완한다.
네트워크 기반 방화벽과 웹 서버 기반 방화벽으로 구분된다.


[웹셀(Webshell)]

1. 특징

① 웹쉘(Webshell)이란 클라이언트의 명령을 Shell에서 실행시켜주는 프로그램이다.

② 웹쉘은 공격자가 악의적인 목적을 가지고 만든 프로그램으로, 주로 주로 RSS(Server Side Script) 언어인 ASP, PHP, JSP 등을 사용한다.

③ 웹쉘이 완성되면, 취약점이 존재하는 서버에 업로드시키고 공격자가 만든 웹쉘에 성공적으로 서버에 업로드가 된다면, 공격자는 자신이 서버에서 실행시키고자 하는 명령을 웹쉘을 통해서 실행이 되게 한다.

④ 즉, 공격자는 해당 서버의 모든 제어권을 장악하고, 정보탈취, 변조, 악성코드 삽입 등 각종 악성행위를 한다.

⑤ 웹쉘 공격은 HTTP서비스를 통하여 통신을 하기 때문에 탐지가 어렵고, 제작이 비교적 쉽고 서버에서 어드민과 공유하기 때문에 흔히 사용되는 공격방법이다.

3) 리버스 텔넷

① 리버스 텔넷(Reverse Telnet)은 웹 해킹을 통해 시스템의 권한을 획득한 후 해당 시스템에 텔넷과 같이 직접 명령을 입력하고 확인할 수 있는 쉘을 획득하기 위한 방법으로, 방화벽이 존재하는 시스템을 공격할 때 자주 사용된다.

② 일반적으로 웹 서버는 방화벽 내부에 존재하는데, 웹 서버는 80번 포트를 이용한 웹 서비스만 제공하면 되기 때문에 방화벽은 외부 인터넷을 사용하는 사용자에 대해 80포트만을 허용한다. 이런 경우에는 웹 서버의 텔넷이 열려 있어도 방화벽으로 인해 공격자가 외부에서 접근할 수 없다.

③ 보안측으로 파일 업로드를 먼저 막아야 한다.

④ 외부에서 내부로의 접속뿐만 아니라 내부에서 외부로의 불필요한 접속도 방화벽으로 막는 것이 좋다.

⑤ 서버에서 본인의 컴퓨터로 원격접속하게 하는 기술이다.


(7) CSRF 취약점

① CSRF(Cross Site Request Forgery)는 특정 사용자를 대상으로 하지 않고, 불특정 다수를 대상으로 로그인된 사용자가 자신의 의지와는 무관하게 공격자가 의도한 행위(수정, 삭제, 등록, 송금 등)를 하게 만드는 공격이다.

② CSRF는 기본적으로 XSS 공격과 매우 유사하며 XSS 공격의 발전된 형태라고 보기도 한다. 하지만 XSS 공격은 악성 스크립트가 클라이언트에서 실행되는 데 반해, CSRF 공격은 사용자가 악성 스크립트를 서버에 요청한다는 차이가 있다.

07 코드 공격

(1) 버퍼 오버플로 공격

1) 버퍼 오버플로 개요
① 버퍼는 하드웨어 장치나 프로그램이 사용하는 임시 메모리 공간을 말한다.
② 운영체제의 통제 하에 프로그램이 메모리에 적재되어 프로세스로서 작성된 코드를 실행할 때, 메모리 공간을 여러 목적의 구역으로 나누어 사용하는데 이 중 일부가 버퍼에 해당한다.
③ 버퍼 오버플로는 버퍼로 사용하는 메모리 공간의 관리 문제로 일어나는 문제로, 프로세스가 버퍼를 사용할 때 원래 할당받은 영역에 대한 관리나 통제 소홀로 인해 그 경계를 초과한 공간으로 데이터가 침범하는 상황을 말한다.
④ 이를 악의적으로 이용할 경우 특정 동작을 수행하도록 흐름을 제어할 수도 있다.
⑤ 스택 구역은 프로그램을 함수라는 모듈의 집합으로 볼 때, 함수의 진행에 따라 함수 내에서 사용할 데이터, 함수에 필요한 인자, 함수의 결과 등을 저장할 공간으로 사용한다.
⑥ 스택에는 프로그램 진행의 흐름과 내용이 담겨있다.

2) 셸과 SetUID

버퍼 오버플로를 이용한 기법은 운영체제의 허점 등의 비정상적인 경로를 사용하는 방법이다.

① 셸과 셸코드
㉠ 셸(shell)은 사용자가 운영체제를 사용하기 위한 인터페이스로, 입력받은 명령어를 해석하여 실행하는 역할을 한다.
㉡ 일단 셸이 실행되면, 해당 계정의 권한에 허용된 모든 프로그램을 실행할 수 있다.
㉢ 일반 사용자라면 시스템 환경설정이나 프로그램 설치 등에 상당한 제약을 받지만, 관리자 계정의 셸 실행이 가능하다면 어떤 제약도 없으므로 이는 버퍼 오버플로를 이용한 기법의 일차적인 목표가 된다.
㉣ 일반적인 프로그램의 내부에서 셸을 직접 실행할 필요가 많지 않기 때문에, 버퍼 오버플로를 이용한 기법에서는 대부분 프로그램의 명령 코드에 셸을 강제로 실행할 수 있는 기계어 코드를 삽입하는데, 이를 셸코드(shellcode)라고 한다.

② SetUID
㉠ 각각 0인 UID와 GID를 갖는 루트 권한은 제약없이 모든 사용자의 파일 및 영역에 접근할 수 있다.
㉡ SetUID가 설정된 파일은 실행 권한 문자가 ‘s’임을 확인할 수 있다.




㉢ SetUID가 설정된 파일은 실행될 때, 실행한 주체에 관계없이 임시적으로 그 실행 파일의 소유자 권한을 갖는다.
㉣ 해당 파일의 소유자가 관리자라면 해당 파일을 실행하는 사람은 임시적으로 관리자의 권한을 얻을 수 있다는 것이다.
㉤ SetUID는 해당 파일의 소유자, 또는 관리자 권한을 가진 계정이 설정될 수 있다.

3) 버퍼 오버플로를 이용한 기법
① 스택과 프로그램 흐름을 관리한다면 현재 함수를 종료할 때 돌아갈 위치(RET : return address)가 필수적이다.
② 함수 내에서 사용되는 변수들은 스택 구역에 관리되는데 이러한 변수를 해당 함수의 지역 내에서만 사용한다고 하여 지역 변수(local variable)라고 한다.
③ 지역 변수와 RET 같은 함수 하나에 종속적이므로 체계적으로 관리하기 위해 함수의 구역을 나눠주는 작업이 필요하고, 이러한 구역을 스택 프레임(stack frame)이라 한다.
④ 스택 프레임의 관리를 위해 각 스택 프레임의 시작점 위치(SFP : stack frame pointer)를 따로 두고 지역 변수는 이 위치를 기준으로 번지를 정하여 사용한다.
⑤ 새로운 함수의 스택 프레임에 대한 SFP를 지정하기 위해서는 현재 스택의 크기를 항상 유지해야 한다.
⑥ 따라서 CPU의 스택 포인터 레지스터(SP : stack pointer register)에 항상 스택의 끝 위치 값을 유지하고 있으며, 함수 호출 시 호출 대상 함수의 SFP값으로 사용된다.
⑦ 스택 버퍼 오버플로를 이용한 기법은 함수 호출 시의 이러한 스택 변화 특성을 이용한다.
⑧ 함수의 실행이 종료되면 SFP를 복구하고 RET에 들어있는 주소로 복귀하는 것이 통상적인 흐름이다.
⑨ 그런데 프로그램의 오류에 의해 크기가 정해져 있는 지역 변수에 크기가 벗어난 데이터를 넣어서 RET 영역을 덮어 쓴다면, 통상적으로 RET가 가리키는 곳에 제대로 된 명령이 없기 때문에 프로그램이 비정상 종료될 것이다.
⑩ 스택 버퍼 오버플로를 이용한 기법에서는 이 RET 영역에 의도한 명령을 실행할 코드가 들어있는 주소값을 집어 넣으며, 일반적으로 셸을 실행할 수 있는 셸코드가 들어 있다.
⑪ 만약 관리자 권한으로 SetUID가 설정된 프로그램이라면 해당 프로그램을 결국 관리자 권한을 갖고 있는 셸을 실행하게 될 것이다.














4) 스택 버퍼 오버플로를 이용한 절차

① 셸코드와 같은 특정 코드를 메모리의 임시 공간에 저장한다.
② 여러 방법으로 해당 프로그램의 스택 크기를 추정하여, 버퍼 오버플로에 취약한 함수가 실행될 때, RET 영역을 덮어씌울 수 있는 인자값을 집어 넣는다. 이때 RET 영역에 들어갈 주소는 ①에서 저장한 임시 공간의 주소이다.
③ 해당 함수의 실행이 끝날 때, RET 영역에 들어간 주소의 코드가 실행될 것이다.

5) 정리

① C언어에서는 정수, 실수와 같은 지역 변수의 타입과 크기를 체크하기 때문에 일반적으로 이런 일이 일어날 수 없으나, 특정 함수의 경우 변수를 사용하면서 그 크기를 체크하지 않고 단지 특정 숫자(일반적으로 0)로 끝을 나타내는 방식을 사용하기 때문에 버퍼 오버플로를 이용한 기법의 대상이 된다.
② 문자열을 복사하거나 비교하는 strcpy(), strcat() 함수들이 그 예인데, 최근에는 이러한 함수들을 사용할 때 경고 메시지를 띄우고 다른 함수를 사용하기를 권장하고 있다.
③ 운영체제 차원에서도 스택가드(stack guard)를 두어 스택이 임의의 접근에 의해 조작되었는지 검사하여 실행을 거부한다. 스택가드는 Canary 값을 스택에 넣는다.
④ 스택 조작을 막기 위해 스택 위치를 랜덤으로 위치시키는 방어 기법이 도입되고 있다.
⑤ 스택쉴드(stack shield)는 리턴주소를 다른 곳으로 옮겨 덮어쓰기 힘들게 한다.

[심화학습]
버퍼 오버플로 공격 대응책

1. Non-Executable 스택
스택에서 프로그램을 실행할 수 없도록 한다. 즉 스택에서의 x(execute) 권한을 제거한다.

2. 스택가드(Stack Guard)
컴파일러가 프로그램의 함수 호출 시에 RET 앞에 Canary 값을 주입하고, 종료 시에 이 Canary 값이 변조되었는지의 여부를 확인하여 공격을 탐지한다.

3. 스택쉴드(Stack Shield)
함수 호출 시 RET를 Global RET 스택이라는 특수 스택에 저장하고 함수의 종료 시 Global RET 스택에 저장된 RET 값과 스택의 RET 값을 비교하여 일치하지 않으면 프로그램을 종료한다.

4. ASLR(Address Space Layout Randomization)
스택, 힙, 라이브러리 등의 데이터 영역 주소 등을 난수화하여 프로세스의 주소 공간에 배치하는 것으로 리눅스 커널 2.6.12 이후 적용되었다.



버퍼 오버플로에 취약한 함수

① strcpy(char *dest, const char *src);
② strcat(char *dest, const char *src);
③ getwd(char *buf);
④ gets(char *s);
⑤ scanf(const char *format, ...);
⑥ realpath(char *path, char resolved_path[]);
⑦ sprintf(char *str, const char *format);

Canary 종류

• Random Canary : Canary 값 변경, 이전 사용한 Canary 값 사용 못함
• Null Canary : Canary에 NULL 포함
• Terminator Canary : Canary에 함수 종료값을 조합한 값 포함

힙 버퍼 오버플로

힙(heap)에 저장되는 데이터를 변조하거나, 함수에 대한 포인터 값을 변조함으로써 RET 값을 변조하여 임의의 코드를 실행하는 공격

rtl 공격

스택에 있는 RET 주소를 실행 가능한 임의의 주소(libc 영역의 주소)로 돌려 원하는 함수를 수행하게 만드는 기법이다. 메모리에 적재된 공유 라이브러리는 스택에 존재하는 것이 아니므로 Non-Executable 스택을 우회하는 것이 가능하다.

(2) 포맷 스트링 공격

1) 포맷 스트링 개요

① 포맷 스트링(format string)이란 출력하려는 데이터의 형태를 기술한 문자열이다.
② 포맷 스트링은 %로 시작하는 지시자를 사용함으로써 구성되고, 포맷형에 들어갈 데이터 변수를 설정함으로써 문자열 출력이 구성된다.
③ 포맷 스트링 없이 printf() 계열의 함수를 사용할 경우 데이터 변수를 검사 없이 출력에 적용하게 된다.
④ 이때 데이터 변수 내용에 %로 시작하는 지시자가 있는 경우 printf()는 이를 포맷 스트링으로 해석하여 출력한다.
⑤ printf()는 인자로 필요한 데이터 변수가 지정되지 않더라도 그 위치를 변수 형식에서 자동 계산하여 인자로 집어넣기 때문에 오류가 발생하지 않는다.

2) 포맷 스트링 공격

① printf()라는 출력함수에서 변수의 값을 변경시킬 수 있는 방법을 제공한다고 볼 수 있다.
② 포맷 스트링이 제대로 지정되었다면 문제가 발생하지 않겠지만, 그렇지 않을 경우 printf()에 이 지시자가 포함된 인수를 넣어 스택 버퍼 오버플로를 이용한 기법과 비슷한 효과를 얻을 수 있다.
③ 실행 파일의 기계어 코드를 분석하는 디스어셈블(disassemble)과 포맷 스트링이 없는 printf() 등을 이용해 메모리 내용을 출력하여 코어 덤프(core dump)를 분석하면 main() 함수의 스택 프레임 크기를 추산할 수 있다.
④ 이를 이용하여 printf() 이후에 돌아올 RET의 위치를 알 수 있다.
⑤ %n에 해당하는 인자에 RET의 주소를 넣고, 그 전에 다른 지시자를 다수 조합하여 셸코드가 담긴 주소값만큼 문자열을 출력하게끔 조정하면 RET의 영역에 셸코드의 주소값이 들어가게 된다.
⑥ 포맷 스트링 공격은 데이터의 형태와 길이에 대한 불명확한 정의로 인한 문제점 중 ‘데이터 형태에 대한 불명확한 정의로 인한 것이다.

(3) 레이스 컨디션 공격

1) 레이스 컨디션 개요

① 멀티태스킹을 지원하는 일반적인 운영체제에서는 여러 개의 프로세스를 동시에 실행하는 것과 같은 효과를 얻기 위해, 각 프로세스에 CPU 시간을 배분한다.
② 프로세스 입장에서 보면 한정된 자원인 CPU를 차지하기 위해 동시에 여러 프로세스들이 경쟁을 벌이는 것인데, 이를 레이스 컨디션(race condition)이라 한다.
③ 시스템 위험에서 레이스 컨디션을 이용한 기법은 임시 파일을 생성하면서 SetUID가 설정된 프로그램과 심볼릭 링크를 이용한다.

레이스 컨디션 필요 조건

• 공격대상 프로그램의 소유자가 root여야 한다.
• 공격대상 프로그램이 SetUID 비트를 가져야 한다.
• 생성되는 임시파일의 이름을 알고 있어야 한다.

2) 심볼릭 링크

① 유닉스, 리눅스에서는 하나의 파일에 다른 이름을 주는 다음과 같은 방법이 있다.
㉠ 하드 링크(hard link) : 파일의 상세 정보가 담겨져 있는 메타 정보를 복사하고 파일의 실제 데이터에 연결(link)하는 것이다.
㉡ 심볼릭 링크(symbolic link) : 새로운 파일을 만들고 이 파일은 어떤 경로의 파일에 연결되어 있다는 정보만 기록한다.

② 심볼릭 링크는 원래 파일이 새로운 파일로 변경되어도 경로만 같으면 상관없으므로, 파일의 업데이트를 별다른 변경 절차 없이 이용할 수 있어 많이 사용된다.

3) 심볼릭 링크를 이용한 기법

① 시스템의 어떤 실행 파일에 관리자 권한의 SetUID가 설정되어 있고, 이 파일은 임시 디렉터리에 임시 파일을 생성한다고 가정한다.
② 임시 디렉터리를 관찰하면 임시 파일의 이름을 쉽게 알아낼 수 있으므로, 실행 파일이 임시 파일을 생성하기 전에 해당 파일의 이름으로 심볼릭 링크를 생성한다.
③ 리눅스, 유닉스는 파일을 열 때 생성 단계에서 파일이 존재할 경우 이를 그대로 사용한다.
④ 실행 파일이 심볼릭 링크에 대한 대처를 하지 않을 경우, 실제 조작되는 파일은 심볼릭 링크를 걸어놓은 파일이 된다.
⑤ 중요한 설정 파일을 연결해 놓을 경우 임의의 데이터가 덮어써져서 시스템의 비정상적인 동작을 유발할 수 있고, 관리자 권한으로 어떤 파일을 작성하게 할 수 있다.
⑥ 심볼릭 링크를 이용한 공격을 막기 위해 프로그램 작성자들은 임시 파일을 생성하기 전에 파일이 이미 생성되어 있는지 조사하고, 링크가 걸려있는 파일이면 삭제한다.

소프트웨어 개발 보안 적용 사례

① MS-DL(Microsoft-Secure Development Lifecycle)
마이크로소프트사는 보안수준이 높은 안전한 소프트웨어를 개발하기 위해 자체수립한
SDL(Secure Development Lifecycle) 방법론을 적용하였으며, SDL이 적용된 소프트
웨어는 이전 버전에 비해 50% 이상 취약점이 감소하였다고 발표했다.

② Seven Touchpoints
Seven Touchpoints는 실무적으로 검증된 개발보안 방법론 중 하나로서 소프트웨어
보안의 모범 사례를 소프트웨어 개발 라이프사이클에 통합했다.
공통 위협요소를 파악하고 이해하며, 보안을 설계하고 모든 소프트웨어 산출물에 대해
철저하고 객관적인 위험분석 및 테스트를 거쳐 안전한 소프트웨어를 만들어내는 방법을
정의하고 있다.
이러한 보안활동을 수행하는 동안 소프트웨어 위험요소에 대해서 위험관리 프레임워크에
따라 명시적으로 추적하고 모델링을 수행한다.

③ CLASP(Comprehensive, Lightweight Application Security Process)
SW개발보안 방법론 중 하나인 CLASP는 소프트웨어 개발 생명주기(SDLC) 초기단계에
보안강화를 목적으로 하는 정형화된 프로세스로서, 활동중심ㆍ역할기반의 프로세스로
구성된 집합체이다.
이미 운영 중인 시스템에 적용하기 좋다.


심화학습
소프트웨어 보안 취약점

1. 입력데이터 검증 및 표현

① SQL 삽입

㉠ 정의
데이터베이스(DB)와 연동된 웹 어플리케이션에서 입력된 데이터에 대한 유효성
검증을 하지 않을 경우, 공격자가 입력 폼 및 URL 입력란에 SQL 문을 삽입하여
DB로부터 정보를 열람하거나 조작할 수 있는 보안약점을 말한다.

㉡ 보안대책
• Prepared Statement객체 등을 이용하여 DB에 컴파일된 쿼리문(상수)을 전달
  하는 방법을 사용한다.
• Parameterized Statement를 사용하는 경우에는 DB쿼리에 사용되는 외부 입
  력값에 대하여 특수문자 및 쿼리 예약어를 필터링한다.

㉢ 스트러츠(Struts), 스프링(Spring)등과 같은 프레임워크를 사용하는 경우에는
외부 입력값 검증 모듈 및 보안 모듈을 상황에 따라 적절하게 사용한다.

② 자원삽입

㉠ 정의
외부 입력값을 검증하지 않고 시스템 자원(Resource)에 대한 식별자로 사용하는
경우, 공격자는 입력값 조작을 통해 시스템이 보호하는 자원에 임의로 접근하거나
수정할 수 있고 잘못된 입력값으로 인해 시스템 자원간 충돌이 발생할 수
있다.


㉡ 보안대책
• 외부의 입력을(파일, 소켓의 포트 등) 식별자로 사용하는 경우, 적절한 검증을
  거치도록 하거나 사전에 정의된 적합한 리스트에서 선택되도록 작성한다.
• 외부의 입력이 파일인 경우에는 경로순회(Directory Traversal)를 수행할
  수 있는 문자를 제거한다.

③ 크로스사이트 스크립트

㉠ 정의
웹 페이지에 악의적인 스크립트를 포함시켜 사용자 측에서 실행되게 유도할 수
있다. 예를 들어, 검증되지 않은 외부 입력이 동적 웹페이지 생성에 사용될 경우,
전송된 동적 웹페이지를 열람하는 접속자의 권한으로 부적절한 스크립트가 수행
되어 정보유출 등의 공격을 유발할 수 있다.

㉡ 보안대책
• 일반적인 경우에는 사용자가 문자열에 스크립트를 삽입하는 것을 막기 위해
  사용자가 입력한 문자열에서 <, >, &, " 등의 문자 변환 함수나 메소드를
  사용하여 &lt, &gt, &amp, &quot로 치환한다.
• HTML 태그를 허용하는 게시판에서는 게시판에서 지원하는 HTML 태그의 리
  스트(White List)를 선정한 후, 해당 태그만 허용하는 방식을 적용한다.

④ 운영체제 명령어 삽입

㉠ 정의
• 적절한 검증절차를 거치지 않은 사용자 입력값이 운영체제 명령어의 일부 또는
  전부로 구성되어 실행되는 경우, 의도하지 않은 시스템 명령어가 실행되어
  부적절하게 권한이 변경되거나 시스템 동작 및 운영에 악영향을 미칠 수 있다.
• 일반적으로 명령어 라인의 파라미터나 스크립트 입력 등 외부 입력을 사용하여
  시스템 명령어를 생성하는 프로그램이 많이 있다. 하지만 이러한 경우 외부
  입력 문자열은 신뢰할 수 없기 때문에 적절한 처리를 해주지 않으면, 공격자가
  원하는 명령어 실행이 가능하게 된다.

㉡ 보안대책
• 웹 인터페이스를 통해 서버 내부로 시스템 명령어를 전달시키지 않도록 어플리
  케이션을 구성하고, 외부에서 전달되는 값을 검증없이 시스템 내부 명령어로
  사용하지 않는다.
• 외부 입력에 따라 명령어를 생성하거나 선택이 필요한 경우에는 명령어 생성에
  필요한 값들을 미리 지정해 놓고 외부 입력에 따라 선택하여 사용한다.

⑤ 위험한 형식 파일 업로드

㉠ 정의
서버측에서 실행될 수 있는 스크립트 파일(asp, jsp, php 파일 등)이 업로드 가능
하고, 이 파일을 공격자가 웹을 통해 직접 실행시킬 수 있는 경우, 시스템 내부명령
어를 실행하거나 외부와 연결하여 시스템을 제어할 수 있는 보안약점이다.

㉡ 보안대책
• 화이트리스트 방식으로 허용된 확장자만 업로드를 허용한다.
• 업로드 되는 파일을 저장할 때에는 파일명과 확장자를 외부사용자가 추측할
  수 없는 문자열로 변경하여 저장하며, 저장 경로는 ‘web document root’ 밖에
  위치시켜서 공격자의 웹을 통한 직접 접근을 차단한다.
• 파일 실행 여부를 설정할 수 있는 경우, 실행 속성을 제거한다.

⑥ 신뢰되지 않는 URL 주소로 자동 접속 연결

㉠ 정의
• 사용자로부터 입력되는 값을 외부사이트의 주소로 사용하여 자동으로 연결하는
  서버 프로그램은 피싱(Phishing) 공격에 노출되는 보안약점이다.
• 일반적으로 클라이언트에서 전송된 URL 주소로 연결하기 때문에 안전하다고
  생각할 수 있으나, 해당 폼의 요청을 변조함으로써 공격자는 사용자가 위험한
  URL로 접속할 수 있도록 공격할 수 있다.

㉡ 보안대책
자동 연결할 외부 사이트의 URL과 도메인은 화이트 리스트로 관리하고, 사용자
입력값을 자동 연결할 사이트 주소로 사용하는 경우에는 입력된 값이 화이트
리스트에 존재하는지 확인해야 한다.

⑦ XQuery 삽입

㉠ 정의
XQuery를 사용하여 XML 데이터에 대한 동적 쿼리를 생성할 때 사용하는 외부
입력값에 대해 적절한 검증절차가 존재하지 않으면 공격자가 쿼리문의 구조를
임의로 변경할 수 있게 된다. 이로 인해 허가되지 않은 데이터를 조회하거나
인증절차를 우회할 수 있다.

㉡ 보안대책
XQuery에 사용되는 외부 입력데이터에 대하여 특수문자 및 쿼리 예약어를 필터
링하고, XQuery를 사용한 쿼리문은 스트링을 연결하는 형태로 구성하지 않고
파라미터(Parameter)화된 쿼리문을 사용한다.

⑧ XPath 삽입

㉠ 정의
외부 입력값을 적절한 검사과정 없이 XPath 쿼리문 생성을 위한 문자열로 사용
하면, 공격자는 프로그래머가 의도하지 않았던 문자열을 전달하여 쿼리문의 의
미를 왜곡시키거나 그 구조를 변경하고 임의의 쿼리를 실행하여 인가되지 않은
데이터를 열람할 수 있다.

㉡ 보안대책
Xpath 쿼리에 사용되는 외부 입력데이터에 대하여 특수문자(" , [ , ] , / , = , @
등) 및 쿼리 예약어 필터링을 수행하고 파라미터가 쿼리문을 지원하는 XQuery를
사용한다.

⑨ LDAP 삽입

㉠ 정의
• 공격자가 외부 입력을 통해서 의도하지 않은 LDAP(Lightweight Directory
  Access Protocol) 명령어를 수행할 수 있다. 즉 웹 응용프로그램이 사용자가
  제공한 입력을 올바르게 처리하지 못하면, 공격자가 LDAP 명령문의 구성을
  바꿀 수 있다.
  이로 인해 프로세스가 명령을 실행한 컴포넌트와 동일한 권한(Authentication)
  을 가지고 동작하게 된다.
• LDAP 쿼리문이나 결과로 외부 입력이 부분적으로 적절한 처리없이 사용되면,
  LDAP 쿼리문이 실행될 때 공격자는 LDAP 쿼리문의 내용을 마음대로 변경할
  수 있다.


㉡ 보안대책
• DN(Distinguished Name)과 필터에 사용되는 사용자 입력값에는 특수문자가
  포함되지 않도록 특수문자를 제거한다.
• 만약 특수문자를 사용해야 하는 경우에는 특수문자(=, +, <, >, #, ;, ₩
  등)가 실행명령이 아닌 일반문자로 인식되도록 처리한다.


⑩ 크로스사이트 요청 위조

㉠ 정의
• 특정 웹사이트에 대해서 사용자가 인지하지 못한 상황에서 사용자의 의도와는
  무관하게 공격자가 의도한 행위(수정, 삭제, 등록 등)를 요청하게 하는 공격을
  말한다.
• 공격자는 사용자가 인증한 세션이 특정 동작을 수행하여도 계속 유지되어 정상적인
  요청과 비정상적인 요청을 구분하지 못하는 점을 악용하여 공격을 수행한다.
• 웹 응용프로그램에 요청을 전달할 경우, 해당 요청의 적법성을 입증하기 위하
  여 전달되는 값이 고정되어 있고, 이러한 자료가 GET방식으로 전달된다면
  공격자가 이를 쉽게 알아내어 원하는 요청을 보냄으로써 위험한 작업을 요청할
  수 있게 된다.

㉡ 보안대책
• 입력화면 폼 작성 시 GET 방식보다는 POST 방식을 사용하고 입력화면 폼과
  해당 입력을 처리하는 프로그램 사이에 토큰을 사용하여, 공격자의 직접적인
  URL 사용이 동작하지 않도록 처리한다.
• 특히 중요한 기능에 대해서는 사용자 세션검증과 더불어 재인증을 유도한다.

⑪ 디렉터리 경로 조작

㉠ 정의
• 외부의 입력을 통하여 “디렉터리 경로 문자열” 생성이 필요한 경우, 외부 입력
  값에 대해 경로 조작에 사용될 수 있는 문자를 필터링하지 않으면, 의도하지
  않은 접근 제한 영역에 대한 경로 문자열 구성이 가능해져 시스템 정보노출,
  서비스 장애 등을 유발시킬 수 있다.
• 경로 조작을 통해 인가되지 않은 접근 권한을 획득하여, 설정에 관련된 파일을
  변경하거나 실행시킬 수 있다.

㉡ 보안대책
파일경로와 이름을 생성할 때 외부 입력값을 사용하는 경우, 정해진 경로 이외의
디렉터리와 파일에 접근할 수 없도록 처리하고 외부 입력값에 대해 replaceAll()
등의 메소드를 사용하여 의도하지 않은 경로로의 접근을 허용하는 위험 문자(“,
/, ₩, ..)을 제거하는 필터링을 수행한다.

⑫ HTTP 응답분할

㉠ 정의
HTTP 요청에 들어 있는 파라미터(Parameter)가 HTTP 응답헤더에 포함되어
사용자에게 다시 전달될 때, 입력값에 CR(Carriage Return)이나 LF(Line Feed)
와 같은 개행문자가 존재하면 HTTP응답이 2개 이상으로 분리될 수 있다. 이
경우 공격자는 개행문자를 이용하여 첫 번째 응답을 종료시키고, 두 번째 응답에
악의적인 코드를 주입하여 XSS 및 캐시 훼손(Cache Poisoning) 공격 등을 수행
할 수 있다.


ㄴ 보안대책
• 외부에서 입력된 파라미터(Parameter)를 HTTP 응답헤더(Set Cookie 등)에 포함시킬 경우, CRLF 등의 개행문자를 제거한다.

⑬ 정수 오버플로우
㉠ 정의
정수형 변수의 오버플로우는 정수값이 증가하면서, 허용된 가장 큰 값보다 더 커져서 실제 저장되는 값은 의도하지 않게 아주 작은 수이거나 음수가 될 수 있다. 특히 버퍼뿐만 아니라, 메모리 할당, 메모리 복사 등과 같은 조건으로 사용자가 제공하는 입력값을 사용하고 그 과정에서 정수 오버플로우가 발생하는 경우 보안상 문제를 유발할 수 있다.

㉡ 보안대책
• 언어/플랫폼별 정수타입의 범위를 확인하여 사용한다. 정수형 변수를 연산에 사용하는 경우, 결과값의 범위를 체크하는 모듈을 사용한다.
• 특히 외부 입력값을 동적으로 할당하여 사용하는 경우, 변수의 값 범위를 검사하여 적절한 범위에 존재하는지 확인한다.

⑭ 보호메커니즘을 우회할 수 있는 입력값 변조
㉠ 정의
• 응용프로그램이 외부 입력값에 대한 신뢰를 전제로 보호메커니즘을 사용하는 경우, 공격자가 입력값을 조작할 수 있다면 보호메커니즘을 우회할 수 있게 된다.
• 개발자들이 흔히 쿠키, 환경변수 또는 히든필드와 같은 입력값이 조작될 수 없다고 가정하지만, 공격자는 다양한 방법을 통해 이러한 입력값들을 변경할 수 있고 조작된 내용은 탐지되지 않을 수 있다.
• 인증이나 인가와 같은 보안설정이 이런 입력값(쿠키, 환경변수, 히든필드 등)에 기반해 수행되는 경우, 공격자는 이런 입력값을 조작하여 응용프로그램의 보안을 우회할 수 있다. 예로, 충분한 암호화, 무결성체크 또는 다른 메커니즘이 없는 경우에 외부사용자에 의한 입력값을 신뢰해서는 안 된다.

㉡ 보안대책
• 상태정보나 민감한 데이터, 특히 사용자 세션정보와 같은 중요한 정보는 서버에 저장하고 보안확인 절차도 서버에서 실행한다.
• 보안설계 관점에서 신뢰할 수 없는 입력값이 어플리케이션 내부로 들어올 수 있는 지점과 보안결정에서 사용되는 입력값을 식별하고, 제공되는 입력값에 의존할 필요가 없는 구조로 변경할 수 있는지 검토한다.

2. 보안기능
① 적절한 인증없이 중요기능 허용
㉠ 정의
적절한 인증과정 없이 중요정보(계좌이체 정보, 개인정보 등)를 열람(또는 변경)할 때 발생하는 보안약점이다.

㉡ 보안대책
• 클라이언트의 보안검사를 우회하여 서버에 접근하지 못하도록 설계하고, 중요한 정보가 있는 페이지는 재인증을 적용(은행 계좌이체 등)한다.
• 안전하다고 확인된 라이브러리나 프레임워크(OpenSSL이나 ESAPI의 보안 기능 등)를 사용하는 것이 중요하다.


② 부적절한 인가
㉠ 정의
프로그램이 모든 가능한 실행경로에 대해서 접근제어를 검사하지 않거나 불완전하게 검사하는 경우, 공격자는 접근 가능한 실행경로를 통해 정보를 유출할 수 있다.

㉡ 보안대책
• 응용프로그램이 제공하는 정보와 기능을 역할에 따라 배분함으로써 공격자에게 노출되는 공격 노출면(Attack Surface)을 최소화하고, 사용자의 권한에 따른 ACL(Access Control List)을 관리한다.
• 프레임워크를 사용해서 보안약점을 피할 수도 있는데 예를 들면, JAAS Authorization Framework나 OWASP ESAPI Access Control 등이 인증 프레임워크로 사용 가능하다.

③ 중요한 자원에 대한 잘못된 권한설정
㉠ 정의
SW가 중요한 보안관련 자원에 대하여 읽기 또는 수정 권한을 의도하지 않게 허가할 경우, 권한을 갖지 않은 사용자가 해당자원을 사용하게 된다.

㉡ 보안대책
설정파일, 실행파일, 라이브러리 등은 SW 관리자에 의해서만 읽고 쓰기가 가능하도록 설정하고 설정파일과 같이 중요한 자원을 사용하는 경우, 허가받지 않은 사용자가 중요한 자원에 접근 가능한지 검사한다.

④ 취약한 암호화 알고리즘 사용
㉠ 정의
SW 개발자들은 환경설정 파일에 저장된 패스워드를 보호하기 위하여 간단한 인코딩 함수를 이용하여 패스워드를 감추는 방법을 사용하기도 한다. 그렇지만 Base64와 같은 지나치게 간단한 인코딩 함수를 사용하는 것은 패스워드를 제대로 보호할 수 없다.

㉡ 보안대책
• 자신만의 암호화 알고리즘을 개발하는 것은 위험하며, 학계 및 업계에서 이미 검증된 표준화된 알고리즘을 사용한다.
• 기존에 취약하다고 알려진 DES, RC5 등의 암호화알고리즘을 대신하여, 3DES, AES, SEED 등의 안전한 암호알고리즘으로 대체하여 사용한다. 또한, 업무관련 내용, 개인정보등에 대한 암호 알고리즘 적용시, IT 보안인증 사무국이 안전성을 확인한 검증필 암호모듈을 사용해야 한다.

⑤ 사용자 중요정보 평문 저장(또는 전송)
㉠ 정의
프로그램이 개인정보, 인증정보, 금융정보 등의 사용자 중요정보를 평문으로 저장하거나 통신 채널을 통해서 송수신할 경우, 통신채널 스니핑을 통해 인가되지 않은 사용자에게 민감한 데이터가 노출될 수 있는 보안약점이다.

㉡ 보안대책
개인정보(주민등록번호, 여권번호 등), 금융정보(카드번호, 계좌번호 등), 패스워드 등을 저장할 때에는 반드시 암호화하여 저장하고, 통신 채널을 통해 전송할 때에도 암호화한다.


CMVP
암호모듈 검증제도(CMVP, Cryptographic Module Validation Program)는 미국의 NIST(National Institute of Standards and Technology)와 캐나다의 CSEC(Communications Security Establishment Canada)가 공동으로 주관하여 암호모듈 검증을 시행하기 위하여 시작한 제도이다.
암호모듈 검증제도는 민감한 정보의 보호를 위해 양국의 연방 정부가 FIPS 140-1과 FIPS 140-2를 사용하여 암호모듈을 검증을 시작하였다. 현재 암호모듈 검증제도는 미국과 캐나다를 제외하고 여러 국가에서 시행되어지고 있는데 대표적으로 한국, 일본, 영국에서 시행되어지고 있다.
국내에서도 시행되어지고 있는 CMVP의 경우 전자정부법 시행령 제 69조 [암호모듈 시험 및 검증지침]에 의거, 국가·공공기관 정보통신망에서 소통되는 자료 중에서 비밀로 분류되지 않은 중요 정보의 보호를 위해 사용되는 암호모듈의 안전성과 신뢰성을 검증하는 제도이다. 검증대상에 암호모듈은 소프트웨어, 하드웨어, 펌웨어 또는 이들을 조합한 형태로 구현될 수 있으며 소프트웨어 암호모듈을 검증기준 또는 암호모듈 검증기준(KS X ISO/IEC 19790)을 준수하여 시험되고 있다. 국가·공공·민간기관에서 사용하는 매일 암호화 모듈, 구간암호화 모듈, PKI 제품, SSO 제품, 키보드 암호화 모듈 등 보안제품에는 암호모듈검증제도를 통해 검증 받은 암호모듈이 탑재되어야 한다.

⑥ 하드코드된 패스워드
㉠ 정의
• 프로그램 코드 내부에 하드코드된 패스워드를 포함하고, 이를 이용하여 내부 인증에 사용하거나 외부 컴포넌트와 통신을 하는 경우, 관리자 정보가 노출될 수 있어 위험하다.
• 코드 내부에 하드코드된 패스워드가 인증실패를 야기하는 경우, 시스템 관리자가 그 실패의 원인을 파악하기 쉽지 않은 단점이 있다.

㉡ 보안대책
패스워드는 암호화하여 별도의 파일에 저장하여 사용하고 SW설치 시 사용하는 디폴트 패스워드, 키 등을 사용하는 대신 “최초-로그인”모드를 두어 사용자가 직접 패스워드나 키를 입력하도록 설계한다.

⑦ 충분하지 않은 키 길이 사용
㉠ 정의
• 길이가 짧은 키를 사용하는 것은 암호화 알고리즘을 취약하게 만들 수 있다.
• 키는 암호화 및 복호화에 사용되는데 검증된 암호화 알고리즘을 사용하더라도 키 길이가 충분히 길지 않으면 짧은 시간 안에 키를 찾아낼 수 있고 이를 이용해 공격자가 암호화된 데이터나 패스워드를 복호화할 수 있다.

㉡ 보안대책
RSA 알고리즘은 적어도 2,048비트 이상의 길이를 가진 키와 함께 사용해야 하고, 대칭암호화 알고리즘(Symmetric Encryption Algorithm)의 경우에는 적어도 128비트 이상의 키를 사용한다.

⑧ 적절하지 않은 난수 값 사용
㉠ 정의
예측 가능한 난수를 사용하는 것은 시스템에 보안약점을 야기시킨다. 예측 불가능한 숫자가 필요한 상황에서 예측 가능한 난수를 사용한다면, 공격자는 SW에서 생성되는 다음 숫자를 예상하여 시스템을 공격하는 것이 가능하다.

㉡ 보안대책
• 난수발생기에서 시드(Seed)를 사용하는 경우에는 예측하기 어려운 방법으로 변경한다.
• 일반적으로 Java에서는 java.lang.Math.random() 메소드 사용을 자제하고, java.util.Random 클래스를 사용, C에서는 rand() 대신 randomize(seed)를 사용하는 것이 좋다.
• 세션ID, 암호화키 등 보안 결정을 위한 값을 생성하고 보안결정을 수행하는 경우에는 java.security.SecureRandom 클래스를 사용한다.

⑨ 패스워드 평문 저장
㉠ 정의
패스워드를 설정파일에 암호화되지 않은 상태로 저장하게 되면, 암호가 외부에 직접적으로 드러날 위험성이 있다. 따라서 패스워드는 쉽게 접근할 수 없는 저장소에 저장하는지 아니면 암호화한 상태로 저장하여야 한다.

㉡ 보안대책
패스워드를 외부 환경 파일에 저장한다면, 암호화하여 저장한다.


⑩ 하드코드된 암호화 키
㉠ 정의
• 코드 내부에 하드코드된 암호화키를 사용하여 암호화를 수행하면 암호화된 정보가 유출될 가능성이 높아진다.
• 많은 SW 개발자들이 내부의 고정된 패스워드의 해쉬를 계산하여 저장하는 것이 패스워드를 악의적인 공격자로부터 보호할 수 있다고 믿고 있다. 그러나 많은 해쉬 함수들이 역계산이 가능하며 적어도 무차별 대입(Brute-Force) 공격에는 취약하다는 것을 고려해야 한다.

㉡ 보안대책
암호화 알고리즘에서 상수가 아닌 키를 사용해서 암호화를 수행하도록 설계하여야 하며, 암호화되었다고 패스워드를 상수의 형태로 프로그램 소스코드 내부에 저장하여 사용하면 안 된다.

⑪ 취약한 패스워드 허용
㉠ 정의
사용자에게 강한 패스워드 조합규칙을 요구하지 않으면 사용자 계정이 취약하게 된다. 안전한 패스워드를 생성하기 위해서는 숫자/문자/특수문자를 조합하여 9자리 이상으로 해야 한다.

㉡ 보안대책
패스워드 생성 시 강한 조건 검증을 수행한다. 비밀번호(패스워드)는 숫자와 영문자, 특수문자 등을 혼합하여 9자리 이상으로 정하고, 분기별로 1회 이상 주기적으로 변경 사용하도록 해야 한다.

⑫ 사용자 하드디스크에 저장되는 쿠키를 통한 정보노출
㉠ 정의
대부분의 웹 응용프로그램에서 쿠키는 메모리에 상주하며, 브라우저의 실행이 종료되면 사라진다. ‘프로그램을 위한 경우 브라우저 세션이 끝난 후에도 지속적으로 저장되도록 설정할 수 있으며 이것은 디스크에 기록되고 다음 브라우저 세션이 시작되었을 때 메모리에 로드된다.’ 개인정보, 인증정보 등이 영속적인 쿠키(Persistent Cookie)에 저장된다면 공격자는 쿠키에 접근할 수 있는 보다 많은 기회를 가지게 되며, 이는 시스템을 취약하게 만든다.

㉡ 보안대책
쿠키의 만료시간은 세션이 지속되는 시간과 관련하여 최소한으로 설정하고 영속적인 쿠키에는 사용자 권한 등급, 세션ID가 포함되지 않도록 한다.

⑬ 보안속성 미적용으로 인한 쿠키 노출
㉠ 정의
HTTPS로만 서비스하는 경우, 모든 정보가 암호화되어 안전하게 전송된다고 생각한다. 그러나 보안에 민감한 데이터를 브라우저 쿠키에 저장할 때 보안 속성을 설정하지 않으면 공격자에게 단순한 텍스트의 형태로 노출될 수 있다.

㉡ 보안대책
HTTPS로만 서비스하는 경우 브라우저 쿠키에 데이터를 저장할 때, 반드시 쿠키 객체의 setSecure(true) 메소드를 호출하여 보안속성을 설정한다. 한 사이트(도메인)에서 HTTP와 HTTP와 HTTPS를 함께 사용하는 경우 setSecure(true) 메소드를 호출하면 해당 쿠키가 HTTP를 통해서는 서버에 전송되지 않아 장애가 발생할 수 있으므로 주의해야 한다.










⑭ 주석문 안에 포함된 패스워드 등 시스템 주요정보
    ① 정의
        • 패스워드를 주석문에 넣어두면 시스템 보안이 훼손될 수 있다.
        • 소프트웨어 개발자가 편의를 위해서 주석문에 패스워드를 적은 경우, 소프트웨어가 완성된 후에는 그것을 제거하는 것이 매우 어렵게 된다. 또한 공격자가 소스코드에 접근할 수 있다면 아주 쉽게 시스템에 침입할 수 있다.
    ② 보안대책
        주석에는 ID, 패스워드 등 보안과 관련된 내용을 기입하지 않는다.

⑮ 솔트 없이 일방향 해시 함수 사용
    ① 정의
        패스워드 저장시 일방향 해시 함수의 성질을 이용하여 패스워드의 해시값을 저장한다. 만약 패스워드는 솔트(Salt) 없이 해시하여 저장한다면, 공격자는 레인보우 테이블과 가능한 모든 패스워드에 대해 해시값을 미리 계산하고, 이를 이용한 전수조사를 통해 패스워드를 찾을 수 있게 된다.
    ② 보안대책
        패스워드 저장시 패스워드와 솔트를 해시함수의 입력으로 하여 얻은 해시값을 저장한다.

⑯ 무결성 검증없는 코드 다운로드
    ① 정의
        원격으로부터 소스코드 또는 실행파일을 무결성 검사 없이 다운로드 받고 이를 실행하는 제품들이 종종 존재한다. 이는 호스트 서버의 변조, DNS스푸핑(Spoofing) 또는 전송 중의 코드 변조 등의 방법을 이용하여 공격자가 악의적인 코드를 실행할 수 있도록 한다.
    ② 보안대책
        • DNS스푸핑(Spoofing)을 방어할 수 있는 DNS lookup을 수행하고 코드 전송시 신뢰할 수 있는 암호기법을 이용하여 코드를 암호화한다.
        • 다운로드된 코드는 작업을 위해 필요한 최소한의 권한으로 실행하도록 한다. 이와 함께 자일(Jail) 또는 이와 유사한 샌드박스(Sandbox)환경에서 실행되도록 한다.

3. 시간 및 상태
    ① 경쟁조건 : 검사시점과 사용시점(TOCTOU)
        ① 정의
            • 병렬시스템(멀티프로세스로 구현한 응용프로그램)에서는 자원(파일, 소켓 등)을 사용하기에 앞서 자원의 상태를 검사한다.
            • 하지만 자원을 사용하는 시점과 검사하는 시점이 다르기 때문에 검사하는 시점(Time of Check)에 존재하던 자원이 사용하던 시점(Time of Use)에 사라지는 등 자원의 상태가 변하는 경우가 발생한다.
            • 하나의 자원에 대하여 동시에 검사시점과 사용시점이 달라 생기는 보안약점으로 인해 동기화 오류뿐 아니라 교착상태 등과 같은 문제점이 발생할 수 있다.
        ② 보안대책
            공유자원(예 파일)을 여러 프로세스가 접근하여 사용할 경우, 동기화 구문을 사용하여 한 번에 하나의 프로세스만 접근 가능하도록(Synchronized mutex 등)하는 한편, 성능에 미치는 영향을 최소화하기 위해 임계코드 주변만 동기화 구문을 사용한다.

    ② 제어문을 사용하지 않는 재귀함수
        ① 정의
            • 재귀의 순환회수를 제어하지 못하여 할당된 메모리나 프로그램 스택 등의 자원을 과다하게 사용하면 위험하다.
            • 대부분의 경우 귀납조건(Base Case)이 없는 재귀함수는 무한 루프에 빠져 듣게 되고 자원고갈을 유발함으로써 시스템의 정상적인 서비스를 제공할 수 없게 한다.
        ② 보안대책
            모든 재귀 호출시, 재귀 호출 수를 제한하거나 초기값을 설정(상수)하여 재귀 호출을 제한해야 한다.

4. 에러처리
    ① 오류메시지 통한 정보노출
        ① 정의
            • 응용프로그램이 실행환경, 사용자, 관련 데이터에 대한 민감한 정보를 포함하는 오류 메시지를 생성하여 외부에 제공하는 경우 공격자의 악성 행위를 도와줄 수 있다.
            • 예외 발생 시 에이전트이나 스택 트레이스를 출력하는 경우 프로그램 내부구조를 쉽게 파악할 수 있다.
        ② 보안대책
            • 오류메시지는 정해진 사용자에게 유용한 최소한의 정보만 포함하도록 한다.
            • 소스코드에서 예외 상황은 내부적으로 처리하고 사용자에게 민감한 정보를 포함하는 오류를 출력하지 않도록 미리 정의된 메시지를 제공하도록 설정한다.

    ② 오류 상황 대응 부재
        ① 정의
            오류가 발생할 수 있는 부분을 확인하였으나 이러한 오류에 대하여 예외처리를 하지 않을 경우 공격자는 오류 상황을 악용하여 개발자가 의도하지 않은 방향으로 프로그램이 동작하도록 할 수 있다.
        ② 보안대책
            오류가 발생할 수 있는 부분에 대하여 제어문을 사용하여 적절하게 예외처리(C/C++에서 if와 switch, java에서 try-catch 등)를 한다.

    ③ 적절하지 않은 예외처리
        ① 정의
            프로그램 수행 중에 함수의 결과 값에 대한 적절한 처리 또는 예외상황에 대한 조건을 적절하게 검사하지 않을 경우 예기치 않은 문제를 야기할 수 있다.
        ② 보안대책
            값을 반환하는 모든 함수의 결과 값을 검사하여 그 값이 기대한 값인지 검사하고 예외 처리를 사용하는 경우에 광범위한 예외처리 대신 구체적인 예외처리를 수행한다.

퍼징(Fuzzing)

1989년 Wisconsin대학 Madison 캠퍼스의 Barton Miller 교수가 개발한 퍼징(Fuzzing)은 임의로 발생시킨 데이터를 프로그램의 입력으로 사용하는 소프트웨어 테스트 기법이다.
이 방법의 목적은 프로그램 또는 함수가 비정상적인 입력을 올바르게 처리하는지 아니면 종료되거나 적절하지 못하게 반응하는지 등을 확인하는 것이다.
퍼징의 주요 장점은 단순성과 프로그램에 대한 예상 입력에 대한 가정으로부터 자유롭다는 것이다. 테스트를 위한 많은 데이터를 만들어내는 비용도 매우 적다. 각각 이런 테스트 프로그램의 보안 결점뿐만 아니라 신뢰성을 확인하는 데도 도움을 준다.
입력을 완전히 임의로 만들 수도 있지만 어떤 형판에 맞춰 임의로 만들 수도 있다. 이런 형판은 버그가 일어나리라를 검사하기 위해 설계된다. 예를 들면 매우 긴 입력, 공백이나 단어 경계가 없는 텍스트 입력 등이 있다. 네트워크 프로토콜에 대해 사용될 때, 이 형판은 프로토콜의 중요한 부분을 대상으로 할 수 있다. 이러한 형판은 버그를 찾을 가능성을 높여준다. 형판은 단순한 입력에 대한 가정을 한다는 것이다. 다른 형태의 입력에 의한 버그는 놓칠 수 있다. 따라서 이런 기법들의 결함을 통해 합리적인 입력의 범위를 정하는 것이 필요하다. 퍼징은 개념적으로 매우 간단한 테스트 방법이지만 제한적이고 자주 사용되어야 한다.


5. 코드오류
    ① 널(Null)포인터 역참조
        ① 정의
            • 널 포인터 역참조는 ‘일반적으로 그 객체가 널(Null)이 될 수 없다’라고 하는 가정을 위반했을 때 발생한다.
            • 공격자가 의도적으로 널 포인터 역참조를 발생시키는 경우 그 결과 발생하는 예외 상황을 이용하여 추후의 공격을 계획하는 데 사용될 수 있다.
        ② 보안대책
            널이 될 수 있는 레퍼런스(Reference)는 참조하기 전에 널 값인지를 검사하여 안전한 경우에만 사용한다.

    ② 부적절한 자원 해제
        ① 정의
            • 프로그램의 자원 열린 파일디스크립터(Open File Descriptor), 힙 메모리(Heap Memory), 소켓(Socket) 등은 유한한 자원이다.
            • 이러한 자원을 할당받아 사용한 후, 더 이상 사용하지 않는 경우에는 적절히 반환하여야 하는데 프로그램 오류 또는 에러로 사용이 끝난 자원을 반환하지 못하는 경우이다.
        ② 보안대책
            자원을 획득하여 사용한 다음에는 반드시 자원을 해제하여 반환한다.

6. 캡슐화
    ① 잘못된 세션에 의한 데이터 노출
        ① 정의
            • 다중 스레드 환경에서는 싱글톤(Singleton) 객체 필드에 경쟁조건(Race Condition)이 발생할 수 있다.
            • 따라서 다중 스레드 환경인 java의 서블릿(servlet) 등에서는 정보를 저장하는 멤버변수가 포함되지 않도록 하여, 서로 다른 세션에서 데이터를 공유하지 않도록 해야 한다.
        ② 보안대책
            싱글톤 패턴을 사용하는 경우, 변수 범위(Scope)에 주의를 기울여야 한다. 특히 Java에서는 HttpServlet 클래스의 하위클래스에서 멤버필드를 선언하지 않도록 하고 필요한 경우 지역 변수를 선언하여 사용한다.

    ② 제거되지 않고 남은 디버그 코드
        ① 정의
            디버그 코드는 설정 등의 민감한 정보를 담거나 시스템을 제어하게 허용하는 부분을 담고 있을 수 있다. 만일 남겨진 채로 배포될 경우 공격자가 식별과정을 우회하거나 의도하지 않은 정보와 제어 정보를 노출될 수 있다.
        ② 보안대책
            • SW배포 전 반드시 디버그 코드를 확인 및 삭제한다.
            • 일반적으로 Java개발자의 경우 웹 어플리케이션을 제작할 때 디버그용도의 코드를 main()에 개발한 후 이를 삭제하지 않는 경우가 많다. 디버깅이 끝나면 main() 메소드를 삭제해야 한다.

    ③ 시스템 데이터 정보 노출
        ① 정의
            시스템, 관리자, DB 정보 등 시스템의 내부 데이터가 공개되면 공격자에게 또 다른 공격의 빌미를 제공하게 된다.
        ② 보안대책
            일부 개발자의 경우 예외상황이 발생할 경우 시스템 메시지 등의 정보를 화면에 출력하도록 하는 경우가 많다. 예외상황이 발생할 때 시스템의 내부 정보가 화면에 출력하지 않도록 개발한다.

    ④ Public 메소드부터 반환된 Private배열
        ① 정의
            Private 배열을 Public메소드가 반환하면 배열 주소값이 외부에 공개됨으로써 외부에서 배열 수정이 가능해진다.
        ② 보안대책
            Private로 선언된 배열을 Public 메소드를 통해서 반환하지 않도록 하고 필요한 경우 배열의 복제본을 반환하거나 수정을 제어하는 별도의 Public 메소드를 선언하여 사용한다.

    ⑤ Private 배열에 Public 데이터 할당
        ① 정의
            Public으로 선언된 데이터 또는 메소드의 파라미터를 Private배열에 저장하면 Private배열을 외부에서 접근할 수 있다.
        ② 보안대책
            Public으로 선언된 데이터가 Private으로 선언된 배열에 저장되지 않도록 한다.

7. API 오류
    ① DNS lookup에 의존한 보안결정
        ① 정의
            공격자가 DNS엔트리를 속일 수 있으므로 도메인명에 의존해서 보안결정(인증 및 접근 통제 등)을 하지 않아야 한다. 만약 로컬 DNS서버의 캐시가 공격자에 의해 오염된 상황이라면 사용자와 특정 서버간의 네트워크 공격자를 경유하도록 할 수도 있다. 또한 공격자가 마치 동일 도메인에 속한 서버인 것처럼 위장할 수도 있다.
        ② 보안대책
            보안결정에서 도메인명을 이용한 DNS lookup을 하지 않도록 한다.
